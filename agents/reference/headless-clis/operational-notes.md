# Headless CLI operational notes

Notes from live sessions, not vendor documentation. Read alongside the matching vendor file in this directory. Flags come from the installed binary's `--help`; each vendor page lags its binary.

## Claude Code

- Claude Code 2.1.272 through 2.1.317 reject a `--json-schema` document declaring `https://json-schema.org/draft/2020-12/schema` before starting a model request: 2.1.317 exits 1 with `Error: --json-schema is not a valid JSON Schema: no schema with key or ref "https://json-schema.org/draft/2020-12/schema"` on stderr. Use a Draft 7 schema instead.
- Check stderr for launch failures and the result event on stdout for failures during a run. Preserve the exit code and report a recognized error category without printing raw provider output. An invalid schema prints `Error: --json-schema is not a valid JSON Schema` on stderr; other failures need the result event.
- The official [model configuration reference](https://code.claude.com/docs/en/model-config) lists the pinned model IDs and the effort levels each model supports. Read it instead of inferring from the examples in `claude --help`.

## Grok CLI

- The vendor page omits `--prompt-file`, `--permission-mode`, `--reasoning-effort`, `--sandbox`, `--allow`, and `--add-dir`. `grok --help` on grok 1.0.70 lists them all.
- `--prompt-file <path>` is its own single-turn mode: on grok 1.0.46, `-p` together with `--prompt-file` exits 2 with "the argument '--single <PROMPT>' cannot be used with '--prompt-file <PATH>'". Pass one of them.
- A read-only run, such as a review, removes the shell, write, and edit tools: `grok --prompt-file <absolute path> --tools read_file,list_dir,grep,todo_write --cwd <dir>`. On grok 1.0.50 the run then has only those four tools plus the MCP meta-tools `search_tool` and `use_tool`, and a probe asked to run a command, write a file, and edit a file could do none of them. The reviewer cannot run `git`, so hand it the diff as a file. Add `web_search,web_fetch` when it must read docs; a probe with them still had no shell or write tool. Keep `spawn_subagent` and `get_command_or_subagent_output` out: with both added, the run executed shell commands anyway. Output prints only at the end.
- `--allow` rules are not an allowlist. A shell command that matches no rule goes to Grok's own check instead: on grok 1.0.50 a `mkdir` and `touch` in the working folder ran under both `--permission-mode default` and `dontAsk`, and a long multi-command script needed approval, which a headless run cannot give. The whole turn then ends with no report, exit 0, and `"cancellation_category":"permission_cancelled"` in the session's `events.jsonl` under `~/.grok/sessions/<url-encoded cwd>/`.
- Point a review's `--cwd` at a throwaway copy or a detached worktree, never at a checkout with uncommitted work.
- A headless run reads only inside `--cwd`. On grok 1.0.70, adding `--add-dir` makes it exit 1 at once with "Couldn't create session: additionalDirectories is not supported: a session works only in its cwd". Paste a file from outside `--cwd`, such as a spec, into the `--prompt-file` text instead.
- `-s/--session-id` starts a new conversation with an unused UUID; `-r/--resume` restores one with full context. The vendor page's "create or resume" wording for `-s` is wrong for 1.0.25, and a non-UUID value fails with exit 1. Pin the id before launch so a repair round can find the session after a dead run. Read it from the kernel, which needs no package; `uuidgen` comes from Debian's `uuid-runtime`, and an empty id fails with "--session-id must be a valid UUID (got '')":

```bash
SID=$(cat /proc/sys/kernel/random/uuid)
grok -p "$(cat /absolute/task.md)" --session-id "$SID" --always-approve --output-format json --cwd <worktree>
grok -p "<findings>" --resume "$SID" --output-format json --cwd <worktree>
```

- Pass absolute paths. A relative path is reported to resolve against `--cwd`, not the launching shell.
- `--output-format json` yields one object with `text`, `stopReason`, `sessionId`, `num_turns`, `total_cost_usd`.
- `--sandbox <profile>` takes a built-in profile (`workspace`, `devbox`, `read-only`, `strict`) or one defined in `~/.grok/sandbox.toml` or `.grok/sandbox.toml`; a codex-style value such as `workspace-write` errors. The table is in `~/.grok/docs/user-guide/18-sandbox.md`. The Linux profiles need `bwrap`: on devbox, which lacks bubblewrap, grok 1.0.50 refuses to start with "Install bubblewrap".
- `--always-approve` approves every tool execution. It is a broader grant, for authorized unattended runs only.
- `grok mcp list` shows no MCP servers, so a headless run cannot reach Linear or any other MCP-backed system.
- Optional MCP startup can emit authentication or handshake failures. Isolate or disable optional integrations when a clean startup is required, and verify the command's exit status and final output before calling the run failed.
- Unverified: an immediate exit 1 with "Not signed in" is reported when `~/.grok/auth.json` is missing and a stale `auth.json.lock` remains. Recovery is an interactive `grok login` by Omer.

## Codex CLI

- The vendor page omits `-m`, `-c`, `-C`, `--worktree`, `--add-dir`, `--profile`, `--image`, `--thread-source`, `--enable`, and `--disable`. `codex exec --help` on codex-cli 0.166.0 lists them.
- `codex debug models | jq -r '.models[] | "\(.slug) default=\(.default_reasoning_level) \([.supported_reasoning_levels[].effort] | join(","))"'` lists the model ids and their effort levels. Filter it every time: the raw JSON was about 600 KB on codex-cli 0.163.0. `gpt-6.1-sol` defaults to `low`, so pass `-c model_reasoning_effort=<effort>`.
- A prompt argument starting with `---` is parsed as a flag and exits 2. Pass the prompt on stdin: `codex exec --sandbox read-only -c model=<model> -c model_reasoning_effort=<effort> - < prompt.md`.
- `~/.codex/config.toml` sets the top-level `model` and `model_reasoning_effort` a bare `codex exec` runs with, and they change across sessions on this host. Global limits and defaults live under `[agents]` in `config.toml`; custom agents are standalone TOML files in `~/.codex/agents/` (the dotfiles repository's `desktop/codex/agents/`) or `.codex/agents/` in a project.
- `codex exec` spawns subagents: `multi_agent` is stable and on in codex-cli 0.166.0 (`codex features list`), they run in parallel, and each can carry its own `model` and `model_reasoning_effort` through a custom agent file. On 0.166.0 a custom agent file sets only developer instructions, model settings (`model`, `model_reasoning_effort`, `model_reasoning_summary`, `model_verbosity`), personality, disabled skills, and five feature keys, which it can only turn off: `shell_tool`, `apps`, `plugins`, `memories`, and `request_permissions_tool`. A spawned subagent takes its service tier from the root session. Codex ignores the file's `sandbox_mode`, `approval_policy`, `model_provider`, and `mcp_servers` (`codex-rs/core/src/agent/role.rs` and `child_config.rs` at tag `rust-v0.166.0`), so give the parent `codex exec` the sandbox and MCP servers its subagents need. Non-interactive runs work except that an action needing a fresh approval fails instead of prompting (read-only reviews never need one). Vendor page saved verbatim as `chatgpt-subagents.md`. Do not claim `codex exec` cannot spawn subagents.
- `/tmp` sits on the btrfs root subvolume on nixos-desktop and nixos-rog. With that layout, codex-cli 0.156 and 0.157 failed every sandboxed shell command, git included, with `error building bubblewrap command: cannot establish app-server socket mount isolation` ([openai/codex#47415](https://github.com/openai/codex/issues/47415)). On 0.163.0 the plain sandbox works: `codex sandbox -- git -C <repo> log -1` passes and a `touch` inside the repo fails with `Read-only file system`, with no wrapper (observed on nixos-rog). If that bubblewrap error returns, give codex a private tmpfs `/tmp` and bind back only the output directory: `bwrap --dev-bind / / --tmpfs /tmp --bind /tmp/claude-1000 /tmp/claude-1000 --die-with-parent -- codex exec --sandbox read-only ...`.
- Start a consult or review with `codex-ask` (nixos-config `pkgs/agent-tools`) and wait with the `wait-exit` command it prints, in 540 s slices that fit Claude Code's 600 s Bash limit; a slice that ends 124 leaves Codex running, and 125 means the session died without a status. A `timeout` around `codex exec` kills a session that is still working and loses its answer: the longest gpt-6.1-sol review under `/tmp/agents` on 02-11-2026 took 653 s, measured from its `prompt.md` to the `exit N` line. Codex 0.166.0 bounds a stall itself: the built-in OpenAI provider ends a stream silent for 300000 ms (`stream_idle_timeout_ms`) and retries it up to 5 times (`stream_max_retries`) and a request up to 4 (`request_max_retries`), then exits 1; `config.toml` cannot change these for that provider. Only `features.unbounded_connection_retries`, on by default, retries a failed connection forever, so `codex-ask` passes `--disable unbounded_connection_retries`. Silence in Codex's output is not a stall: it prints a reasoning item only once the item completes, and `--json` has no heartbeat either (source at the `rust-v0.166.0` tag, `codex-rs/model-provider-info/src/lib.rs` and `codex-rs/exec/src/event_processor_with_human_output.rs`).
- `-o/--output-last-message <file>` writes the final message even under `--sandbox read-only`, because codex itself writes it.
- A prompt that should run a Codex skill names it as `$<skill-name>`, for example `$thermo-nuclear-code-quality-review`, because that is how Codex invokes a skill, in the app, the TUI or a herdr pane. A prose mention such as "use the thermo-nuclear-code-quality-review skill" may not load it.
- Under `--sandbox read-only`, codex cannot create a temp directory, so `pytest` inside the session can fail with `FileNotFoundError: No usable temporary directory`. Observed 13-08-2026 as a failed tool call, not a dead run; re-verify on the current version.
- `codex exec resume` fails with `thread-store conflict: thread ... already has an active writer` when the target thread is open elsewhere. Send the message to the thread through the app (`codex_app__send_message_to_thread`) instead.
- `codex exec resume <thread_id>` accepts `-m`, `-c`, `--json`, and `-o`, but not `-C` or `-s`. Run it from the lane directory and set the sandbox with `-c sandbox_mode=...`. The `workspace-write` sandbox cannot write a `.git` shared across worktrees, so a worktree lane needs `danger-full-access`. Observed 10-09-2026; re-verify on the current version.
- Inside a sandboxed `codex exec` session, `systemctl --user` and other user-bus D-Bus commands fail with `Operation not permitted`. Inspect from the host side instead: process list, KWin window list.
- A forked, tool-disabled resume of a large transcript can stall in compaction. Fall back to a bounded wait and read the rollout JSONL directly with structural filters.
- Semgrep writes settings, logs, and its version cache under `$HOME`. In a read-only-home sandbox, set `SEMGREP_SETTINGS_FILE`, `SEMGREP_LOG_FILE`, and `SEMGREP_VERSION_CACHE_PATH` to writable paths before `semgrep scan`.

## Antigravity CLI (agy)

- Before each `agy -p`, run `timeout 20 agy models`, and start the run only when it lists models. When it prints `Please sign in to view available models` or `timeout` ends it, start no `-p` run and ask Omer to sign in by running `agy` in his own terminal (`! agy` in Claude Code). Never ask him for the login code.
- On agy 1.4.9 in a Claude Code Bash call, a signed-out `agy -p` printed `Authentication required. Please visit the URL to log in` with a Google OAuth URL and waited for a code until `timeout` ended it. The vendor page says such a run exits instead.
- `--mode plan` turns `response` into a pointer to `~/.gemini/antigravity-cli/brain/<conversation id>/implementation_plan.md`. On agy 1.4.9, one multi-turn plan-mode run that read files and images returned no `structured_output` key, while two short plan-mode probes kept it. Run a prompt that needs `--json-schema` output without `--mode`, and check that `structured_output` exists before reading it. The vendor page does not document `--mode`; `agy --help` lists `accept-edits`, `auto`, and `plan`.
- agy 1.4.9 loads global skills from `~/.gemini/antigravity-cli/skills`, which `desktop-sync.sh` fills with the same links as `~/.agents/skills`. It leaves out every skill whose frontmatter sets `disable-model-invocation: true`: a probe on `gemini-4-argon-high` listed `humanizer` only after that field was removed.

## tmux wrapping

- In `"<cmd> | tee f; echo MARKER"` the marker lands in the pane, which vanishes when the session ends, so a `tmux capture-pane` poller never sees it. Append the marker to the output file: `tmux new-session -d -s <name> "<cmd> > <file> 2>&1; echo \"===EXIT_\$?===\" >> <file>"`.
