# Engineering rules for specific kinds of change

`core.md` (Engineering) holds the rules every code change follows.

## Wrapper code

- Before you write, port, merge, or review wrapper code, meaning code that adds behaviour around another tool, platform, or service, such as polling it, queueing messages for it, retrying it, scheduling it, or storing its state, or code for a job a platform may already ship, such as scheduled upgrades, backups, or log rotation, check what that tool or platform already does in the installed version. For a CLI, run the `--help` of each command group the code touches; for an API or a service, read its versioned schema or official docs; when the code names or pins an older version, also read the changelog since that version. Use the tool's own command, event, or setting, or the platform's own mechanism, such as a NixOS option, a distro service, or a maintained GitHub Action, even when it drops a feature the custom code has; name the dropped feature as the trade-off, and keep custom code only for a need the request or Omer names and the tool cannot meet. When one option is a setting in a tool already running and another adds a service, even one the platform ships, prefer the setting, because the service brings its own build, secrets, and upkeep. Name the version you checked, each gap that remains, and the command or doc that showed each gap in the plan, review brief, PR body, or report, because custom machinery around a solved job is what Omer later rejects as overfitting. Bad: an inbox file and a poll loop around a tool that ships its own message command and event stream. Good: the tool's message command and event stream, with custom code only for what they lack.

## An unfamiliar feature from scratch

- Before you build an unfamiliar feature from scratch, one full of edge cases such as authentication, rate limiting, retries, a parser, or a protocol client, search for prior art on GitHub (`gh search repos`, `gh search code`) and in the package registry, because a maintained project's code and issues hold the edge cases a fresh version finds one bug at a time. Judge each candidate by its recent commits and releases, how its maintainers answer issues, and its license, because stars also count abandoned projects. Before the first edit, write down the trade-off and carry it into the plan, PR body, or final report: the case each candidate solves, the dependencies it pulls in, and where it differs from the current need. Reuse, adapt, or write your own from that comparison. Prefer a library the repository already uses, and list a new dependency's maintenance state and transitive dependencies in the trade-off. Adapt code only when its license allows use under this repository's license, keep its license notice, and name the upstream URL and commit in the license header. Logic specific to the repository needs no search; wrapper code follows the bullet above.

## A file of a kind the repository already has

- Before you add a hook, script, component, or other file of a kind the repository already has, find the closest existing one and follow its structure, naming, and error handling, because it carries conventions the docs often leave out. Call the helpers it uses instead of copying their code, and name that file in the final report or PR body. When the repository marks that file as legacy or as a migration in progress, follow the pattern the migration moves to. A new test follows `testing-discipline.md` instead.

## Timeouts around a step with its own cleanup

- Before you add a timeout around, reorder, or wrap a step that has its own cleanup or deadlines (an EXIT trap, a rollback, a wait or retry loop, a restart unit), list each failure point and what runs there, and size the outer bound above the sum of the inner deadlines.

## Stored records and references

- Give every stored record kind, and every reference from one record to another, an identity that survives each event the data goes through, such as a rename, a refresh or re-fetch, a re-import, a migration, an export and restore, or a merge of two copies. Records the system creates get a generated key it never reuses, such as a database id, UUID, or ULID, and an export carries that key and every record its references point to, so a restore keeps every reference. Records from outside keep the source's own id, such as a post or repository id, or a normalized form of their link that maps every form of one thing to one key and never maps two things to the same key. A name, title, position, path built from a title, or text match serves as an identity only when the repository records it as a deliberate choice together with the event that breaks it. Before you add a table or record kind, a stored reference (a foreign key, an id inside JSON, a link in a generated file, a cache or file key), or a format that leaves the system, write its identity, the events it survives, and the events that break it in the doc that owns the data model, in the same change, or in the PR body when the repository has no such doc. A review of such a change names each new reference, checks it against that record, and checks that the code does what the record says, because a wrong identity only shows once real data depends on it, as orphaned links, duplicates, or lost user edits. Bad: an X post's Item is keyed by its full URL, so the x.com, twitter.com, and photo-page links of one post become separate Items. Good: the key is the post's status id, which every form of the link carries, and the data-model doc says so.

## Deployment compatibility

- Determine deployment status and compatibility requirements from the target repository and current evidence. Keep product-specific production assumptions in that repository. Where those requirements permit breaking changes, prefer removing obsolete paths directly over adding compatibility layers, and update callers, stored state, and tests together.

## Browsers

- Drive browsers with the agent-browser skill. Use the box browser on devbox and nixos-desktop freely, within the task's authorization. Default to headless for a page that needs no login. When the box browser lacks a login that a secret store this session reads holds, sign it in yourself as the agent-browser skill says. When no store holds it, ask Omer to sign in once with `box-view <host>`, naming the host whose box browser you drive, because that login then serves every later agent at any hour; on nixos-rog with Omer present, the step may move to his local Brave instead, where he clicks Allow. In his Brave, local or lent, a click, a read, or a write the task already authorizes runs without asking. Ask before other GUI automation there; a request in the session that names agent-browser or an existing CDP session has already answered. Phrase the ask as an offer to do the step in his browser ("I can submit the domain verification form in your Brave; go?"), so a step this session can do never reaches him as his to-do.

## Hand fixes to live state

- When a hand fix repairs live state, update the config source of truth in the same session and add a guard against the same drift, or record a tracked follow-up when the guard spans repositories.
