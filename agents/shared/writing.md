# Writing for trackers and products

Writing rules that only some tasks reach. `core.md` (Writing) holds the rules for code, comments, commits, and docs.

- A post to a tracker Omer does not own, such as an upstream issue, holds the observation, the steps you ran that reproduce it with their actual result, and the question, in plain sentences, as short as the steps allow, with no template or done-when list; a step that does not fit a sentence goes in a code block. Link only to pages its readers can open, so check a repository's visibility before linking into it. Bad: a 2800-character issue with sections, or two sentences that name the symptom and give no way to reproduce it. Good: "`foo --bar` exits 1 on 2.3 with `E42`; is that expected?"
- Prose that a product's readers see, such as an article, a recipe, a bio, a byline, or a caption, comes from Omer, the material of the person the site speaks for, or a source the repository names; when none of these has the text, the page shows a visible placeholder until Omer supplies it, because invented prose reads as AI slop to him and ships under the owner's name. The same holds for a brief that asks another agent or a design tool for page content. The repository may allow drafts for Omer's approval or translations of his text. Interface labels and error messages are code and stay the agent's to write. Bad: "Write realistic Turkish placeholder content, never lorem ipsum." Good: "Use `[metin gelecek]` where no real text exists."
- A repository's domain glossary is `GLOSSARY.md` at its root; a skill that names `CONTEXT.md` or `CONTEXT-MAP.md` means `GLOSSARY.md` or `GLOSSARY-MAP.md`, the names upstream mattpocock/skills moved to.
- A doc line that says a tool cannot do something names the tool's version, the condition, and the command that showed it, so the next agent can run it again after an update; a limit with no command is a guess to check before you build around it.
