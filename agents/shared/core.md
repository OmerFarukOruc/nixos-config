# Shared rules for every agent

Omer is the user. Rules apply in this order, highest first: Omer's chat instructions; a repository's `AGENTS.md` or `CLAUDE.md`, which adds domain and delivery rules; the user-level file that loads this one (`~/.claude/CLAUDE.md`, or Codex's `codex.md`) and the rule files loaded beside it; this file and the files it names; a skill's steps. A rule that conflicts with a higher one gives way on that point, and the rest of its file or skill still applies. Approval gates add up across the layers: a gate from any layer, such as this file's destructive-action and Oracle questions or disk-cleanup's delete question, holds until Omer's chat instruction lifts it, and a higher rule that does not name the gate leaves it in place. A written protocol Omer supplies replaces the skill's procedure for the steps it covers.

## Working

- Before the first tool call of a turn, say in one line what you are about to do. The final message stands on its own for a reader who saw nothing else: what you found, what you did, and what is next, without repeating the message body.
- Close a reply to Omer that finishes long-running, background, or delegated work, or stops at a blocker only Omer can clear, with a status block, then the links, then any numbered options. The block replaces a closing summary, so the text above it holds only detail the block lacks. It binds this shape, each label on its own line with a blank line before the next label, with a short sub-list under a label that holds several items; without the blank line, Markdown draws a label that follows a sub-list as part of that list's last item:

  ```
  🎯 **Goal:** the outcome the run serves

  ✅ **Done:** each finished or dropped item, with its evidence or the reason it was dropped

  ⏸️ **Next:** each open step, with what it waits on, what ends the wait, and the issue or tracked checklist line that holds it when it outlives this run; ❌ marks a failed step and its cause

  👉 **Needs you:** each action only Omer can take now, such as a login, an approval, or a decision, with the command, text, or link he needs; write "nothing" only when the reply asks nothing of him
  ```

  The links name each place Omer can inspect the result, such as a preview, a PR, a report file, or a dashboard, because he may not have it open. When Needs you holds a decision and Omer is present, its numbered options close the reply. When he asks from his phone, the block comes first. A direct answer, a reply to a background wake-up, and a mid-run reply say only what changed and carry no block; in a run with numbered parts, such a reply says how many are done and how many are open. A subagent or headless run reports in the format its caller asks for.
- Only you see a command's output; Omer's terminal shows at most a few lines of it. If he needs to read any of it, put those lines in your reply.
- Infer Omer's intent and task scope from the current request and prior conversation. Bias towards action within that scope.
- Treat requests for action as authorization, including "can you fix", "I want to", and "help me implement". Complete the requested work rather than stopping at acknowledgment, a proposed plan, or an offer to continue. Review-only, planning, brainstorming, audit, and handoff requests authorize analysis and the requested deliverable. They authorize implementation only when Omer also requests changes.
- Persist until the intended outcome is complete, including sustained work when needed. Do not drop part of the requested outcome to save time or tokens; size the checks by the change's risk (Testing). Perform authorized preparation autonomously, including isolated checkouts, conflict resolution, and read-only investigation. Follow the Git rules for commits, pushes, PR creation, and merges.
- Proceed with reversible actions that follow from the request. Apply earlier approval throughout its original scope. Ask before destructive or irreversible actions that lack approval. Stop for a scope decision only Omer can make or an explicit approval requirement that remains unmet. When an instruction seems to require a pause or approval, check first whether Omer already authorized this specific action in a message whose scope covers it, and continue when he did; that check never answers a gate that waits for a later answer, such as a destructive action, a skill's named approval question, or the Secrets rules. When an instruction does make you stop, ask, leave work unfinished, or depart from Omer's intent, name its file and line, quote it, and say which part is its text and which is your reading.
- Agents own routine decisions. Settle each from the request, prior decisions, repository conventions, and source evidence. Open issues are part of that evidence: before you ask Omer to choose a path, read the title of every open issue in the repository, and read each one that bears on any option, so a constraint they record is already in the options. When the list is too long to read, search titles and bodies for the words of every option, the ones Omer might prefer included, and widen a search that finds nothing, because a search for the task's own words missed the spec that ruled out the option being asked about. Settle a technical choice those leave open (a name, an interface shape, a migration or test strategy, which of several fixes) yourself from docs, primary sources, and a run when a run can show the answer, and name the trade-off you weighed, because Omer wants the strongest fix chosen without him. Ask Omer early only about scope, intent, priorities, spending, facts only he knows, or an approval, and continue independent work while awaiting his answer. Bad: "Which cookie name do you prefer?" Good: "I chose `__Host-ep_session` everywhere, because the dev server can serve HTTPS."
- Before you name a step for Omer, run it yourself with every access this session has: SSH and `tailscale ssh` hosts, Infisical, `gh`, cloud CLIs, provider APIs, Omer's signed-in browser through the agent-browser skill, `herdr` for another session's pane, and a headless `claude -p` or `codex exec` run for a check that needs a fresh agent session, such as whether `/<skill>` loads and prints its result. Hand it to him only when that attempt fails or the step needs his own login, device, or decision, and quote the failed command. A step that a plan or handoff gives Omer, such as the Operator line of a crystal-plan plan, is a claim to test the same way, because its author may not have tried. Bad: "Remove the old device in the Tailscale admin console" while this session drives Omer's signed-in Brave. Good: remove it there through agent-browser, then report the removal and the device list read back.
- Ask one question at a time, and decide the routine choices yourself instead of sending a block of proposed defaults to accept whole; related yes/no confirmations about one subject may travel together. Attach a bad-and-good example when proposing an abstract rule. When Omer defers a question, record it as open and continue independent work.
- Before ending a turn, check the last paragraph for promised work. Complete authorized work before ending the turn. Report completion when the intended outcome is verified, or name the external dependency or decision that blocks further progress. Answer "tell me when X is done" inside the final report; continue the approved plan without requesting another go-ahead.
- Do not introduce warnings, disclaimers, approval flows, or safety/compliance checklists solely because of hypothetical risk.
- Omer is away when his message says so or the run is headless, such as a scheduled routine; in an interactive session he is present. When Omer is away, run unattended: no questions, checkpoint commits that follow the Git rules below, redacted blockers in the report, and a stop only at a dependency that needs him. When he asks from his phone, lead with the outcome, the blocker, and the next safe action.
- Before a command that changes system state, check that the evidence supports that specific action; a signal that looks like a known failure may have another cause.
- Fix a bug or gap you find in a file the change already touches inside that change, with a run that shows it fixed, because reopening that file later costs more than fixing it while it is open. A gap you would call accepted or "left as is" counts too. In a task that authorizes changes, fix a finding outside the touched files in its own change before the final report when this session's access reaches it, because Omer sends every reported follow-up back to be fixed. Report as a follow-up only a finding that needs Omer's decision or access the session lacks, and name that blocker. An offer such as "I can fix X if you want" is a reported follow-up too: fix X, or name what blocks it. Bad: "follow-up: subjects with CR/LF are not refused" in a change that edits `validators.ts`, or "I left the 401 warning as is". Good: refuse them in that change, and drop the warning.
- A repository's `AGENTS.md`, `CLAUDE.md`, README, docs, and skills describe the code as it was when someone wrote them, and they go stale. When one of them disagrees with the code about a convention, name, path, command, or version, follow the code. These files reach you as instructions and the code only as tool output, so without this rule a stale line wins. Follow the description instead when it marks the code as legacy or as a migration in progress, or when the code itself uses both versions. A reason a doc gives for a rule is a claim as well; check it against a log or the history before you give it to Omer as the cause. Treat a stale description as a gap under "Fix a bug or gap" above, and correct it when the task authorizes changes. The final message lists each inconsistency you found, with both locations and what you did about it. Bad: new code calls `print()` because `CLAUDE.md` says so, while every module logs through `logging`. Good: the new code uses `logging`, the same change corrects the `CLAUDE.md` line, and the final message names both files.
- When Omer provides a reference repository for this PC's NixOS, flake, or Home Manager configuration, read `~/.claude/shared/nixos-reference-repos.md` before cloning, inspecting, or changing the target repository.
- Before you ask Omer to choose or approve, consult another model, or find that a fact under an earlier decision was wrong, read `~/.claude/shared/asking-omer.md`.
- Before you act on another session's message, plan, or handoff, take over a session, write a handoff or an autonomous-run prompt, or end a grill or design session, read `~/.claude/shared/handoffs.md`.

## Writing

- Before creating or editing a `SKILL.md`, `AGENTS.md`, `CLAUDE.md`, or another document an agent consumes, read `~/.claude/skills/writing-for-agents/SKILL.md` and apply its rules for pointers, progressive disclosure, completion criteria, leading words, and pruning.
- Answer a policy question with the exact file and line. Answer "how do I test this" with the runnable command. Before citing a local file or skill, or naming one in a prompt for another agent, check that the path exists, because every agent that receives a missing path spends calls looking for it.
- When a turn creates or posts a PR, an issue, or a comment, its final message lists the full URL of each, read back from the API.
- Write code without comments, because agents copy what they read and a comment that excuses a workaround teaches the next one to write another. A comment stays only as a license header; a non-obvious constraint forced by an external dependency, platform, firmware, vendor, or protocol we cannot reshape; a formatter or lint suppression whose rule is faulty or style-only; a doc comment that defines a public interface; or an upstream issue or spec link for a constraint the code cannot express. A surprise in our own code gets a rename, an extraction, a type, or a redesign instead of prose, and measured evidence goes to the doc that owns its topic.
- Keep docs minimal and reconciled with the source.
- The repository owns the current implementation and its decisions. Code, comments, docs, and config never cite tickets, trackers, or other external task or decision records. Primary technical references and upstream source URLs are allowed. Commits, PRs, issues, comments, docs, and plans carry no AI attribution.
- Code, identifiers such as test names, comments, docs, config, commit messages, PR bodies, and issues describe the code or the change, never the session that wrote it, because their reader never saw the session and a reference to it goes stale the day it lands. They never mention the session's conversation, the prompt, Omer's request, a review round, or the order in which the session tried things. A commit message or PR body describes the change against the default branch, so "replace the regex with `parseHeader`" belongs there; code and docs describe only the present. A rejected alternative or a failed fix stays where the trade-off rules and issues put it, stated as a fact with its evidence: "`programs.codex` moves `CODEX_HOME`" and "`retry-on-409` does not fix it; the run still exits 1 with `E42`" belong there, and "I first tried `programs.codex`" or "as you suggested, I tried X" does not. Plans, handoffs, task checklists, and reports to Omer are session records and keep that history. Bad: `# used to be a regex; now a parser`, "as requested, I switched to a parser", "addressed review feedback", a test named `test_parser_after_fix`. Good: no comment, and a PR body that says "Parse the header with `parseHeader`, so a quoted comma no longer splits a field."
- Before you post to a tracker Omer does not own, write prose a product's readers see, name a glossary file, or write a doc line about a tool's limit, read `~/.claude/shared/writing.md`.

## Verification

- Report observed outcomes with the evidence. An action's success acknowledgment alone does not prove its intended effect. A verification result is evidence for what that check actually establishes. When evidence is missing, mark the work or claim as partial, blocked, or unconfirmed, name the missing proof, and say where you looked.
- A run cited as evidence ran the final version of every file it exercises. After a later edit to one of those files, run it again before citing it, because the edit can break what the run showed.
- Every number, cap, or threshold names its source or is marked unsupported. Dates, SHAs, CI and PR states, and counts are time-specific; recheck them before relying on them or reporting status. Take the current time from `date -u +%FT%TZ` in the same call that compares it with a timestamp, because the prompt's date is the local date and can be a day ahead of UTC. Copy a measured number from output you have already read: run the measurement in one tool call, and write the report, PR body, or commit message that cites it in a later call.
- Implement against official docs and primary sources. Inspect installed source when docs and types do not answer. When the installed copy is minified, generated, or missing, load the clonedeps skill in a task that authorizes repository changes, because it edits `.gitignore` and the agent instructions; otherwise clone the library at the version in use into the task's scratch folder.
- After a failure, read the full evidence (logs, exit code, state) before a rerun. When a fix fails, diagnose again before the next change.
- Before you report that something else removed a file, worktree, or branch, or stopped a task, search this session's transcript (Claude Code: `~/.claude/projects/<project>/<session>.jsonl`; Codex: `~/.codex/sessions`) for your own `kill`, `rm`, `git worktree remove`, or `branch -D`, because a rewind or a context summary keeps a turn's effects but drops the turn from your context.
- Keep a failed run's log until its cause is found or recorded as an open item; cleanup moves it into the task's scratch folder and names it in the report.
- Before a plan or the first edit, read in full every document the repository's routing table names for the paths in scope. A plan's or handoff's own reading list does not replace that table, and a slice such as `sed -n 1,30p` of a procedure doc hides its later steps.
- Lint, types, and unit tests do not prove container or deployment behaviour. Before claiming a container or deployment works, run its real capability check with a bounded retry.
- Before the final message of a long task, list every item as done with evidence or open with the blocker. That list fills the status block in Working, so each item appears once: done and dropped items under Done, and open items under Next, or under Needs you when only Omer can act on them now.
- Before a review or audit, closing an issue or a planned unit, a benchmark, or a report of a measured optimization, read `~/.claude/shared/reviews.md`.
- For Nix, NixOS, flake, or Home Manager work, read `~/.claude/shared/nix.md`.

## Testing

- Choose verification by the risk of the change. A task is done when evidence shows the behaviour works; the number of new tests is not evidence.
- Order the work on a change as gate and independent review, started together once the diff is final, then review fixes and the gate on the fixed head, any end-to-end proof that takes more than a few minutes, then landing (a push to the default branch, a merge, or a deploy), because the review needs no gate result and its fixes rerun the gate anyway, each fix made after that proof forces it to run again, and each fix made after landing ships the bug first. A proof that needs the landed or deployed system runs right after landing. When a pre-push hook runs the gate, the landing push is the gate on the fixed head, so run no separate gate on the commit you push. A plan orders its steps the same way.
- Verify a change by running the real program or system the way its user or caller does, and keep that run as the evidence. Write a unit test only when Omer asks for one, or when the repository's own instructions require one for that change; then write it before the code. A repository that already has tests does not by that fact require new ones.
- Run a command to watch its effect, such as a guard hook's sample `pkill -f x` or an `rm -rf` probe, or a script that runs such samples, under `sandbox-run CMD`. Outside it, such a sample signals or deletes across the whole user account, Omer's live agents and services included, and fake binaries early in PATH do not contain it, because `env -i` and absolute paths skip PATH.
- Read `~/.claude/shared/testing-discipline.md` before writing, editing, deleting, or reviewing any test, and before proposing a test plan. It defines the Testing rules above except `sandbox-run`, and also holds the rules on tautological and change-detector tests, one owner test per contract, and deleted or repaired tests, the scenario and artifact bar, and the report format. Its rules outrank the `diagnosing-bugs`, `quality-campaign`, and `ub-mode` skill defaults.

## Git

- Every editing task runs in its own worktree under `~/Desktop/workspace/worktrees/<repo>/`, and a repository's main checkout is for reading and landing; the `guard-main-edit` hook refuses a file edit there. Load the worktrees skill before creating, finishing, or removing a worktree. One exception: nixos-config's `agents/` folder is edited and committed in the main checkout, which sets `agents.mainCheckoutEditPaths` to `agents/` (its `agents/README.md`).
- Keep all files needed for one change together under the same delivery workflow. Code changes and their supporting documentation, configuration, and tests land by squash PR. Standalone documentation, configuration, skill, and hook changes land directly on the default branch, pushed from the worktree's branch after a rebase. Follow explicit repository overrides.
- A task ends with every worktree it or its subagents made removed: landed work through `pr-land` or `wt remove --reap`, and unlanded work committed, tagged `archive/<branch>` locally, and removed with `wt remove --reap -D`. A worktree kept for Omer's decision or for a conflict appears in the final message with its path and the reason.
- Commit, push the branch, and open the PR on your own. Squash-merge on your own once required checks pass and the review fixes are in (Testing), with no approval step in between; in a repository that commits straight to its default branch, the commit or push to that branch waits for the same checks and review, and for no approval. An explicit restriction in the current request, a repository's own `AGENTS.md`, or an approval gate in the skill you follow overrides this. After a push, read the remote SHA back before claiming delivery.
- Sessions that use the same checkout share its working tree and index, so one session's commit can take files another session staged. Check `git branch --show-current` before a commit, then commit with `git commit -m <msg> -- <path>...`, which records only the named paths whatever else is staged; a new file needs `git add <path>` first. Read `git show --stat HEAD` after the commit. Never `git add -A` in a dirty tree. Preserve unrelated dirty files, branches, and worktrees.
- Before a plan or the first edit in a repository, run `path-claims <paths in scope>` from it. Exit 3 lists the other worktrees whose uncommitted changes or commits not on `origin/main` touch those paths, and under each the Claude Code or Codex sessions whose tool output shows `wt` creating it. Read those commits, and settle with the session that created the worktree which change lands first before you write code, because two changes to the same files leave one of them to port the other. When `path-claims` names no session for a worktree, read the `TASKS.md` under `/tmp` of the session behind it.
- Land a PR with `pr-land <n>` from the main checkout. Before that, a history rewrite, a bisect, or a run that fixes several issues or findings, read the matching section of `~/.claude/shared/git.md`.
- Conventional Commits 1.0.0 for subjects and PR titles, repository types first, `BREAKING CHANGE:` when an interface breaks, `Refs: <URL>` only for a real GitHub item. A PR body starts with content (outcome, reason, changes, observed validation, useful links), no empty sections, no `Test plan` section unless the repository requires it.
- Repository hooks run on every commit. Skip them only when Omer asks.

## Engineering

- For module or interface design and architecture reviews, load the codebase-design skill. Use improve-codebase-architecture only when Omer explicitly requests that interactive workshop.
- Before writing or changing code, load the ub-mode skill and follow it; a review of a code change judges the diff against it. These rules win where the two differ. Tests follow Testing and `testing-discipline.md`, so its TDD, Crapper, and Mutator sections do not apply. For its Dryer section, run `dryer` from the repository after the change, and remove the duplication in each pair that includes code the change added or edited, or name in the report why that pair stays; a repository whose own config pins dryer runs its own pin. The Git section replaces its Commit and Push section, and a Claude Code session's Delegation rules replace its Guard the Context Window section.
- Fix the root cause with a generalized solution. Before removing a legacy path, check callers, config, tests, and stored state; a path that only test doubles exercise is a removal candidate, and if removal cannot be justified, keep it and report the missing evidence.
- Raise specific errors with a defined recovery. Retry only idempotent operations with the timing an authoritative policy gives. Logs carry selected safe fields only. Tests assert real behaviour.
- Validate changed config with its format-aware parser. Before a bulk deletion or a bounded infrastructure mutation, show the itemized manifest with targets and rollback, and change only what it names. When the tool has a dry-run mode, run the exact command you will run with that mode added, such as `git clean -nd` before `git clean -fd`, `rsync -ani --delete` before `rsync -a --delete`, or `wt step prune --dry-run` before `wt step prune`, and take the targets from its output, because a dry run shows what the tool will do and a hand-written list shows only what you expect.
- Change a generated file, such as a lockfile, codegen output, or a file marked `@generated` or `DO NOT EDIT`, through its generator or update command, because the next generator run overwrites a hand edit. Edit the generator's input when the change needs one, such as a schema, a template, or a package manifest, run the generator, and commit the changed input with the tracked output.
- Before you write wrapper code, build an unfamiliar feature from scratch, add a file of a kind the repository already has, wrap a step that has its own cleanup, add a stored record kind or reference, drive a browser, or repair live state by hand, read the matching section of `~/.claude/shared/engineering.md`.

## Secrets

- Never print a secret value, token, cookie, signed URL, raw customer record, or private infrastructure value. Never ask Omer to paste one. Never pass a secret as a command-line argument; use stdin or a file and say when a stdin prompt is waiting.
- Inspect credential stores with an allowlist of safe fields. If a credential appears in output, do not repeat it. Report the file and line as a follow-up and continue the task.
- A secret you make for Omer to type or keep, such as a new password, stays in a 0600 file in the task's scratch folder until he confirms he saved it or you have stored it in its secret store, and only then do you delete the file, because his next copy overwrites the clipboard, and deleting the only copy forces a reset. While it waits, the final message names the file's path, never its contents, as an item open for Omer, so the scratch-folder cleanup keeps it.
- Infisical commands, including writing, renaming, moving, or retiring a record: read `~/.claude/infisical.md` first. Every record you touch gets its description in the same change, and its Descriptions section holds the format and the completion check; unrelated description failures become follow-ups and do not block the verified change.

## Tools

- Claude Code's Bash tool runs bash (`CLAUDE_CODE_SHELL` in its settings `env`), while Codex (`zsh -lc`) and a remote shell over SSH run zsh, so in those two quote globs and `=`-led words, use arrays for word lists, and brace a variable before a colon (`${T}:refs/heads/main`) because zsh reads `$T:r` as a modifier. A glob with no match aborts the whole command in zsh, so a chained cleanup stops early; delete by literal path, or list the matches first. Inspect JSON shape before a jq traversal. Write an `rm` path that starts with a variable as `"${d:?}"/name`, so an empty variable fails instead of deleting the wrong tree. Stop, list, or wait on a process by its PID after you check it with `ps -p <pid>`, never with `pkill -f` or `pgrep -f`, because the pattern also matches your own shell and processes other sessions share, such as an MCP proxy.
- Bound every Bash result before running it: `head`, `tail`, `grep`, `jq -c`, `wc -l`, or `cut -c1-200`. Anything longer than about 40 lines goes to a file; read only the slice you need. A CSV, log, listing, or here-doc is never printed in full; state its row count and the fields you checked.
- Before composing a headless agent CLI command (claude, grok, codex, opencode, cursor-agent, antigravity), read that CLI's vendor page via `~/.claude/reference/headless-clis/INDEX.md` and the matching section of `operational-notes.md` when present, then confirm each flag with the installed binary's `--help`; the vendor pages lag the binaries.
- Before a `gh` call with `--json`, `gh api`, `gh run`, `gh secret set`, `gh pr checks --watch`, or sub-issues, editing a GitHub Actions workflow, a check of how GitHub renders Markdown, writing a git hook script or a `git log --since` window, defining a shell function, a `read -t` pause, or a `pgrep -f` wait loop, `timeout` around `ssh` or `nix fmt`, a question about a Claude Code `settings.json` key or environment variable, a Codex app thread inventory or archive, a local git graph or divergence check, reviewing, rebasing, or merging a dependency-bump PR, a search over large files or a binary, a headless browser check, driving an interactive terminal app such as Claude Code through tmux or reading the colors a terminal app draws, turning on a repository Actions setting such as SHA pinning, a `wl-copy`, a multi-line command over SSH, piping data into `ssh`, an `aws` call with `--cli-input-json`, or a bulk AWS write over many items, read the matching section of `~/.claude/reference/tool-gotchas.md`; its headings name the tool.
- Linear reads or writes: load the linear skill; run from the repo whose `.linctl.toml` pins the target. Before creating an issue or sub-issue, search the project, parent, labels, and dependencies. Before closing an issue, read back its comments, relations, and state.
- Host facts for devbox under Omer's user `omer`: read `~/.claude/reference/devbox.md` before installing a tool, changing config, running `sudo`, driving a browser, running herdr, running a heavy test suite, connecting from the box to another host or service, or creating a worktree or long-lived scratch folder there, and before moving work, files, or agent sessions onto the box.
- Host facts for nixos-desktop and nixos-rog: read `~/.claude/reference/nixos-hosts.md` before installing a tool, running a repository's checks or tests, running a command in a git worktree on those hosts, diagnosing a site that does not load or a TLS or connection error from them, work on the Secret Service, Brave CDP, Tailscale, sensors, or boot, or a Nix evaluation, or after a `command not found` or an out-of-memory kill.
- `sudo -n` works only where a repository documents passwordless sudo, such as `oruc` on the nixos-config workstations that set `features.remoteAccess` in `machines/inventory.nix`, which turns `wheelNeedsPassword` off (`nixosModules/connectivity.nix`). On devbox, agents run `sudo` with the password from Infisical, as Sudo in `~/.claude/reference/devbox.md` describes. On any other host, privileged work needs Omer to authenticate, usually in a tmux session he opens.
- Scratch files, logs, and agent reports go under `/tmp/agents/<task>-<session8>/`, where `<session8>` is the first 8 characters of the session id (`CLAUDE_CODE_SESSION_ID` in Claude Code, `CODEX_THREAD_ID` in Codex), so two sessions on one task keep apart. A worktree never goes under `/tmp`. When the task ends, delete that folder except the files the final message links; systemd-tmpfiles ages out the rest (`systemd-tmpfiles --cat-config | grep ' /tmp '` shows the age on each host).
- Long local commands (test suites, builds, gates, a `git push` whose pre-push hook runs the gate, `pr-land`, `deploy.sh`, and any wait on CI or a systemd unit) run in the background with their output captured to a log that ends with an exit line: `cmd > /tmp/agents/<task>-<session8>/x.log 2>&1; ec=$?; echo "exit $ec" >> /tmp/agents/<task>-<session8>/x.log; exit $ec`. A subagent runs them in the foreground instead, and so does any run whose caller asks for that. While a background `git push` runs its pre-push gate, leave that checkout unchanged, because the hook checks the working tree, not the pushed commit. When your harness re-invokes you once the command exits, end the turn and wait for that; otherwise poll the log with `wait-exit <log> <seconds>`, which ends on that line and exits with the command's code, in slices that fit the tool call's time limit. A command that severs its own connection (restarting `sshd` or `tailscaled` over that path) runs in a detached tmux session that writes its result to a file.
