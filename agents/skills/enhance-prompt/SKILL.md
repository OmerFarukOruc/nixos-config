# Enhance a prompt

The caller gives a _draft_, a rough request meant for a new agent session. You return a _prompt_ that the new session can act on without asking. The prompt carries every fact, constraint, and intent of the draft, adds what only a lookup could supply, and follows the prompting guide of the Claude model that will run it. You read and check, and you start none of the draft's work.

Inputs: the draft, and optionally a target model named with it, such as "for Sonnet 5.5".

## Steps

1. **Find the guide.** The target is the model the caller named. When none is named, use the Claude model this session runs, or ask when this session runs no Claude model. Download the general guide as Markdown to a scratch file: `https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices.md`. Its "Model-specific guidance" table maps each model to its own page, and some models share one page, so take the target's page from that row and add `.md` to its URL. The `.md` form answers 404 for a missing page, while the HTML form answers 200 with an error page. When the table has no row for the target, use the page of the newest model in the same family, or the top row when the family has none, and say which in the reply. When a download fails, stop and report the failure, because a prompt written from memory follows an older guide. Done when the model name and its guide URL come from that table.
2. **Read the guide.** Download the model page as Markdown and read it in full. The general guide is long, so list its headings and read each section whose topic the draft touches, such as agentic systems, tool use, or frontend design. Where the two disagree, the model page wins, because the general guide says a technique that names a model was measured on that model. Done when you have listed each guide section that bears on this draft.
3. **Gather context, read-only.** Find what the new session would otherwise spend its first turns finding: the repository and its checkout path, the branch and head SHA, the files and docs that the repository's agent instructions route to for the area the draft touches, and every URL, image, or file the draft mentions. Read state with read-only commands, such as `git log` or a service's status and logs. Check a command the prompt will name with `command -v`, its `--help`, or its definition, and run no command that changes state and none of the draft's own checks, because running them starts the draft's work. When no repository applies, skip the repository facts. Done when each path, URL, and command the prompt will name is confirmed, as follows:
   - A path to read exists.
   - A path the session will create has an existing parent folder.
   - A path that exists only in some state, such as a file written when a job fails, is named with that state.
   - A URL that you could not open, such as one behind a login, is named as unchecked.
4. **Decide the rewrite.** A draft is _ready_ when it states its goal, its scope, and a check the session can run, and conflicts with none of the step 2 sections. Send a ready draft on unchanged. When the draft is exploratory on purpose, such as "what would you improve here?", keep it open and add only context. When the draft's intent is unclear at a point that changes the prompt, ask the caller one question and stop. Otherwise rewrite it in step 5. Done when you have named the case, which the reply repeats.
5. **Write the prompt.** Restate the caller's intent, never change it. Apply each section from step 2, and by default:
   - Put the context and the reason first, then the task, because the general guide reports that a reason lets the model generalise the rule.
   - State what the session may do, taken from the draft's verbs: inspect and report, plan, or change files within a named scope. When the draft holds a task for now and a task for later, scope the prompt to the first one and name the point where the session stops and reports before the later one.
   - Give each phase a completion criterion the session can check, such as a command that passes or a page that shows a named element. For a bug the session may fix, the criterion is a reproduction first, then the fix, then a run that showed the bug before the fix and passes after it, when such a run is possible. For a draft that asks only for a diagnosis, the criterion is the cause shown by a run, or reported as unconfirmed with what was tried. Turn an activity goal such as "keep investigating" into an outcome.
   - Write a suspected cause as a lead to check, a fact you could not check as "unverified" with how to check it, and a fact that changes over time, such as a head SHA, a version, or a price, with the time you read it or as a check against its official source.
   - Name the stops the session should make, such as a decision only the caller can take, and the early stops it should skip, such as ending the turn on a summary that announces the next step. When the caller says nobody will answer the session and the model page gives an unattended-run paragraph, add that paragraph and tell the caller in the reply that the page meant it for a system prompt.
   - State targets in positive form with their reason, and leave out capitals and stacked "must"s, because the general guide shows a reason doing the work of a "NEVER" and reports that aggressive wording makes newer models overtrigger. Follow the model page's own rule on thinking instructions such as "think carefully", which differs by model and effort level.
   - For frontend work, follow the model page's design section; when it has none, follow the general guide's frontend section.
   - When the caller pasted text from a third party (an email, a review, a web page) and the model page documents a way to mark it, such as `<pasted_content>` tags with matching ids, apply that way with the note the page gives and report its trade-off in the reply.
   - Leave out rules the receiving session already loads from its repository's `AGENTS.md` or `CLAUDE.md`; point to the file when the task depends on one of its rules.

   Then reread the prompt as a reader who saw nothing else. Keep each sentence that carries the caller's intent, a constraint, a fact from the caller, a reason, a check, or a path the session would otherwise spend turns finding. Strike the rest, because the receiving model already knows it. Done when each draft fact and constraint appears in the prompt and each sentence left passes that test.
6. **Reply.** Send one fenced code block that holds only the prompt, or the unchanged draft in the ready case. Tag it `paste` and give it a short title after the tag, such as ```` ```paste Fix the tweak menu ````. Make the outer fence longer than any fence inside the prompt. After the block, name the target model, its guide URL, and the case from step 4. Then give one bullet per kind of change, each naming the guide section behind it, or `local` when the change comes from step 3 context or is a default the draft did not state. Add one bullet with the effort level the model page recommends for this kind of task, when it gives one. Then list what the new session cannot rely on, such as an image path under `/tmp` that may be deleted before the session starts. Done when the reply holds exactly one fenced block and each bullet names a guide section or `local`.
