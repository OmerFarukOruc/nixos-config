# Enhance a prompt

The caller gives a _draft_, a rough request meant for a new agent session. You return a _prompt_ that the new session can act on without asking. The prompt carries the facts, constraints, and intent of the draft, adds what only a lookup could supply, and follows the prompting guide of the Claude model that will run it. You read and check, and the only thing you write is the prompt, at its destination.

Inputs:

- The draft. It is a _file draft_ when the whole draft is one file path, or the caller says the file holds the draft. A draft that only mentions a file, such as "fix the bug described in /tmp/bug.md", is a text draft.
- Optionally, a target model, such as "for Sonnet 5.5".
- Optionally, a destination file path.

## Steps

1. **Find the guide.** The target is the model the caller named. When none is named, use the Claude model this session runs, or ask when this session runs no Claude model. Download the general guide as Markdown to a scratch file: `https://platform.claude.com/docs/en/build-with-claude/prompt-engineering/claude-prompting-best-practices.md`. Its "Model-specific guidance" table maps each model to its own page, and some models share one page, so take the target's page from that row and add `.md` to its URL. The `.md` form answers 404 for a missing page, while the HTML form answers 200 with an error page. When the table has no row for the target, use the page of the newest model in the same family, or the top row when the family has none, and say which in the reply. When a download fails, stop and report the failure, because a prompt written from memory follows an older guide. Done when the model name and its guide URL come from that table.
2. **Read the guide.** Download the model page as Markdown and read it in full. The general guide and the model page are the only guide sources, so read no other copy. The general guide is long, so list its headings and read each section whose topic the draft touches, such as agentic systems, tool use, or frontend design. Where the two disagree, the model page wins, because the general guide says a technique that names a model was measured on that model. Done when you have listed each guide section that bears on this draft.
3. **Gather context, read-only.** Find what the new session would otherwise spend its first turns finding: the repository and its checkout path, the branch and head SHA, the files and docs that the repository's agent instructions route to for the area the draft touches, and every URL, image, or file the draft mentions. When the draft continues an earlier session, find that session's transcript or handoff file and name its path, or name it as unavailable. Read state with read-only commands, such as `git log` or a service's status and logs. Check a command the prompt will name with `command -v`, its `--help`, or its definition, and run no command that changes state and none of the draft's own checks, because running them starts the draft's work. When no repository applies, skip the repository facts. Done when each path, URL, and command the prompt will name is confirmed, as follows:
   - A path to read exists.
   - A path the session will create has an existing parent folder.
   - A path that exists only in some state, such as a file written when a job fails, is named with that state.
   - A URL that you could not open, such as one behind a login, is named as unchecked.
   - A command or skill that is missing is named as missing.
4. **Pick the case.** Test the cases in this order, and take the first that fits:
   - _Portable_: the caller says the prompt must work in any repository or with any model. Keep the intent of each sentence and check each claim against the step 2 sections, and against the repository when one applies. Replace incidental repository facts, host paths, and model names with a rule to read the repository's own instructions, and turn each detail the draft depends on into a placeholder, with the draft's value as its default, in one block the session fills first. Skip the repository facts from step 3.
   - _Ready_: the draft states its goal, its scope, and a check the session can run. It conflicts with none of the step 2 sections, each path, URL, and command in it passed step 3, and none of the step 5 bullets on scope, secrets, results, and stops would change it. It goes on unchanged.
   - _Open_: the draft is exploratory on purpose, such as "what would you improve here?". Keep it open and add only context.
   - _Standard_: any other draft. Write it in step 5.

   When the draft's intent is unclear at a point that changes the prompt, ask the caller one question and wait for the answer. Done when you have named the case, which the reply repeats.
5. **Write the prompt.** Restate the caller's intent, never change it. Apply each section from step 2, and by default:
   - Put the context and the reason first, then the task, because the general guide reports that a reason lets the model generalise the rule.
   - State what the session may do, taken from the draft's verbs: inspect and report, plan, or change files within a named scope. Carry scope words such as "information only" or "audit only" as limits, with the reason the draft gives, and offer a wider scope in the reply instead of adding it. For "independent discovery", leave the caller's own hypotheses and earlier conclusions out of the prompt, because they would steer the session. When the draft holds a task for now and a task for later, scope the prompt to the first one and name the point where the session reports and waits for the caller before the later one.
   - When the caller hears about or decides on items one at a time, as in "explain each of it to me", "walk me through each", or "one by one", tell the session to present a single item, never a group or an area, then end the turn and wait for the caller's answer, because such a caller answers item by item.
   - Give each phase a completion criterion the session can check, such as a command that passes or a page that shows a named element. For a bug the session may fix, the criterion is a reproduction first, then the fix, then a run that showed the bug before the fix and passes after it, when such a run is possible. For a draft that asks only for a diagnosis, the criterion is the cause shown by a run, or reported as unconfirmed with what was tried. Turn an activity goal such as "keep investigating" into an outcome.
   - Pair a threshold on a score that varies between runs with a cap on rounds or time, because the threshold alone can loop. Take the cap from the draft, or choose it and name it in the reply, and tell the session to report the last score and the unmet threshold when it reaches the cap.
   - When a check can be blocked, such as a browser tool the system under test refuses, tell the session to name the error, mark that check as not run, go on with each phase that does not depend on it, and report the missing proof.
   - Write a suspected cause as a lead to check, a fact you could not check as "unverified" with how to check it, and a fact that changes over time, such as a head SHA, a version, or a price, with the time you read it or as a check against its official source.
   - Copy each tool, skill, command, and model the draft names into the prompt in the draft's words, and say which phase uses it. When the draft leaves a role open, such as which model implements or reviews, say in the reply that the prompt leaves it to the session's defaults.
   - Say where the session puts its result: the place the draft names, or its final reply when the draft names none. When the new session will start in plan mode, say that it writes a named file only after the caller approves its plan.
   - Name the points where the session waits for the caller, such as a decision only the caller can take. When the draft includes a step that publishes, deletes, or moves live data, such as a deploy, a data migration, or a repository move, and does not say the session may do it, tell the session to prepare that step in full and wait for the caller's go. Name the early stops the session should skip, such as ending the turn on a summary that announces the next step.
   - When the caller says nobody will answer the session, tell it to prepare each step that would wait for the caller, report it, and end instead of waiting. Add the model page's unattended-run paragraph when it gives one, and tell the caller in the reply that the page meant it for a system prompt.
   - State targets in positive form with their reason, and leave out capitals and stacked "must"s, because the general guide shows a reason doing the work of a "NEVER" and reports that aggressive wording makes newer models overtrigger. Follow the model page's own rule on thinking instructions such as "think carefully", which differs by model and effort level.
   - For frontend work, follow the model page's design section; when it has none, follow the general guide's frontend section.
   - When the caller pasted text from a third party (an email, a review, a web page) and the model page documents a way to mark it, such as `<pasted_content>` tags with matching ids, apply that way with the note the page gives and report its trade-off in the reply.
   - Name where the session reads a secret or an account id, and leave its value out of the prompt.
   - Leave out rules the receiving session already loads from its repository's `AGENTS.md` or `CLAUDE.md`; point to the file when the task depends on one of its rules.

   Then reread the prompt as a reader who saw nothing else. Keep each sentence that carries the caller's intent, a constraint, a fact from the caller, a reason, a check, or a path the session would otherwise spend turns finding. Strike the rest, because the receiving model already knows it. Done when each draft fact and constraint appears in the prompt or is listed for the reply as left out or replaced with its reason, and each sentence left passes that test.
6. **Deliver.** Take the first destination that applies:
   - This session is in plan mode. The plan file holds only the prompt. Approving the plan with the option that clears the context sends the file to a fresh session as its first message, while any other approval option starts the work in this session. So the reply, given before you submit the plan, tells the caller to pick the clear-context option or to copy the prompt from the plan file.
   - The caller named a destination file. Write the prompt there. When the file exists, copy it first to `<name>.orig` beside it, unless git tracks it with no uncommitted change, because git then holds the old version.
   - A file draft. Write the prompt into that file, with the same backup rule.
   - Otherwise, the chat reply holds the prompt in one fenced code block tagged `paste` with a short title after the tag, such as ```` ```paste Fix the tweak menu ````. Make the outer fence longer than any fence inside the prompt.

   Done when the prompt is at its destination and any backup exists.
7. **Reply.** Name the destination, which is "chat" for the last case, and the path and size in bytes of any file written and of its backup. Name the target model, its guide URL, and the case from step 4. Give one bullet per kind of change, each naming the guide section behind it, or `local` when the change comes from step 3 context or is a default the draft did not state. List each draft fact left out or replaced, with the reason. Add one bullet with the effort level the model page recommends for this kind of task, when it gives one. Then list what the new session cannot rely on, such as an image or file under `/tmp` that may be deleted before the session starts. Done when the reply holds at most one fenced block and each change bullet names a guide section or `local`.
