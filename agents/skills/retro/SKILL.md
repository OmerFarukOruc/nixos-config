---
name: retro
description: "Runs a retrospective on a coding session or a stretch of agent work, then applies the environment changes the user picks. Use when asked for a retro, or after a wave or phase of a multi-agent campaign ends."
---

You are running a **retrospective**. You find what in the coding agent's **environment** (its steering files, checks, hooks, scripts, docs, and access) made the session slower or wrong, and change it so the next run goes better. A finding is friction or an **escape** (a bug that a review, gate, or test passed and a later stage caught, or that shipped) that an environment change would prevent next time; a one-off task slip that no change would prevent is task noise.

Keep every change inside your scratch directory `/tmp/agents/retro-<session8>/` (the first 8 characters of the reviewed session's id, the first one when there are several; `session-digest --out` creates it and prints its path) until the user answers step 4 or the request already named the fix: no edits, deletions, branch or Git changes, and no messages to other sessions. Reads, probes that change nothing, and `git fetch` are fine. Until step 4, a reply to the user names what you ran and what is still running, and no candidate, count, cause, or recommendation, because the user acts on what you send before step 3 has checked it; a question about the user's intent or scope is fine.

## Steps

1. Read the session as **evidence**. Your memory of the session is a lead to check against the transcript.
   - The caller names the session; default to the current one. Resolve a name or a scope such as "this wave" to session ids yourself: the transcript's `agent-name` and `ai-title` entries hold its names, or ask. Take an id from the user or from the digest's own header; a path in tool output can belong to an earlier session after a resume.
   - Before the first digest run, list the scratch directory; when it holds an earlier retro's files, move them into an `earlier/` folder inside it, because this run writes the same file names.
   - Run `<this skill's directory>/scripts/session-digest --out` by its path for the current session, or add the session id (or `agent-<id>` for a subagent) for another; pass ids, not paths. Call it by its path in each command, because a command name kept in a shell string runs as one file name in zsh and splits at blanks in bash. For the current session it stops where this retro started. It counts tool calls by tool and lists, with line numbers, the steering files the session received, compactions, user messages, messages from other sessions and background tasks, errors and hook blocks grouped by their failing line (including failure text in commands that exited 0), repeated calls, and the subagents with whether each reported.
   - Read with `--show <line>` or `--show A-B`, which print whole entries, each hit you will cite or cannot classify from its digest line, and each user message whose digest line ends in `...`. Add `--all` when a section list is cut and `--cap N` when a `--show` entry is cut. Search with `--grep <regex>`, which ends with the count of matching entries, and across sessions with `--find <regex>`; `--timeline` lists every tool call and `--commands` every Bash command. Use these instead of your own transcript parser or a `grep -c` on a `.jsonl`, which also counts the api-request entries that repeat each call. Keep a jq read of a transcript in a Bash call that runs no script, because the `bash-guard.py` hook denies a call that runs a script and names a file holding kill commands, which a transcript often does. Test-runner failures piped through `tail` exit 0, so also search for them, for example `--grep 'FAILED \(|FAIL: |✖ |\b[1-9][0-9]* failed'`.
   - Search for escapes, because a stage that passes a bug raises no error, so the digest lists at most the later catch and never the stage that passed it. Run two searches with `--agents`, which also searches each subagent transcript the digest lists, retro refuters excepted: `--grep '(?i)partial review|not (read )?in full|targeted greps|did not (read|run)' --agents` for an agent saying it covered only part of its scope, and `--grep '(?i)blocker|regression|should have caught|missed by' --agents` for a later review, gate, test, deploy, or user message that found a bug. Skip hits in steering text and verdicts that found nothing. For each hit that reports partial coverage or a bug found, find the earlier stage that passed the same code and what that stage checked.
   - For each subagent that never reported, read its last entries with `--show`, and the whole transcript only when it bears on a candidate. Read the earlier transcript a plan or handoff names. Subagents the digest labels as retro refuters belong to an earlier retro; read them only as leads.
   - Read the environment the session ran in: the repo's own check command (its hook config, its `package.json` or build-tool `lint` and `check` scripts, its CI workflow), and the steering files. Compare the steering files the session received with the ones the repo and the user's scope hold, and run `readlink -f` and `git log -1` on each one you cite; a file that never loaded explains every rule the session missed from it.
   - When no transcript exists (another harness, expired, never written) or the digest exits 3 (a format it cannot read), say so, read what exists with `jq`, and mark each finding that rests on memory as unconfirmed.
   - Create `dispositions.md` in the scratch directory right after the first digest run, and add each line as you classify it, so a compaction loses nothing.
   - List friction in this retro's own run under "Skill notes" in step 4, from one run of `session-digest --since-retro` before you write the report; it is not a finding about the session.
   Done when `/tmp/agents/retro-<session8>/dispositions.md` has one line for each user redirect or complaint, one for each escape, one for each error group or repeated call that occurred 2 or more times or touches a candidate, and one per kind for the single-occurrence rest with their line numbers; each line names its candidate or why it is task noise.

2. Find candidates in the categories under Reference. For each, write what happened (with its count and `<session id>:L<line>`), the cause, and the change that prevents it.
   - Before you draft a fix for a document an agent reads, load the `writing-for-agents` skill when it is installed (the Skill tool, or its `SKILL.md`) and follow it, so the text the user approves in step 4 is the text you apply.
   - When a rule in a steering file already covered the case, check that the rule existed on the session's date (`git log` on the file), then find out why it failed (buried, ambiguous, or ignored) and fix that rule instead of adding a sibling. When the fix would enforce an existing rule, also offer deleting or narrowing that rule, and quote the user message, if any, that favours one of them. A candidate an earlier retro dropped is a lead, not a verdict.
   - A rule, guard, or check that existed before the event did not stop it, so it is the finding, not coverage; the disposition names the command that shows why it did not act (for a shell guard, test the option in the agent's own shell). A rule counts as loaded only when the digest's steering list shows its file.
   - A later change counts as coverage only when it is dated after the event, you quote the line of it that would have stopped this event, and you opened each source of the behaviour (the steering file, the template or skill that wrote the plan or handoff, the doc a command was copied from).
   Done when each candidate's fix is drafted as the exact text or diff it adds, written after you loaded `writing-for-agents`.

3. **Verify** each candidate, then have it refuted.
   - Check the fix text: open the file it changes and every file that fills or repeats the same rule (its template, checklist, reviewer rubric, the doc that explains a hook); grep for each term the text uses and for existing code or scripts the new rule would forbid; take each case it lists (exit codes, flags, states) from the code, with their count; and keep only numbers its reader can see in the output of the command it names.
   - Run the cheapest check that could disprove the candidate: grep the steering files for the topic; read the whole record a claim rests on; search the transcript for the session's own actions (`branch -D`, `rm`, a reset) before you call a cause unknown; read the commit behind a recorded decision before you propose reversing it; probe runtime behaviour live (one request, one headless run, each under a timeout sized to the command and stated) instead of reasoning about it, replay a failure that depends on load under the same concurrent load, and print every result when reruns of the same code differ; check open PRs and other running sessions for the same fix.
   - Open evidence yourself; a summary, a subagent's claim, or a check of a nearby case does not clear or confirm a candidate.
   - Take every number from a command run in this retro, or mark it as an estimate.
   - Build each new or changed hook, script, gate step, or lint rule you propose as a prototype in the scratch directory, and report three results a run produced: `caught N of M` on the session's M failing commands (`session-digest <id> --replay <hook> --lines <their line numbers>` for a hook on Bash calls); `fired on K of T` on a wider set (`--replay <hook> --days 30` for a hook, the repo tree and its last 30 days of commits for a gate step or lint rule), with each hit judged in the scratch directory and quoted redacted; and the slowest input's run time against the time limit. With no failing command, write `0 of 0` with the sessions and lines where the failure recurs, the size in lines, and the upkeep. Write a number no run produced as `not run`.
   - Drop a candidate whose check fails. Drop one that occurred once, cost no user correction, and that the session recovered from at once, unless another session shows it recurring; it goes on the No change line. Keep an escape that occurred once, because its cost is the bug the earlier stage passed, not the time the session lost. Mark one whose check needs access you lack as unconfirmed, and quote the failed attempt. When a check shows that the session stated something wrong, add the correction to the report.
   - Then start one new subagent with the prompt in [`references/refuter.md`](references/refuter.md), even when the session folder already holds refuters from an earlier retro. Continue only once its answer arrives; when it arrives as a notification, end your turn with one line saying the refuter is running. In plan mode that holds too: call neither AskUserQuestion nor ExitPlanMode before its answer, and keep the dispositions as a table in the plan file while plan mode blocks scratch writes. When you cannot start a subagent, say the findings were checked by you alone.
   - Save its answer as `refuter-answer.md` in the scratch directory. Drop or rewrite each candidate it refutes with evidence. For each line of the answer that is not a plain `confirmed` (an `unclear` or `refuted` verdict, a caveat, a refuted dropped reason, a missed friction or escape, a fact it adds), run this step's check yourself and add a line to dispositions.md: `rechecked: <command>, showed <result>`, or `not rechecked`. Correct each number and reason the answer changed; a fix it shows would not have prevented the event is rewritten or dropped. A finding you add that the refuter did not name goes back to it with SendMessage, or the report says you alone checked it.
   Done when each finding carries the command or transcript line that confirms its cause, or is marked unconfirmed with the failed attempt quoted, and each line of the refuter's answer that is not a plain `confirmed` has its line in dispositions.md.

4. Present the findings.
   - Open with the count and the finding whose fix would most have changed the session's outcome; rank the rest by that, then by how often the failure will recur.
   - Write each finding as a short paragraph in this order: what happened, with its evidence (`<session id>:L<line>`) and its observed cost (user corrections, failed calls, minutes, each from a command or marked as an estimate); the cause and the command that confirmed it; the fix as the exact text or diff it adds, with its target file (for a script or hook, its input, its output or deny message, and its size in lines; for a text longer than about 15 lines, a guess at what still reads in one screen, its changed sentences and its size); and the failure it prevents. Print each refuter caveat and each `(refuter, not rechecked)` fact beside its finding. Write that the refuter confirmed a finding only when its line is a plain `confirmed`, give the number of findings it received, and leave its model out. Define each project term and each name the user has not used the first time it appears. A finding that needs a decision gives a recommended option.
   - Close with these lines in this order, with exactly these labels: `No change: <count> candidates (<each in a few words>); reasons in /tmp/agents/retro-<session8>/dispositions.md`; `Clean: <category> (<command or digest section>); ...` for each category you ran a command for; and `Skill notes: <entry with its count and lines>; ...` from `session-digest --since-retro`, or `Skill notes: none`. Closing lines the user's rules ask for follow these lines and do not repeat them.
   - With 0 findings, open with "0 findings", list each candidate with its quoted line and the source you opened in place of the No change line, and ask whether to look again at any of them.
   - Label the findings F1, F2, ... and a finding's own options F1a, F1b, and use those labels in every later message, so a reply such as `2` cannot mean both a finding and an option. Ask once which findings to apply, name the recommended set by label, and accept a reply that lists labels such as `F1 F3` or `all`; decide how they land from the user's rules and the target repository's, and name the shape in the apply report. Recommend only findings whose cause step 3 confirmed, and list one still unconfirmed as optional with what is unconfirmed. Name each candidate you sent earlier and later dropped as withdrawn, with its reason. When the request already asked to fix something, apply the findings that fix what it named and ask about the rest. A reply that names findings, by label or by quoting their text, approves exactly those and the options it quotes.
   Done when the report holds each finding in the order above, the question is asked, each label a sentence cites matches the list, and every command, script, hook, file, label, project term, or session in it was typed by the user in the reviewed session or this retro, or is defined in a clause where it first appears. Compaction summaries, tool output, and your own earlier messages do not count as typed, and a name this run or an earlier retro added counts as new. Name a session by its repo and title with its id after them: `nixos-config session "code-reviewer retro" (6dab42cd)`.

5. Apply the approved findings: read [`references/apply.md`](references/apply.md) and follow it, and read it again after a compaction during the apply.
   Done when each approved finding has its report line, as apply.md step 4 describes.

## Reference

### Categories

- **Navigation**: how easy was it for the agent to find the right files? Are there hidden dependencies between files? Would a **navigation pointer** make it easier? _Use when_ the session took a long time to find a piece of information.
- **Automated checks**: are there automated checks that could catch errors the agent made? Linting, typing, tests, filesystem linters, and hooks the agent harness runs on tool calls? Read the repo's own check command first (its `package.json`/build-tool `lint`/`check` scripts, its CI workflow), so a check that already exists but sits unwired, silently broken, or too weak to catch this mistake is the finding, not a reinvention. A repo with no **guardrail** (no pre-commit hook and no CI job running its lint/typecheck/test command) is itself a finding: an un-linted repo is a standing missed opportunity, not a neutral default. _Use when_ the agent made a mistake an automated check could have caught, or the repo has no guardrail at all.
- **Coding standards**: should the **reviewer agent** be given a new rule to enforce? Should an existing rule be removed or clarified? Classify the violation first: a **mechanical** one (a fixed syntactic pattern, a banned API, an import shape, a file-location rule, a command shape) gets a deterministic check, full stop: a custom rule in the repo's own linter, a new pre-commit hook, a harness hook, or a new CI job, whichever the repo's language and existing guardrail make cheapest. Default to building the check over writing the rule, and always when the same mechanical slip recurs after a rule already named it. Reserve the repo's standards file (`CODING_STANDARDS.md` or its equivalent) for genuine **judgement calls** (cross-file consistency, "matches the surrounding style," anything no guardrail could ever substitute for). _Use when_ the reviewer agent failed to catch a mistake, including an escape whose cause is a missing or unclear rule.
- **Escapes**: which stage passed an escape, and why? A reviewer that read only part of a large diff, a test that waits on a fixed tick instead of the state it needs, and a lint config with no rule for the bug class are typical causes. Put the fix in the earliest stage that can catch the bug class: a deterministic check for a mechanical bug, as Coding standards says, otherwise the stage that passed it. _Use when_ a later review, gate, test, deploy, or user found a bug an earlier stage passed, or an agent said it covered only part of its scope.
- **Global AGENTS.md**: are there any steering instructions that should be moved to coding standards, automated checks, or a file that loads only for the paths it covers? _Use when_ the AGENTS.md file is particularly large - in the repo OR the user's global scope.
- **Tool economy**: did the agent make expensive tool calls that could be streamlined? Is there any custom tooling (CLI's, MCP's) that is particularly token-inefficient? Did it rebuild the same sequence by hand several times (a wait loop, a landing sequence, a transcript slice), which a script would replace? _Use when_ the agent made an expensive tool call or a call the digest lists as repeated.
- **No-ops**: look for instructions in steering files that don't modify the agent's behavior. _Use when_ the steering files are large and unwieldy.
- **Information access**: look for opportunities to increase the agent's access to information. Teeing dev server logs, readonly access to third-party services. Steps the agent handed to the user that its own access could have done count here. _Use when_ a crucial piece of information was not available to the agent, or the user had to act for it.
- **Containment**: which guard should have stopped the damage, and why did it not act? Check its status before proposing diagnostics, because a second incident can arrive before the next review. _Use when_ the session handled an incident: a crash, data loss, a resource exhausted, a bad deploy.
- **Orchestration**: did subagents stall, lose their reports, or duplicate a peer's work? Did a notice reach the wrong session? Did two sessions contend for a shared resource (a checkout, a port, a CI concurrency group, a protected branch)? _Use when_ the session ran subagents or worked beside other sessions.
- **Outputs**: do the things the session shipped (PR titles, commit subjects, docs, its final report) follow the conventions in force and cover every outcome the task required? A user asking "did you also do X?" marks a gap in the report. _Use when_ the session delivered PRs, commits, or a report.

### Implementation vs Review

Remember that all work goes through two stages: implementation and review. The implementation agent has the most **context pressure**. They are responsible for exploration, writing code, and debugging failures.

The review agent has the least context pressure - it receives a diff, so no exploration needed. It often does not need to write code or debug.

This means that the review agent should be responsible for imposing coding standards, not the implementation agent.

### Files

You have access to several files in the repo:

- `CLAUDE.md`/`AGENTS.md`: these files are pushed to the context window of any agent working in this repo. They should be used incredibly sparingly, usually only for **navigation pointers** to other files.
- `CODING_STANDARDS.md` (or the repo's equivalent): this file is read during review, not implementation. Add **navigation pointers** to docs folders if the standards file gets more than 1,000 lines long.
- Docs: use docs as references files, pointed to by other files. Look for existing docs before writing new ones.
- Skills: use skills for docs (since their description goes into the agent's context window), or for user-invoked commands. Follow the advice in the `writing-for-agents` skill.
- Hooks, lint configs, and scripts: deterministic checks live here, and they hold on every run whether or not the agent remembers a rule.
- Host config (services, units, scripts on the machine): a valid target when the friction came from the host; name the repo that owns it.
