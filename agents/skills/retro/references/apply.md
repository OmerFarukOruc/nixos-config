# Applying approved findings

Apply exactly the findings the user approved. A finding that appears after the user's answer, such as one from the refuter or from the proof, is unapproved: ask about it before you apply it. Ask once, giving the action, its size (a guess is fine), and its rollback, before you create or change an external resource the approved findings do not name, such as a token, a secret, a cloud object, or a remote setting, because the approval covers only its original scope.

Deliver each change under the target repository's own rules and the user's instructions for commits, reviews, and pushes; this file adds only what a retro change needs on top of them. A retro change that lands straight on the default branch still gets the one independent review the user's rules require (the `code-reviewer` agent in Claude Code) before its push, the same as any change of its kind. Work those rules require beyond the approved text, such as a review finding, another copy of a pattern the change hardens, or a bug found while proving a fix, stays in the same change when it is in a file the approved change touches. Otherwise, before you start each such item, post one line with the file, the rule that requires it, and its expected time (a guess is fine), then do it in its own commit after the approved findings land.

Before you edit a document an agent reads, load the `writing-for-agents` skill when it is installed (the Skill tool, or its `SKILL.md`) and follow it.

1. **Fresh target.** Re-read the target file right before editing it. Check that no other session, open PR, or merge since the retro already made the change: before the first edit, run `git fetch`, `path-claims <targets>` where it exists, and `gh pr list --state open --json number,files` filtered to the target paths. When the target is a symlink or a generated file, edit its source and regenerate what derives from it.
2. **Place it where its reader looks.** A new line goes under the heading the agent reads when it meets the case.
3. **Prove it against the session.**
   - A new or changed check fails on the session's original failure and passes after the fix.
   - A changed script or hook reruns the exact command that failed in the session, first against the pre-fix revision and then against the fix. Run the pre-fix revision in a scratch copy or a detached worktree, because the old code can repeat the damage it did in the session.
   - A changed instruction or doc gets its commands run the way an agent will run them. Every fact it states comes from a run or a primary source; a number the tool prints for itself stays out of the doc.
   - Size the proof to the change. A one-sentence rule gets the facts and commands it states run, plus one task from the session run once with the old text and once with the new, one agent each; for such a rule this replaces the task count in writing-for-agents `TESTING.md`. Run that file's full baseline when the finding is about a skill's or prompt's effect on what agents do.
   - A run that passes only in part counts as a fail.
4. **Report** one line per finding: done, with the evidence and the commit or PR read back from the remote, or open, with its blocker. Each line also names its review (the reviewer and the findings fixed) or why it had none, its proof command or `not proven`, and each hook block, rejected push, or failed command during the apply with the rerun that followed. Quote each applied line beside the approved line wherever they differ, even by one clause, and list each line that review added; when a finding's applied change is more than twice the size the proposal gave, name both sizes and what added the rest. List follow-ups found while applying. Every command, script, hook, file, label, or session in the report was typed by the user or gets a defining clause where it first appears. Close with `Skill notes: <entry with its count and lines>; ...` for the retro and apply run from `session-digest --since-retro`, or `Skill notes: none`; closing lines the user's rules ask for follow it.
