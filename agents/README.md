# agents

This folder holds the configuration of Omer's agent CLIs: Claude Code, Codex and the others. `home-manager/modules/agents.nix`, which `nixosModules/agents.nix` imports on nixos-desktop, nixos-rog and devbox, keeps a main checkout of this repository current on each of them and links each home to this folder in that checkout, so an edit to a linked file works at once; `claude/settings.json` reaches `~/.claude/settings.json` only at the next switch.

## Layout

| Path | Read through | Holds |
| --- | --- | --- |
| `shared/` | `~/.claude/shared` | `core.md`, the rules every agent follows, and the rule files it points to |
| `claude/CLAUDE.md` | `~/.claude/CLAUDE.md` | Claude Code's user instructions, which import `core.md` |
| `claude/rules/` | `~/.claude/rules` | Claude Code rule files |
| `reference/` | `~/.claude/reference` | reference pages the rules send agents to |
| `infisical.md` | `~/.claude/infisical.md` | the Infisical usage note |
| `skills/<name>/` | `~/.claude/skills`, `~/.agents/skills`, `~/.gemini/antigravity-cli/skills` | Omer's own skills; `skills/SOURCES.md` names what they borrow |
| `claude/hooks/` | `~/.claude/hooks` | Claude Code hooks: `bash-guard.py` with its modules, `guard-main-edit.py`, `bash-env.sh`, `stop-sound.sh` and its sounds, and `herdr-agent-state.sh`, which `herdr integration install claude` writes and `.gitignore` keeps out of git |
| `claude/statusline.sh` | `~/.claude/statusline.sh` | the status line |
| `claude/agents/` | `~/.claude/agents` | the `code-reviewer` and `comment-sicko` agents |
| `opencode/agents/` | `~/.config/opencode/agents` | the opencode agents `opencode-review`, read-only with no shell, and `opencode-implement`, which set their model and permissions ([herdr.md](reference/headless-clis/herdr.md), Starting an opencode agent) |
| `claude/mods/<name>/` | `CLAUDE_CODE_PLUGIN_DIRS`, which names `claude/mods/` | Claude Code mods, each loaded at session start ([Mods](#mods)) |
| `claude/settings.json` | `~/.claude/settings.json` | Claude Code's settings |
| `codex/codex.md` | `~/.codex/AGENTS.md` | the Codex-only rules |
| `codex/agents/` | `~/.codex/agents/<file>` | the Codex agent roles `default`, `worker`, `explorer` and `code_reviewer`, which reads `claude/agents/code-reviewer.md` |
| `grok/managed_config.toml` | `/etc/grok/managed_config.toml` | Grok's default settings |

Each path above `claude/settings.json`, and each file in `codex/agents/`, is a live link into the checkout or, for the mods, the folder that holds them, so a new mod folder loads in the next session without a switch; a new file in `codex/agents/` gets its link at the next switch. `programs.claude-code.settings` merges `claude/settings.json` into `~/.claude/settings.json` at each switch with `mutableSettings`, so Claude Code and `herdr integration install claude` can still write to that file and keep their keys, such as each host's `autoMode.environment`. A declared key overwrites the live one, a declared list replaces the live list, and a key removed from `claude/settings.json` stays in the live file until someone deletes it there. Other hooks come from elsewhere:

- herdr writes its `SessionStart` hook.
- `programs.worktrunk.claudeCodeIntegration` (`home-manager/modules/agent-cli.nix`) adds the `WorktreeCreate` and `WorktreeRemove` hooks, which run `wt`, and activity hooks that set a marker for `wt list` in the repository's `.git/config` at each prompt, question, and stop. `agent-cli.nix` replaces its `WorktreeRemove` command with one that passes `--force`, so a discard at exit removes a worktree with uncommitted changes. `WorktreeCreate` runs `wt switch --create`, so an `isolation: "worktree"` agent's worktree starts from the default branch, not from the parent session's commit; for a local branch that already exists it runs `wt switch` without `--create`, which returns that branch's worktree.
- `home-manager/modules/claude-tools.nix` adds the `StopFailure` hook that `claude-tools rotate` reads.
- The impeccable plugin adds a `SessionStart` hook, a `PostToolUse` hook on `Edit|Write`, and a `Stop` hook, each running its `impeccable hook` script.

Enabled plugins and their marketplaces are settings keys. Claude Code fetches a plugin that user settings enable once a session starts, and loads it from the next session on. `autoUpdate` on a marketplace makes Claude Code update it and its plugins after a session starts; Anthropic's own marketplaces update without it.

An edit inside a `skills/<name>/` folder works at once, but a new folder gets its links only at the next Home Manager switch, because the module lists `skills/` when it evaluates. Skills copied whole from other projects come from flake inputs: `home-manager/modules/agent-skills/` applies each local patch from its `patches/` folder and links the result into the same three folders, and into `~/.codex/agents` for impeccable's Codex agents. A skill whose upstream ships a Claude Code plugin reaches Claude Code as that plugin and the other agents as the copy, unless only Omer starts it, which `skills/SOURCES.md` explains. `skills/SOURCES.md` lists both kinds and what each patch keeps. The module writes `home.file` entries instead of using `programs.claude-code.skills`, because that option fills only `~/.claude/skills`, the other two folders need the same names, and the own skills need links into the checkout.

Grok 1.0.77 reads `/etc/grok/managed_config.toml` as a layer below `~/.grok/config.toml`, so these defaults reach every host while a setting changed inside Grok wins on that host and stays there; `grok inspect --json` lists both files under `configSources`. `nixosModules/agents.nix` writes the file at each NixOS switch. Its keys leave out the ones Grok writes as state (`privacy`, the `marketplace` install flags, `cli.installer`) and the `rea` MCP server, which only nixos-rog installs by hand and which its own `config.toml` keeps. The Grok package already sets `GROK_DISABLE_AUTOUPDATER=1`, and the Amp package `AMP_SKIP_UPDATE_CHECK=1`, so neither config turns updates off.

`~/.codex/AGENTS.md` is a file that Home Manager builds from `shared/core.md` and `codex/codex.md`, so a change to either reaches Codex at the next switch, within the hour on every host, the PCs only on AC power (the repository's `AGENTS.md`). Home Manager's `programs.codex` would also build it, but with `home.preferXdgDirectories` on these hosts it moves `CODEX_HOME` to `~/.config/codex`. `programs.claude-code` has `context` and `rulesDir`, but `context` would write the link's store path as text and `rulesDir` links file by file, so a new rule file would wait for a switch; raw `home.file` entries avoid both.

Each entry sets `force`, because Home Manager backs up only a target that is not a symlink, and the links an earlier setup left there would otherwise stop the switch. Each switch also runs `agents-pull` before it ends, so the links never wait an hour for files the deployed commit added.

The commands these files name, such as `pr-land`, `wait-exit` and `sandbox-run`, come from `pkgs/agent-tools`, which the same module installs ([its README](../pkgs/agent-tools/README.md)).

Private values stay out of these files ([Checks](#checks)). The Infisical project IDs reach every zsh, interactive or not, through `.zshenv` as `$INFISICAL_PERSONAL_SECRETS_PROJECT` and `$INFISICAL_STATUSLANTERN_PROJECT` from the sops secret `agents-infisical-ids`.

## Claude Code settings

- `switchModelsOnFlag` is `false`, so a request that a safety classifier flags never moves to an older model unnoticed: an interactive session asks first, a headless run ends the turn with a refusal, and an Agent-tool subagent fails (Claude Code model-config docs, "Ask before switching").
- The Bash sandbox stays at its default, off, so `settings.json` sets no `sandbox` key. When it was on, it left empty placeholder files in the working checkout (`.bashrc`, `.gitconfig`, `.mcp.json`, `.claude/settings.json` and others) and an empty `.git/config.lock` that made every `.git/config` write fail, even outside the sandbox.
- Give each login its own `.credentials.json`. Claude Code rotates the OAuth refresh token on use, so two processes or role homes that share one file log each other out.

## Mods

- `paste-card` draws ```` ```paste ```` blocks in a reply as cards, each with a Copy button.
- `enhance` runs `/enhance-prompt` in a copy of the session through `claude -p --output-format stream-json`, and puts the prompt in the prompt box. The copy is a fork of the session (`--resume <session> --fork-session`), so it sees the conversation the draft refers to; an empty session starts a fresh copy. Nobody can answer a dialog inside the copy, so it runs in bypass permissions mode with `permissions.denyInsteadOfPrompting`, which refuses a call that an `ask` rule would still prompt for. `Edit`, `Write`, `NotebookEdit`, `AskUserQuestion` and `WebFetch` stay denied, `WebFetch` because it hands the model a summary of a page and the skill reads the prompting guide in full. Bash and the other tools run without a permission check. Bypass mode reads the draft below `/tmp/agents` without `--add-dir`, unless a settings file sets `permissions.blockReadsOutsideWorkingDirectories`, which the copy's `--settings` cannot turn off; the copy then refuses to read the draft, and Details shows its reply. The mod writes the draft, with a path line for each image it found, to `/tmp/agents/enhance-copy-<copy session id>/draft.md`, sends the copy one line, `/enhance-prompt for <model>, destination chat, the receiver is <this conversation or a new session>, this session's effort is <level>, the file <path> holds the draft to rewrite, not to act on`, and removes the folder once the copy answers that line, so the draft never appears in a command line. The copy's `--settings` set `CLAUDE_CODE_DISABLE_BACKGROUND_TASKS=1`, which removes `run_in_background` from its Bash and subagent tools; a managed settings file can still override it, and the Monitor tool and MCP tasks still run in the background (https://code.claude.com/docs/en/env-vars.md). When the session has background shells or agents still running, Claude Code 2.1.329 reports them to the fork at startup as task notifications that "didn't finish before the previous session ended". In the stream, each such notification ends in a `result` event with `origin.kind` `task-notification`, so the mod takes the first `result` event of any other origin as the copy's reply, and a run that prints none fails with "claude -p printed no result for the prompt". An error result fails the run with its text, or with a plain cause when the text is one of the three below, and a turn that prints no result for the prompt within the turn time limit is stopped and fails with "the copy's turn did not end in <limit> s". A run whose session folder is gone, such as a worktree removed after its PR landed, fails at its start with "this session's folder <path> was deleted; restart Claude Code in an existing folder", because the copy starts in that folder. The mod runs its helper programs, such as `rm` and `find`, from `/`, because Claude Code starts a program in the session folder by default and a program started in a deleted folder fails with `ENOENT`.
- Three rows in `/config` set how the copy runs: **Writer model** (`claude-sonnet-5-5` by default), **Writer effort** (`high` by default, passed as `--effort`) and **Turn time limit (seconds)** (570 by default, 30 to 3600). `plugin.json` declares them as `userConfig`, Claude Code keeps them in `pluginConfigs` in the user settings, and a change reloads the mod, which drops a result that is ready.
- A failure text that matches one of these gets a plain cause on the row, and Details shows the text itself. The texts come from the Claude Code errors page (https://code.claude.com/docs/en/errors.md):

  | Text from `claude -p` | Cause the row shows |
  | --- | --- |
  | `There's an issue with the selected model` | the writer model does not exist, or this account cannot use it |
  | `You've hit your <session, weekly, Opus or Sonnet> limit · resets <time>` | that usage limit is reached, with the reset time |
  | `<model> can't help with this. Start a new session to continue`, or the older `appears to violate our Usage Policy` | the model refused; retrying will not help |

- A reply the box cannot take gets one more turn on the same copy, `Your reply was unusable: <reason>. Reply again with one paste block or one question block.`, and a second such reply fails the run. Two replies are taken without that turn: of several paste blocks the last one is the prompt, and a last paste block that never closes is the prompt up to the end of the reply, with the notes line "The reply's paste block was not closed, so the prompt may be cut off."
- When the copy asks a question, the mod shows it as a dialog and sends the answer back as `Answer: <text>`. A dialog you dismiss sends ``Answer: none; continue, and state what you assume as an `Assuming:` line in the prompt``, so the run goes on.
- Once a prompt is ready, the mod asks a cold reader, a second `claude -p` on the writer model with no tools (`--tools ""`), what it would do with the prompt, and adds its one-sentence answer to the notes as `Cold reader:`, beside the copy's `Understood goal:`. The reader gets the prompt on stdin. In a session that has a turn it is a fork of the session, so it reads what the receiver will read. A reader that fails adds no line, and its session files are deleted when it ends.
- The mod adds three more kinds of line under the copy's notes: `Not in the prompt: <item>` for each path, URL, inline code span and image path of the draft that the prompt does not hold, `Cold reader:`, and `Cost: $<cost>, time: <seconds> s`. The cost is the sum of `model_usage_since_last_result` over the turns of the copy and the reader, because `total_cost_usd` of a resumed or forked run also counts the earlier spend of its session (https://code.claude.com/docs/en/agent-sdk/cost-tracking.md); without that field the line says "not reported".

The Enhance button on the row above the prompt box starts a run on the text of the box, and so does the chord of the keybinding action `app:cycleDiffBase` (`ctrl+x b` by default) while the `/diff` panel is closed. `/enhance <draft>` starts a run on the text typed after it. An empty box, or `/enhance` alone, shows a toast and starts nothing. `enhance` always draws that one row, and its content changes with the state of the run:

| State | Row |
| --- | --- |
| No run | Enhance, Runs, and after a cancel that put the draft back, "Cancelled. The draft is back in the box" |
| The copy runs | "Enhancing the draft…", the seconds so far, the copy's current tool call, Cancel |
| The prompt is in the box | Copy prompt, Restore draft, Send, Revise, Notes, Dismiss, then the goal and the effort |
| The prompt is ready and the box was edited during the run | Use prompt, Copy prompt, Send, Revise, Notes, Dismiss, then the goal and the effort |
| The run failed | the reason, Retry, Details, Dismiss |

- The prompt fills the box only when nobody touched the box during the run. Use prompt puts it there otherwise, and Restore draft puts back the draft, or the box's own text when the box held some. The two swap until the result is sent or dismissed. The row says "Draft already clear, nothing changed" when the prompt equals the draft.
- Copy prompt puts the enhanced prompt on the clipboard and shows a toast with the result. Send submits the prompt as the next user turn.
- Revise asks what should change, resumes the same copy with `Revise: <text>`, and replaces the prompt and the notes with its answer. A Revise turn that fails or is cancelled leaves the earlier prompt, its notes and its record as they were, and a toast gives the reason of a failure. For that, the copy's session files stay while a result is ready. They are deleted when the result is dismissed or sent, when a new run starts, when the session ends, and at the next session start after a session that died with a result ready. A first run that fails or is cancelled deletes them at once.
- The goal and the effort are the notes' `Understood goal:` and `Effort:` bullets, each cut to one line.
- A run that ends ready or failed sends a notification through `$.ui.notify`, "Enhanced prompt is ready" or "Enhance failed". A run you cancel sends none.
- A run that fails or is cancelled while the box is empty and untouched puts the draft back in the box, and the row says so.
- A prompt that the user submits, typed or through Send, clears the row and closes the pane. A task notification or a message from another session leaves a ready result in place.
- The copy's command names the receiver (the session the prompt is written for). After the first turn of a session that is "this conversation", so the skill writes in the first person and leaves out what the conversation already holds. In a session with no turn yet it is "a new session". A draft that names another receiver or target model wins.
- For each `[Image #N]` in the draft, the mod looks for the pasted image under `/tmp/claude-<uid>/<project>/<session id>/images/` and adds its path to the draft. Claude Code documents no such folder, so after an update check that a pasted image still lands there; without the file the draft goes on unchanged. A typed path that ends in `.png`, `.jpg`, `.jpeg`, `.gif` or `.webp`, bare, after `@` or in quotes, absolute, under `~/` or relative to the session folder, gets a line with its full path when the file exists.
- Each run that ends leaves one file, `${XDG_STATE_HOME:-~/.local/state}/enhance/runs/<start time>-<run id>.json`, with a format `version` (2), the draft, the session's id, folder, model and receiver, the seconds the run took, and the outcome: the prompt and notes, the failure reason, or `cancelled`. It also holds what produced the prompt: the `model` the copy ran on, `costUsd`, `turns` and `tokens` summed over the copy and the reader, `skillSha256` (the sha256 of the `SKILL.md` under the Claude config folder, or of the mod's own copy when that file is missing), `guides` (for each guide page the run downloaded into the skill's cache, or whose URL the notes name as read from the cache: its URL, its sha256 and `isDownloaded`), and `case` (the notes' `Case:` bullet). `sent` says what happened to a ready prompt: `as-is`, `edited`, `own-draft` when the draft was sent instead, or `dropped` when it was dismissed or replaced, so a Revise turn, a send and a dismissal each write the file again. A session start deletes the records that started more than 30 days ago, and the folder keeps every other draft and prompt as plain text. The session id and folder in a record are a note of where the run happened and can outlive both. A write that fails shows a toast and leaves the run as it ended, and a session that ends waits up to 1.2 s for the write. `jq -r '[.startedAt, .seconds, .outcome.kind, .sent] | @tsv' "${XDG_STATE_HOME:-$HOME/.local/state}"/enhance/runs/*.json` lists the runs.
- Runs opens the `enhance-runs` pane. Its first row holds this session's last draft with Put draft in box, which is the way back to a draft after a dismissal, because a mod cannot add to the prompt's Up-arrow history. Below it are the 10 newest records: start time (UTC), outcome and the first line of the draft, with Copy prompt on a run that has a prompt.
- Notes opens the `enhance-notes` pane, which draws the copy's notes as Markdown, with the label of a top-level bullet in bold when the bullet opens with up to 40 characters and a colon, then the enhanced prompt in a frame. The pane also opens by itself when a prompt is ready and the terminal is at least 144 columns wide, and it repeats the row's buttons, because Claude Code 2.1.325 leaves the row out while the box is taller than its share of a fullscreen terminal. To see it, fill the box with a prompt of more lines than half the terminal's rows.
- Retry runs the same draft again, and Details opens the pane with the whole reason, the copy's reply when it sent one, and Retry and Dismiss.
- `ctrl+x tab` moves the keyboard to the row or the pane, Tab walks the buttons, and Enter presses one.

### Install enhance on another machine

`.claude-plugin/marketplace.json` at the root of this repository lists `enhance`, so anyone installs it in a Claude Code terminal session with one line:

```
/plugin install enhance --marketplace OmerFarukOruc/nixos-config
```

Claude Code asks to add the marketplace (`y`), then for a scope (the user scope, Enter). `claude plugin update enhance@oruc` fetches a later version. The mod carries the `enhance-prompt` skill as `skills/enhance-prompt`, a link to `agents/skills/enhance-prompt`, so the install brings the skill and `/enhance-prompt` works without a copy in `~/.claude/skills`.

The mod needs Linux or macOS, an account that can run the writer model (Sonnet 5.5 unless the Writer model setting names another), and a network path to `platform.claude.com`, where the skill reads the prompting guide. Each `/enhance` starts a `claude -p` copy in bypass permissions mode, as the `enhance` entry above describes.

## Edit loop

- Edit `agents/` in the main checkout (`~/Desktop/workspace/nixos-config`, the option `oruc.agents.checkout`), commit to `main` there, then run `git pull --rebase` and `git push origin main`. Every other path of this repository still needs a worktree. The pull unit below sets `git config agents.mainCheckoutEditPaths agents/` in the checkout, and Claude Code's edit guard allows the main checkout only for those paths.
- A main checkout needs `direnv allow` once, so the commit hooks find their config.
- Before you commit a change to `model` or `effort` in `claude/agents/`, start that agent once with no per-call `model` or `effort` and confirm the model it ran with `jq -r 'select(.type=="assistant") | .message.model' <transcript> | sort -u`, which prints one model name. The transcript is `~/.claude/projects/<project>/<session>/subagents/agent-<id>.jsonl`, under `subagents/workflows/<runId>/` for a Workflow agent, and `<id>` is the agent id the Agent tool returns. No check reads the frontmatter, and Claude Code 2.1.322 sends an unknown model name to the API, so the agent ends with `model_not_found` and the command prints `<synthetic>`.
- `agents-pull.timer` runs `agents-pull` every hour. It clones the checkout when the folder is missing and otherwise fetches `origin` and fast-forwards `main` to its upstream. The fetch rewrites GitHub's SSH URL to HTTPS for that one command, because the repository is public and the switch that also runs it has no `ssh` and no SSH agent; pushes keep SSH through the `pushInsteadOf` in `home-manager/modules/git.nix`. A failed run leaves a line that each new shell prints until a run succeeds (`home-manager/modules/scheduled-unit.nix`); `journalctl --user -t agents-pull` shows the run. An unreachable GitHub is not a failure.

## Checks

The pre-push gate (`ci/gate.sh`) checks every commit between `origin/main` and the pushed revision:

- `ci/private-scan.sh` runs on every push. It runs `gitleaks git` on those commits and refuses one whose message or added lines, binary files and merge results included, hold one of Omer's private values, such as an account email, an Infisical project ID or the tailnet name. This repository is public and keeps every pushed commit, so a value has to be gone from the commit itself, not only from a later one. The values come from the sops secret `agents-private-values` in `secrets/agents.yaml`, one per line, decrypted to `/run/secrets/agents-private-values` on nixos-desktop, nixos-rog and devbox; `AGENTS_PRIVATE_VALUES` names another file. The scan prints the commit and the file of a hit, never the value. Add a value with `sops secrets/agents.yaml` ([Secrets](../docs/architecture.md#secrets)).
- `ci/agents-checks.sh` runs when those commits touch `agents/`. It runs shellcheck on each `.sh` file and ruff on each `.py` file, and parses each `.json` and `.toml` file, as the pushed revision holds them. When they touch a mod under `claude/mods/`, it also runs `claude plugin validate` on that mod, and `claude plugin test` when the mod has a `tests` folder, on a copy of `agents/` as the pushed revision holds it, with `HOME` and `CLAUDE_CONFIG_DIR` in a scratch folder, so neither needs a login. The devenv shell takes `claude` from the `llm-agents` input of `devenv.yaml`, the input the hosts install Claude Code from, so a Claude Code update that changes the mods API can fail this step. The check has no type check, because `claude` writes a mod's generated types only when a session loads the mod. The `update` workflow's commits touch nothing under `agents/`, so this step does not run on the GitHub runner.
- When every path those commits touch is under `agents/`, the gate skips the Nix checks, unless a `.nix` file names one of those paths or the commits add or remove a folder under `skills/` or a file in `codex/agents/`. `home-manager/modules/agents.nix` reads `shared/core.md` and `codex/codex.md` this way, so a change to either runs the Nix checks, and `home-manager/modules/agent-skills/` lists `skills/`, and `agents.nix` lists `codex/agents/`, when Home Manager evaluates.
