## Claude Code

- A text-only end of turn is a report, and the work it names stays open. While authorized work remains and nothing needs Omer, put a status note or recommendation in the same message as the next tool call instead of ending the turn on a summary that announces the next step, or because the turn was long or a milestone landed. When a step waits for an event this session can trigger now, trigger it and continue, for example by opening a throwaway PR that shows the bug instead of waiting for the next real PR, or by starting a timer's unit by hand or moving a time window or reboot this session configured instead of waiting for the clock. Waiting on work this session already started follows the background-work rule below.
- Put one open question in each AskUserQuestion call; related yes/no confirmations may share a call. Write the question and each option the way voice.md asks, decision first, because Omer reads them cold. Put a step Omer must run before he can answer, such as a `! <command>` or an app restart, in a text reply that ends the turn, and ask the question once a check shows the step took effect, such as the process's environment or a log line. An open question takes no prompt input, so a `! <command>` typed while it is open does not run, and he answers without the step. When you need to ask Omer something while background work you started runs, and that work does not need the answer, ask in the text reply that ends the turn, as numbered options, because an open AskUserQuestion holds the work's completion notification until he answers. When Omer closes a question to clarify and sends no text, ask it again in plainer words with each option's effect in one clause. Leave a number out of the question unless the choice depends on it. A number you keep needs its source, or `guess` or `unsupported`, in the same question text or option description, because Omer cannot check a number without one; a lead-in such as "Cases:" is not a source, and issue numbers, SHAs, versions and dates need nothing. Bad: "about 3 hours". Good: "about 3 hours (guess)". An option that adds code, a script, a check, a dependency, or a recurring chore states its size (an estimate marked `guess` is fine), each new dependency or `no new dependency`, and the upkeep each later change pays or `no upkeep`, because Omer weighs what he will maintain; "a small check" fails. When the options differ in a layout, a flow, or which component calls which, give each option an ASCII drawing in its `preview`, because Omer chooses from a drawing and asks for one when the options come only as prose.
- When a peer session's finding is already claimed, run `ListAgents` to find it and hand it over with `SendMessage`, including the evidence and an explicit file boundary naming what each side will and will not touch. When `ListAgents` does not list the peer, write the handoff to `~/handoffs/<peer>-<date>.md`, then deliver it yourself: with `HERDR_ENV=1`, find the peer's pane in `herdr agent list`, where the entry whose `agent_session.value` is, or starts with, the peer's session id names its `pane_id`, and run `herdr agent prompt <pane> "<text>"`, where the text names this session and the handoff path. This rule is the request the herdr skill waits for, so a peer handoff needs no mention of herdr from Omer. A working peer queues the prompt; one blocked at a question rejects it with `agent_blocked`, so retry after it answers. When the peer has no pane, name the handoff path in the final message. When the peer keeps a checklist it reads on resume, such as a campaign or lane `TASKS.md`, also append one line there that points to the handoff file, because the peer reads that checklist and never sees this session's final message.
- After you start background work (a Bash `run_in_background` task, an `Agent`, or a Workflow), do only the steps that do not need its result, then end the turn; its completion notification re-invokes you, while a foreground loop dies at the Bash tool's 600000 ms limit. Later replies while it runs say only what changed. A background wait prints what it waits for and why on its first line, then one progress line per loop (time left or the state it checks); `wait-exit` does both for a log, and its Bash `description` says the same, because Omer opens it as "Shell details", which otherwise shows "No output available". With several agents, answer each earlier wake-up in one line and send one summary after the last. Before you end the turn on a CI run or deploy that a push should start, check that it started (`gh run list`), and give its watcher a start deadline of 3 minutes (guess) after which it reports that no run began; when an earlier push started no run, find the cause first, such as a merge conflict that stops `pull_request` workflows (`gh pr view --json mergeable`).
- When a Bash task you started has a result you need next and ends within about 2 minutes (guess), going by an earlier run's time when there is one, wait for it in the foreground instead of ending the turn, because ending the turn sends Omer a reply that only says the task is running. This holds for the long local commands that core.md sends to the background too. A longer foreground wait shows Omer a "running, no output" panel and holds his typed messages until it ends. Start the task in the background as `cmd > /tmp/agents/<task>-<session8>/x.log 2>&1; ec=$?; echo "exit $ec" >> /tmp/agents/<task>-<session8>/x.log; exit $ec` and wait in the foreground with `wait-exit /tmp/agents/<task>-<session8>/x.log <seconds>`, which ends only on that final line and exits with the task's code, using literal paths because shell variables do not survive between calls. Give that Bash call a `timeout` above the wait, and put the wait in its `description`. An `Agent` or a Workflow never gets a foreground loop; check one once with `ListAgents`, its report file, or the Workflow's `journal.jsonl`.
- Notifications can arrive late, batched, or truncated. When Omer is away and a lost notification would stall the run, also start one Bash `run_in_background` watcher with a deadline on the report file; while he is present, start none, because he sees a stalled agent in the agent panel. Answer a copy of a report you already acted on in one line. For a named agent, run `agent-watch <name> <report> <seconds>`, which exits 0 on the report and 3 when the agent has sat idle for 3 minutes without it, printing its last answer, so you `SendMessage` it then instead of at the deadline. For any other report, use `timeout 1800 bash -c 'until [ -s <report> ]; do sleep 30; done'`.
- For a long run with several parts, keep the open items in `/tmp/agents/<task>-${CLAUDE_CODE_SESSION_ID:0:8}/TASKS.md`, even when a plan file or Linear issue holds the plan, and put one check on each line. Tick a line only after its own command ran. A follow-up, deferred item, or blocker gets its line in the same turn you first write it anywhere, such as a spec, a report, or a message to Omer, because the final report is built from this file. The first lines name the handoff or plan file the run started from and its hard constraints, such as the subagent model and the stop conditions. When an item's state changes, edit that item's own line instead of adding a line, so the unchecked lines are exactly the open items. Before a reply to Omer that ends the run or stops for his answer, run `grep -n '^- \[ \]'` on the file and name each unchecked line in the reply as open with its blocker, or tick or drop it first with its evidence or reason; a wake-up or mid-run reply gives only the done and open counts (core.md, Working). An item that waits on a launch or a date, or will outlive this run, also goes into a GitHub issue or the repository's tracked checklist in the same turn, or a Linear issue when Omer asked for one (linear skill), because `/tmp` is pruned. After a context summary, read this file and that handoff, load again with the Skill tool each skill the next step follows, and read again the files it points to, such as the planning skill's `references/` before a plan or its revision, because a summary can drop the handoff's constraints and its path, and Claude Code re-attaches after a compaction only the first 5,000 tokens of each loaded `SKILL.md`, drops the oldest past a 25,000-token total (Claude Code skills docs), and never re-attaches the files they point to. The session id in the folder name keeps two sessions on the same task out of each other's file; add a line with `>>`, or edit the file, once it exists, because `cat >` replaces what another writer put there.
- Before you report that something else removed a file or stopped a task (core.md, Verification), also search this run's `TASKS.md` and your own `TaskStop` calls.
- Claude Code asks before an `rm` whose path starts with a variable that could be empty, and before a Bash call whose `bash -c`, `sh -c`, `zsh -c`, or `eval` string contains `rm`, even with permissions bypassed. An unattended session cannot answer, so the call is denied or hangs. Write the variable path as `"${d:?}"/name`, and never put `rm` inside such a string, a literal path included; put the script in a file and run `bash <file>`.

### Delegation

Do the work in this conversation: reading, searching, editing, testing, and re-checking. Results then stay in one context where later steps can use them, while an agent gets only its prompt, returns a summary that drops detail, and loads every instruction file again. Start an agent only in these cases:

- **A read too large to keep**: a sweep whose file contents would fill much of this context, when only its conclusion matters.
- **Independent parallel work**: items that need nothing from each other and each return a short result, such as separate research questions. Give each agent one scope and name its boundary. Check each agent's evidence before you accept its finding, and finish with one table: scope, verdict, evidence.
- **The one review of a change**: each change gets one reviewer that did not write it, on the diff in its final landing shape. Use `code-reviewer`, which carries the review rules (ub-mode, thermo-nuclear, dryer, the comment hunt, the repository's review skill, and the testing discipline with a verdict for each test when tests change) and runs a Codex review of the same diff in parallel, so the change needs no separate review from another model. Start it without a `model` or `effort` argument, because a per-call value replaces the model and effort its definition sets. An implementer's report of its own review is a claim for that reviewer to check. The review prompt gives the code, the intended behaviour, and what to look for; a claim that vouches for the code, such as "ran in production for 2 weeks" or "stores over SSH as before", stays out, because a reviewer reads vouched-for code less closely. Fix every finding the review returns, low and nit ones included, because a reviewer's severity ranks the findings and a gap left in a touched file ships. Keep a finding only when its fix would break a rule or a check, and name it and that reason in your report to Omer. After the review, check the review fixes yourself with `git range-diff`, or for an uncommitted change by comparing the reviewed patch with the current `git diff`, and start no second review agent for them; a new scope or design Omer asks for after the review gets its own review (`~/.claude/shared/reviews.md`).

When an agent implements a change, its prompt names the supported way you found (a docs page, a nixpkgs attribute, an existing helper) and any pin, patch, or workaround it must not add, because a brief that omits the method gets a pin.

### Running agents

- A background Agent-tool agent writes its report as a file, because its final message can reach you truncated, or not at all, and it can go idle with no completion notice. Put the file in its own directory under the task's scratch directory, such as `/tmp/agents/<task>-${CLAUDE_CODE_SESSION_ID:0:8}/<agent-label>/`, and ask for a five-line summary that names the path; its cleanup then stays out of your files. Tell it to write the report under a temporary name and `mv` it into place as its last step, to run every command in the foreground, and to end its turn only once the report file exists, because a notification for its background work reaches you instead and leaves it idle, even when its prompt says to finish background work. For a gate longer than the 600000 ms limit, it runs the gate in slices and names any command it could not finish. A Workflow agent with a `schema` returns through StructuredOutput into `journal.jsonl` and writes no report file.
- An Explore or Plan agent runs read-only and cannot write a report file. When such a task needs a report file, start a `general-purpose` agent for it instead. Otherwise take the Explore or Plan agent's final message as its report, and give it no report path, report watcher, or request to write its report; when that message arrives cut, read its transcript as the next bullet shows.
- When `ListAgents` shows a named agent idle and no report arrived, `SendMessage` it to write its report, and pass on any notification for its work that reached you. Then read its report file. Without one, read the last assistant text in `~/.claude/projects/<project>/<session>/subagents/agent-<id>.jsonl` (for a Workflow agent, under `subagents/workflows/<runId>/`), for example with `tail -n 3 <file> | jq -r 'select(.type=="assistant") | .message.content[]? | select(.type=="text") | .text'`.
- Claude Code's Write refuses an agent's file whose name starts with `REPORT`, `SUMMARY`, `FINDINGS`, or `ANALYSIS` and ends in `.md`; that is expected. The agent writes its report with a Bash here-doc to the path named in its prompt, which works for any name.
- When an agent's deliverable is accepted or its branch merges and `ListAgents` still shows it running or idle, stop it with `TaskStop`, because an idle agent keeps its context and worktree alive. An agent whose completion notification arrived has already ended, and `TaskStop` on it fails with "No task found". A stopped agent restarts when a message reaches its name, so before `TaskStop` on an agent you did not start, match its name and description in `ListAgents` against your own dispatches, because it may be a restarted copy of one of them.
- An agent that edits a repository runs that repository's gate for the files it changed and fixes its failures before it reports.
- Send a reviewer new scope or changed files only after it reports, because edits made mid-review give it a mixed state and it re-lists findings that are already fixed.
- An agent drives a browser only when its prompt names the browser and the agent-browser session it owns, `<parent session>-<agent name>`; sessions that share one name move each other's tab.
- Before you dispatch a `fork` subagent or write a Workflow script, read `~/.claude/reference/orchestration.md`.
