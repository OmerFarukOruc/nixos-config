# Working rules

- Change `nixos-desktop`, `nixos-latitude` and `nixos-rog` only through this repository. `deploy.sh` builds from a copy of this checkout, so an edit to a host's `/etc/nixos` never reaches the system.
- Deploy every change that reaches `main` to each host it affects without asking again, as [docs/deploy.md](docs/deploy.md#deploy-a-change-on-main) describes, except nixos-rog and devbox: their timers deploy `main` within about 2 hours, so deploy them by hand only when the change needs proof on that host now. A host is affected when its system `drvPath` differs between the `main` the change landed on and the change; `scripts/affected-hosts.sh <old>..<sha>` lists the affected hosts of a push, where `<old>` is the `main` the push landed on. Before you end a session that deployed, run `scripts/affected-hosts.sh --running`; it lists each host whose running system differs from `main`, such as one that was offline at the deploy, or a timer host still waiting for its next run. A host that is behind only because of commits another session pushed is that session's to deploy; report it and leave it. `./deploy.sh` does not reboot, so a kernel parameter takes effect at the next boot; the reboot and offline rules for nixos-latitude are in [docs/nixos-latitude.md](docs/nixos-latitude.md#operation).
- Ask Omer only for a login, a greeter password (the SDDM login screen) or a judgement of what is on screen. A screenshot of the whole session (`scripts/screenshot-nixos-rog.sh OUTPUT.png`) needs no approval, but it captures whatever Omer has open, private pages included, so delete a shot of unrelated windows without describing it. A visual change takes the `--window` shot from [Check a visual change](docs/nixos-rog.md#check-a-visual-change), which opens a Ghostty window on Omer's screen, so ask first.
- [CONTEXT.md](CONTEXT.md) defines the domain terms (this PC, the laptop, login session, hybrid mode, integrated mode) and each host's SSH alias.
- When a request moves a setting from one place to another, such as "use nixos-rog's keyboard setup on nixos-latitude", state the source host, the target host and the repository the change lands in, in one sentence, before the first change or push. Ask which host only when the request names none and the change would apply to just one. Shared code goes in `nixosModules/` and `home-manager/`, and code for one host goes in `machines/<host>/` ([docs/architecture.md](docs/architecture.md#inventory)). The `drvPath` rule above decides which hosts to deploy.
- Before changing the machine record (`machines/`), login sessions, theme or Home Manager wiring, read [docs/architecture.md](docs/architecture.md). To move the kernel, an input or an app by hand, read [docs/updates.md](docs/updates.md). nixos-latitude's hardware facts and measured dead ends are in [docs/nixos-latitude.md](docs/nixos-latitude.md). Rollback, boot repair, a first nixos-latitude install, kernel-cache and Home Manager have guides listed in [README.md](README.md#docs).
- This repository is public. Write a placeholder such as `<lan-ip>` or `<tailnet-name>` for a LAN IP, a tailnet name, an Infisical ID or a token.
- A change commits straight to `main`, with no PR, once the git hooks of `devenv.nix` pass: `nix fmt` before the commit, `ci/checks.sh` and `ci/unit-cycles.sh` before the push ([Check before you deploy](docs/deploy.md#check-before-you-deploy)). Work in a worktree on a local branch from a freshly fetched `origin/main`. To land it, run `git fetch origin && git rebase origin/main`, keep `old=$(git rev-parse origin/main)`, then `git push origin HEAD:main`. When the push is refused because `main` moved, fetch, rebase and push again, never with force. Never skip a hook with `--no-verify` or `PREK_ALLOW_NO_CONFIG`; nothing on GitHub checks a commit you push; GitHub builds only the kernel ([kernel-cache/README.md](kernel-cache/README.md)) and the updates of `.github/workflows/update.yml`.
- A worktree from `wt switch --create` runs `direnv allow` and loads the devenv shell itself. In one from `git worktree add`, run `direnv allow <worktree>` and `direnv exec <worktree> true` before the first commit. Until then the hooks find no config and refuse the commit.
- The update workflow merges input and app moves to `main` every 6 hours, so `main` and `flake.lock` move often ([docs/nixos-rog.md](docs/nixos-rog.md#updater)).
- Add a package to a host only when Omer or a coding agent runs it by hand. Linters and formatters come from the devenv shell in `devenv.nix`, which direnv loads.

# Checks

Agents run on nixos-desktop or on nixos-rog; `hostname` tells which. These scripts run Nix on a copy of this checkout in `/tmp` on the host that runs them, under `heavy`. Never send Nix work to the other host over SSH: on 27-10-2026 agents on nixos-desktop filled nixos-rog's memory that way. Only the `*-on-rog.sh`, `*-nixos-rog.sh` and `thermal-test-rog.sh` scripts send work to the laptop, because they act on it; they exit 1 at once while Tailscale reports nixos-rog offline (`scripts/lib/rog-host.sh`). [README.md](README.md#everyday-commands) lists every script you run by hand.

- A change to `pkgs/`, `overlays/`, `home-manager/modules/plasma-*.nix`, `scripts/prepare-update.sh`, `scripts/pull-main.sh`, `machines/nixos-rog/auto-update.nix`, `nixosModules/deploy-host.nix`, `nixosModules/deploy-unit.nix`, `scripts/lib/pull-main.sh`, `scripts/self-deploy.sh`, `scripts/self-deploy-reboot.sh`, `devenv.nix`, `ci/` or `.github/workflows/` gets a review of its final diff from an agent that did not write it, before it reaches `main`.
- A change to `scripts/prepare-update.sh` or `.github/workflows/update.yml` lands first and is then proven by a run of `gh workflow run update.yml`. A change to `scripts/pull-main.sh`, `scripts/lib/pull-main.sh` or `nixosModules/deploy-unit.nix` is proven by `upgrade` on nixos-rog after its deploy ([Updater](docs/nixos-rog.md#updater)). A change to `scripts/self-deploy.sh`, `scripts/self-deploy-reboot.sh`, `scripts/lib/pull-main.sh`, `nixosModules/deploy-unit.nix` or `nixosModules/deploy-host.nix` is also proven by the `devbox-self-deploy` check ([Deploy test in a VM](docs/devbox.md#deploy-test-in-a-vm)).
- `nix fmt` runs `scripts/check-theme-drift.sh`, which fails on a fixed color in a tracked file. A color in new UI comes from `config.scheme` or `oruc.theme.ansi`; otherwise list the app under the fixed colors in [Theme](docs/architecture.md#theme).
- When a hook fails, fix the cause and commit again; a pre-push failure leaves the commit unpushed. `devenv test` runs the pre-push checks without a push. Outside the devenv shell, `scripts/check.sh --fix` formats a copy, copies the fixes back and runs `ci/checks.sh`.
- Print one configuration value with `scripts/eval.sh [--json] <attribute>`. A bare attribute is a path under nixos-rog's `config`; a flake attribute with `#` reaches another host. A value that is not a string needs `--json`.
- Before a new or changed package or overlay lands, prove it builds with `scripts/build.sh [ATTRIBUTE...]`. Each attribute is a flake attribute such as `.#nixosConfigurations.nixos-rog.pkgs.deskflow`; with none it builds nixos-rog's system. It builds from a copy of the checkout and prints each output path.
- Before deploying a new or changed systemd `script`, run it with `scripts/run-unit-on-rog.sh <unit>`; for a new or changed Home Manager user unit, add `--user`.
- Before changing power, fan or heat settings, read [Power and heat](docs/nixos-rog.md#power-and-heat). It names the one owner of each setting and the `scripts/thermal-test-rog.sh` CPU and GPU load test.
- For a change visible on screen, follow [Check a visual change](docs/nixos-rog.md#check-a-visual-change).
- Before changing Deskflow, keyboard keys, Plasma panels, a Plasma look or VS Code settings on nixos-rog, read [Deskflow](docs/nixos-rog.md#deskflow), [Keyboard keys](docs/nixos-rog.md#keyboard-keys), [Plasma panels](docs/nixos-rog.md#plasma-panels), [Plasma looks](docs/nixos-rog.md#plasma-looks) or [VS Code settings](docs/nixos-rog.md#vs-code-settings). To click in VS Code there, use [Drive VS Code](docs/nixos-rog.md#drive-vs-code).

# Nixpkgs

- `flake.lock` holds more than one nixpkgs node. Ours is the one the root input names: `jq -r '.nodes.root.inputs.nixpkgs as $n | "\($n) \(.nodes[$n].locked.rev)"' flake.lock`. llm-agents and nix-cachyos-kernel keep their own nixpkgs on purpose, so their binary caches still match.
- Fix a nixpkgs package with an overlay in `overlays/` (`overrideAttrs` with `patches` or `postPatch`). The module that needs an overlay imports its file in `nixpkgs.overlays` (`git grep -n 'overlays/' nixosModules` lists them), so extend the package's existing overlay or import the new file where the package is used. Fix a NixOS module with `disabledModules` plus the module from a second pinned nixpkgs input. Patching nixpkgs itself needs import from derivation, which `ci/checks.sh` forbids.
- A text edit in a build step fails the build when it changes nothing. Use `substituteInPlace --replace-fail`; after a `sed`, or a `--replace-quiet` where a release may use either of two forms, check the result with `grep`.

# Lookups

Look up a Nix name, hash or rebuild cause before you write it. The tools and the nixpkgs clone below are on nixos-desktop and nixos-rog, so run them directly. They read upstream nixpkgs, not `flake.lock`, so `scripts/eval.sh` stays the source for a value in this configuration. Claude Code also has a `nixos` MCP server that searches search.nixos.org.

- Option, package or `lib` name: `nix-search-tv print --indexes <nixos|home-manager|nixpkgs|noogle> | grep <word>`, then `nix-search-tv preview --indexes <index> --json <name>` for its type, default and declaration. Exit 1 means the name does not exist. plasma-manager options are not indexed.
- Source of a module at the locked revision: `scripts/eval.sh --json '.#nixosConfigurations.nixos-rog.pkgs.path'` prints nixpkgs' store path (without `--json` the script copies it to a new path). `scripts/eval.sh --json '.#nixosConfigurations.nixos-rog.options.<option path>.declarations'` prints the file that declares an option. `scripts/eval.sh '.#nixosConfigurations.nixos-rog._module.specialArgs.inputs.<input>.outPath'` prints another input's path, such as `home-manager`. The script evaluates on this host, so read the file directly.
- Upstream nixpkgs history: nixos-desktop and nixos-rog keep a clone of nixpkgs master in `/var/cache/nixpkgs`, fetched hourly on AC power (`nixosModules/nixpkgs-clone.nix`); `sudo systemctl start nixpkgs-clone` fetches it now. It follows upstream, not `flake.lock`, so use the bullet above for the locked revision.
- Source hash or fetcher block: `nix run nixpkgs#nurl -- --json <url> <rev>`.
- Draft of a new package with its vendor hash: `NIX_PATH=nixpkgs=$(nix eval --raw nixpkgs#path) nix run nixpkgs#nix-init -- --headless --url <url> --rev <tag> /tmp/draft.nix </dev/null`, then edit the draft.
- What an edit rebuilds or restarts: print the system `drvPath` with `scripts/eval.sh '.#nixosConfigurations.<host>.config.system.build.toplevel.drvPath'`, once from your checkout and once from the other commit. The script copies the checkout it lives in, so run it from a detached worktree of the other commit. Before the push, that is `git worktree add --detach <dir> origin/main`; after it, `scripts/affected-hosts.sh <old>..<sha>` prints both paths for each host, where `<sha>` is the pushed commit and `<old>` the `main` it landed on. Then run `nix run nixpkgs#nix-diff -- --color never --skip-already-compared <old.drv> <new.drv> | head -n 200 | cut -c1-300`.
- Which package prints an evaluation warning: `scripts/eval.sh --abort-on-warn '.#nixosConfigurations.<host>.config.system.build.toplevel.drvPath' 2>&1 | grep -o "while evaluating derivation '[^']*'" | tail -n 1`. The last match names the package; `ci/checks.sh` lists each distinct warning.
- Why a package is in the running system: `nix why-depends /run/current-system <store path>`.
- Which nixpkgs advance broke a build: in a copy of the checkout, because `npc` rewrites `flake.lock`, run `npc fetch`, then `npc bisect start --input nixpkgs nixos-unstable` and `npc bisect good|bad`, each as `nix run nixpkgs#npc -- <subcommand>`.
