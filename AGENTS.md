# Working rules

- Change `nixos-latitude` and `nixos-rog` only through this repository. `deploy.sh` builds from a copy of this checkout, so an edit to a host's `/etc/nixos` never reaches the system.
- Deploy every merged change to each host it affects without asking again, as [docs/deploy.md](docs/deploy.md#deploy-a-merged-commit) describes. A host is affected when its system `drvPath` differs between the change and its parent; `scripts/affected-hosts.sh <sha>` lists the affected hosts of a merged commit. Before you end a session that deployed, run `scripts/affected-hosts.sh --running`; it lists each host whose running system differs from `main`, such as one that was offline at the deploy. `./deploy.sh` does not reboot, so a kernel parameter takes effect at the next boot; the reboot rule for nixos-latitude is in [docs/nixos-latitude.md](docs/nixos-latitude.md#operation).
- Ask Omer only for a login, a greeter password (the SDDM login screen) or a judgement of what is on screen. A screenshot of the whole session (`scripts/screenshot-nixos-rog.sh OUTPUT.png`) needs no approval, but it captures whatever Omer has open, private pages included, so delete a shot of unrelated windows without describing it. A visual change takes the `--window` shot from [Check a visual change](docs/nixos-rog.md#check-a-visual-change), which opens a Ghostty window on Omer's screen, so ask first.
- [CONTEXT.md](CONTEXT.md) defines the domain terms (this PC, the laptop, login session, hybrid mode, integrated mode) and each host's SSH alias.
- When a request moves a setting from one place to another, such as "use nixos-rog's keyboard setup on nixos-latitude", state the source host, the target host and the repository the change lands in, in one sentence, before the first change or push. Ask which host only when the request names none and the change would apply to just one. Shared code goes in `nixosModules/` and `home-manager/`, and code for one host goes in `machines/<host>/` ([docs/architecture.md](docs/architecture.md#inventory)). The `drvPath` rule above decides which hosts to deploy.
- Before changing the machine record (`machines/`), login sessions, theme or Home Manager wiring, read [docs/architecture.md](docs/architecture.md). To move the kernel, an input or an app by hand, read [docs/updates.md](docs/updates.md). nixos-latitude's hardware facts and measured dead ends are in [docs/nixos-latitude.md](docs/nixos-latitude.md). Rollback, boot repair, a first nixos-latitude install, kernel-cache and Home Manager have guides listed in [README.md](README.md#docs).
- This repository is public. Write a placeholder such as `<lan-ip>` or `<tailnet-name>` for a LAN IP, a tailnet name, an Infisical ID or a token.
- nixos-rog's hourly updater squash-merges input and app moves to `main`, so `main` and `flake.lock` move often. Branch from a freshly fetched `origin/main` ([docs/nixos-rog.md](docs/nixos-rog.md#hourly-updater)).
- Add a package to a host only when Omer or a coding agent runs it by hand. Linters and formatters come from the dev shell in `tooling.nix`, which direnv loads on a host with Nix.

# Checks

fedora-desktop has no Nix, so these scripts run Nix on a copy of this checkout on nixos-rog. [README.md](README.md#everyday-commands) lists every script you run by hand.

- A PR that changes `pkgs/`, `overlays/` or `home-manager/modules/plasma-*.nix` gets a review of its final diff from an agent that did not write it, before `pr-land`.
- Before a commit, run `scripts/check-on-rog.sh --fix`. It formats, then runs CI's formatter check and `nix flake check` with import from derivation off. CI also evaluates `ci/cached-packages.nix` and runs `ci/unit-cycles.sh`; the script does not.
- Print one configuration value with `scripts/eval-on-rog.sh [--json] <attribute>`. A bare attribute is a path under nixos-rog's `config`; a flake attribute with `#` reaches another host. A value that is not a string needs `--json`.
- Before a new or changed package or overlay lands, prove it builds with `scripts/build-on-rog.sh [ATTRIBUTE...]`. Each attribute is a flake attribute such as `.#nixosConfigurations.nixos-rog.pkgs.deskflow`; with none it builds nixos-rog's system. It builds on nixos-rog from a copy of the checkout and prints each output path.
- Before deploying a new or changed systemd `script`, run it with `scripts/run-unit-on-rog.sh <unit>`.
- Before changing power, fan or heat settings, read [Power and heat](docs/nixos-rog.md#power-and-heat). It names the one owner of each setting and the `scripts/thermal-test-rog.sh` CPU and GPU load test.
- For a change visible on screen, follow [Check a visual change](docs/nixos-rog.md#check-a-visual-change).
- Before changing Deskflow, keyboard keys, Plasma panels, a Plasma look or VS Code settings on nixos-rog, read [Deskflow](docs/nixos-rog.md#deskflow), [Keyboard keys](docs/nixos-rog.md#keyboard-keys), [Plasma panels](docs/nixos-rog.md#plasma-panels), [Plasma looks](docs/nixos-rog.md#plasma-looks) or [VS Code settings](docs/nixos-rog.md#vs-code-settings). To click in VS Code there, use [Drive VS Code](docs/nixos-rog.md#drive-vs-code).

# Nixpkgs

- `flake.lock` holds more than one nixpkgs node. Ours is the one the root input names: `jq -r '.nodes.root.inputs.nixpkgs as $n | "\($n) \(.nodes[$n].locked.rev)"' flake.lock`. llm-agents and nix-cachyos-kernel keep their own nixpkgs on purpose, so their binary caches still match.
- Fix a nixpkgs package with an overlay in `overlays/` (`overrideAttrs` with `patches` or `postPatch`). The module that needs an overlay imports its file in `nixpkgs.overlays` (`git grep -n 'overlays/' nixosModules` lists them), so extend the package's existing overlay or import the new file where the package is used. Fix a NixOS module with `disabledModules` plus the module from a second pinned nixpkgs input. Patching nixpkgs itself needs import from derivation, which CI forbids.
- A package with a free licence that only this flake builds belongs in `ci/cached-packages.nix` ([docs/nixos-rog.md](docs/nixos-rog.md#cached-packages)), because the public cache holds no unfree build; otherwise each host compiles it.
- A text edit in a build step fails the build when it changes nothing. Use `substituteInPlace --replace-fail`; after a `sed`, or a `--replace-quiet` where a release may use either of two forms, check the result with `grep`.

# Lookups

Look up a Nix name, hash or rebuild cause before you write it. The tools run on nixos-rog; from fedora-desktop, quote the whole command, as in `ssh nixos-rog '<command>'`, so that `$(...)` expands on nixos-rog. They read upstream nixpkgs, not `flake.lock`, so `scripts/eval-on-rog.sh` stays the source for a value in this configuration. The login shell on nixos-rog is zsh, so an unmatched glob aborts the command; send a multi-line command as `ssh nixos-rog bash -s <<'EOF'`. Claude Code also has a `nixos` MCP server that searches search.nixos.org.

- Option, package or `lib` name: `nix-search-tv print --indexes <nixos|home-manager|nixpkgs|noogle> | grep <word>`, then `nix-search-tv preview --indexes <index> --json <name>` for its type, default and declaration. Exit 1 means the name does not exist. plasma-manager options are not indexed.
- Source of a module at the locked revision: `scripts/eval-on-rog.sh --json '.#nixosConfigurations.nixos-rog.pkgs.path'` prints nixpkgs' store path (without `--json` the script copies it to a new path). `scripts/eval-on-rog.sh --json '.#nixosConfigurations.nixos-rog.options.<option path>.declarations'` prints the file that declares an option. `scripts/eval-on-rog.sh '.#nixosConfigurations.nixos-rog._module.specialArgs.inputs.<input>.outPath'` prints another input's path, such as `home-manager`. Read the file with `ssh nixos-rog "sed -n 60,80p <file>"`.
- Upstream nixpkgs history: nixos-rog keeps a clone of nixpkgs master in `/var/cache/nixpkgs`, fetched hourly on AC power (`machines/nixos-rog/nixpkgs-clone.nix`). It follows upstream, not `flake.lock`, so use the bullet above for the locked revision.
- Source hash or fetcher block: `nix run nixpkgs#nurl -- --json <url> <rev>`.
- Draft of a new package with its vendor hash: `NIX_PATH=nixpkgs=$(nix eval --raw nixpkgs#path) nix run nixpkgs#nix-init -- --headless --url <url> --rev <tag> /tmp/draft.nix </dev/null`, then edit the draft.
- What an edit rebuilds or restarts: print the system `drvPath` with `scripts/eval-on-rog.sh '.#nixosConfigurations.<host>.config.system.build.toplevel.drvPath'`, once from your checkout and once from the other commit. The script copies the checkout it lives in, so run it from a detached worktree of the other commit. Before the merge, that is `git worktree add --detach <dir> origin/main`; after it, `scripts/affected-hosts.sh <sha>` prints both paths for each host, where `<sha>` is the merge commit. Then run `nix run nixpkgs#nix-diff -- --color never --skip-already-compared <old.drv> <new.drv> | head -n 200 | cut -c1-300` on nixos-rog.
- Which package prints an evaluation warning: `scripts/eval-on-rog.sh --abort-on-warn '.#nixosConfigurations.<host>.config.system.build.toplevel.drvPath' 2>&1 | grep -o "while evaluating derivation '[^']*'" | tail -n 1`. The last match names the package; `check-on-rog.sh` and CI list each distinct warning.
- Why a package is in the running system: `nix why-depends /run/current-system <store path>`.
- Which nixpkgs advance broke a build: in a copy of the checkout, because `npc` rewrites `flake.lock`, run `npc fetch`, then `npc bisect start --input nixpkgs nixos-unstable` and `npc bisect good|bad`, each as `nix run nixpkgs#npc -- <subcommand>`.
