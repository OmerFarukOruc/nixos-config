# Claude account tools

`claude-accounts` runs several Claude Code accounts on one machine at the same time, one config folder per account, and shows their usage and logins. It runs on nixos-desktop, nixos-rog and, under `oruc`, on risoluto-dev-1. Home Manager installs it with the other tools of `pkgs/claude-tools` (`home-manager/modules/claude-accounts.nix`). The account list `accounts.json` and the shared preferences `account-prefs.json` hold emails and organizations, so they stay in the private dotfiles checkout's `desktop/claude-code`; `CLAUDE_ACCOUNTS_DATA` names another folder.

## Layout

| Account | Folder | `CLAUDE_CONFIG_DIR` | Account config |
|---|---|---|---|
| The main account (named in `~/.claude/.claude-profile-name`; without that file, the accounts.json account its login matches, written there, else `main`) | `~/.claude` | unset | `~/.claude.json` |
| Every other account | `~/.claude-<folder>`, marked by a `.claude-profile` file | `~/.claude-<folder>` | `~/.claude-<folder>/.claude.json` |

An extra account's name is the content of its `.claude-profile` file, or `<folder>` when the file is empty; `add` and `rename` write the name into it. `rename` moves an idle account's folder to `~/.claude-<new name>`. While a session runs with the account, `rename` leaves the folder where it is, because the session keeps writing to the path in its `CLAUDE_CONFIG_DIR`. That folder still holds the old name's path, so `add` and `rename` put a new account with that name in `~/.claude-<name>-2` (or `-3`, and so on).

- Each machine logs in to each account on its own, with a browser login (setup-token logins cannot run Remote Control). Never copy a `.credentials.json` to another machine: Claude Code rotates the refresh token on use, so the first refresh on one machine logs the other out. For the same reason no tool of ours refreshes a token; `claude-usage` lets Claude Code refresh it (see Logins and usage).
- An email that belongs to several organizations, such as a personal Max plan and a Team seat, needs one account per organization, because a login holds one organization. After `add`, the Org column of `list` shows which organization the login picked; `personal` is the email's own organization.
- Each extra folder symlinks the entries in the script's `shared` array to `~/.claude`, so settings, skills, hooks, rules, plugins, themes, sessions (`projects`), rewind checkpoints (`file-history`), and plans are one copy for every account. A session resumed under another account keeps its session ID and numbers its checkpoints from that account's `file-history`, so a separate copy per account reuses checkpoint names and rewind can restore another account's file content.
- `history.jsonl` (the prompt history behind the up arrow) stays per account. Claude Code 2.1.292 never reads or writes it through a symlink, and its retention prune rewrites the file, which would break a hard link.
- `.credentials.json` and `.claude.json` stay per folder. Claude Code rotates the OAuth refresh token on use, so two accounts sharing one credentials file log each other out. `.claude.json` holds the account identity next to the MCP servers.
- `.claude.json` also holds preferences that some commands save per account, such as the `/focus` view (`briefTranscript`), so a new profile starts without them. Put a preference every account shares in `settings.json` when it has a key there and /config still shows its row, as `"viewMode": "focus"` does for focus view. `cc-setting KEY` shows whether a key has a `settings.json` key. Otherwise add the key and its value to `account-prefs.json`. That includes `workflowSizeGuideline`: it has a `settings.json` key, but /config hides "Dynamic workflow size" while a settings file sets it. `claude-accounts prefs` merges the file with `~/.claude.json` and every profile's `.claude.json`. A value changed in /config in any account goes into the file and every other account, and a value changed in the file goes into every account. When two sides changed one key to different values, it changes nothing for that key and prints the values on each run until they are equal. `desktop-sync.sh` runs it, and the hourly `desktop-sync-config.timer` on both hosts commits the file, so a change reaches the other host within about two hours.
- `claude-accounts.sh` makes `claude` a shell function and completes `claude-accounts`. It works in zsh and bash, and Home Manager's zsh sources it (`home-manager/modules/claude-accounts.nix`).

## Logins and usage

- `accounts.json` lists every account with the email and organization its login must show and the display name of the Brave profile that holds its claude.ai session. An account name means the same login on every device; the `~/.claude` account's name file says which one it is there (`own-team` on risoluto-dev-1, `work1` on nixos-rog).
- `login NAME` creates the account's folder when the device has none, runs `claude auth login --claudeai --email EMAIL` with `BROWSER=claude-login-browser`, which opens the authorize URL in the account's Brave profile, and then checks `claude auth status` against accounts.json. A login that picked the wrong organization fails with both values printed. `login NAME --on HOST` runs the same login on HOST in a tmux session there, opens its URL here, and tunnels the browser's redirect to the remote claude's `localhost` port with `ssh -L`. `login-window` is the widget's Log in button. Logins on other devices show in the cards because `remote_hosts` in accounts.json names, per device, the devices whose cache `claude-usage` reads over ssh. A device whose everyday key has a passphrase reads with `~/.ssh/id_ed25519_claude_usage`, which the target accepts only for `cat .cache/claude-usage/usage.json`: nixos-config `machines/nixos-rog` declares it for nixos-rog. `login-all --list` prints the accounts that are missing, logged out, or end within 5 days.
- `claude-usage`, which `claude-accounts` runs for the cards, writes each account's 5 h and 7 d use, reset times, login end and state to `~/.cache/claude-usage/usage.json` (`claude-usage.timer`, every 10 min). Its header comment says how it reads usage without refreshing a token. The Claude accounts widget, which nixos-config installs from `pkgs/claude-accounts-widget`, `claude-rotate` and `claude-limit-switch` read that file. `claude-accounts` prints one card per account, and the widget one row per account. Usage limits belong to the account, so each account appears once with the newest reading from any host, followed by one login line per host (`no login` means that host never logged in to it). `claude-accounts --json` adds this list as `combined`, and `claude-accounts --watch` redraws the cards every 30 s. A pace mark follows each percent: ▲ when the account uses the window faster than an even spread to the reset, ▽ when it has room to spare, ≈ within 5 points of even.
- `claude-rotate` opens each interactive `claude` with an account list (`claude-usage --pick`): every account here with its 5 h and 7 d bars and pace, the one with the most room under the cursor, and the highlighted account's windows and login below. Enter starts the highlighted account, 1-9 start a row, `r` checks every account's usage now, and `q` starts nothing; `CLAUDE_ACCOUNTS_PICK=0` starts on the account with the most room without the list. It starts each session on the chosen account and moves the session to the next account when its turn fails on a usage limit; the StopFailure hook `claude-code/hooks/rotate-on-limit.sh` tells it. When no account is free, it moves the session once another account's recorded limit ends, if that comes before its own account's. The `claude` function in `claude-accounts.sh` decides when it runs. `tests/claude-rotate-e2e.sh` checks the list with real accounts; no test covers a move or the wait ([Tests](#tests)).

## Invariants

Keep these true in every change:

- The main account's files stay in `~/.claude`. The default claude-desktop-extra profile and the IDE extensions read only that folder, and Claude Code finds `~/.claude.json` only with `CLAUDE_CONFIG_DIR` unset. Never run the main account with `CLAUDE_CONFIG_DIR=~/.claude`: that writes a second config, `~/.claude/.claude.json`, and a login there leaves `~/.claude.json` naming the old account, so `list` shows the wrong email. `list` marks the main account's links `split` while that file exists. Renaming the main account writes its name file; deleting it is refused.
- `sync_config` writes a profile's `.claude.json` only while no `claude` process runs with that profile, because a running session holds the MCP servers and onboarding keys in memory; only keeping an outside preference key was checked. `cmd_update` checks with `in_use`, and so does `cmd_delete`, because a running session writes its files back into a deleted folder. `prefs` is the exception: it writes the keys in `account-prefs.json` while sessions run, because a running session keeps a key written to its `.claude.json` from outside. To check that with the installed version, while a session runs with `~/.claude.json`:
  1. Add a probe key: `t=$(mktemp ~/.claude.json.XXXX) && jq '.zzProbe=1' ~/.claude.json > $t && chmod 600 $t && mv $t ~/.claude.json`.
  2. Use the session until `stat -c %y ~/.claude.json` shows a newer time, which means the session wrote the file.
  3. `jq .zzProbe ~/.claude.json` prints `1` when the session kept the key. If it prints `null`, `prefs` must skip accounts in use, as `sync_config` does.
  4. Remove the key the same way with `jq 'del(.zzProbe)'`.
- Before linking, `cmd_update` moves the files of a profile's own copy of a shared folder into `~/.claude` with `fold_dir`, also only while no session runs with that profile. A file `~/.claude` already has keeps its copy, and the profile's copy stays in `<folder>.unmerged` inside the profile.
- `sync_config` and `prefs` rewrite `.claude.json` only while they hold its lock directory `.claude.json.lock`, the one Claude Code holds while it writes the file (`claude-config-lock.sh`, 10 s wait). The helper breaks a lock nobody touched for 10 s, as Claude Code does, and never refreshes its own lock, because its holds are short. The directory stays empty, so Claude Code can break a lock of ours that a dead holder left; a holder removes the directory only while its inode and birth time are the ones it recorded after `mkdir`, so a lock another process took is not removed. `prefs` needs one lock per account file and takes them all or none: it waits half a second for each, and when one is held it releases the others and tries again with a growing pause, so no lock it holds ages toward Claude Code's 10 s bound while it waits. A held lock fails the call with "config: not changed" and changes no file. A stale break leaves an empty `.claude.json.lock.break` beside the config, because removing it while another run waits on it would let two runs break at once.
- `sync_config` copies three things from `~/.claude.json`: `mcpServers`, the onboarding keys, and every folder with `hasTrustDialogAccepted`. Then it writes the values in `account-prefs.json`, so a new account starts with them. `claude auth login` leaves the onboarding keys unset, and without them the first interactive start reruns the first-run wizard, which asks for a login method again.
- Delete runs `rm -rf` on the profile folder. `rm` removes the symlinks and never follows them, so `~/.claude` is untouched.
- A claude-desktop-extra profile NAME runs Claude Code in `~/.claude-NAME`, so an account with a desktop profile keeps its folder equal to its name. After renaming such an account, run `claude-desktop --delete-profile=OLD`, move `~/.config/Claude-OLD` to `~/.config/Claude-NEW`, and run `claude-desktop --create-profile=NEW`.
- A write through the `settings.json` symlink keeps the link. This was checked on 26-09-2026 with Claude Code 2.1.283 by changing a setting with `/config` in a profile. Recheck it after a major Claude Code update: `list` shows `broken` in the Links column when a link was replaced.

## Changing the script

1. Edit `bin/claude-accounts`. When the `claude` function needs new behaviour, add a subcommand to the script and call it from `claude-accounts.sh`; keep paths and names out of the shell config.
2. Run `shellcheck -S warning bin/claude-accounts bin/claude-login-browser claude-accounts.sh` and `ruff check bin`; `nix fmt` checks only `*.sh` files. Both must print nothing.
3. Deploy, then run the script against the real accounts. The change is done when every one of these holds:
   - `claude-accounts list` shows every account with its email and `ok` links.
   - `claude-accounts update` prints `config: synced` for each profile with no running session and exits 0.
   - `add tmp-x </dev/null`, then removing one link in `~/.claude-tmp-x`, makes `list` show `broken` for it; `delete tmp-x --yes` then removes the folder.
   - Replacing the `file-history` link in `~/.claude-tmp-x` with a real folder that holds one new file and one file `~/.claude/file-history` already has, then `update`, moves the new file, keeps the other in `file-history.unmerged`, and restores the link. `delete tmp-x --yes` refuses while a process named `claude` runs with `CLAUDE_CONFIG_DIR=$HOME/.claude-tmp-x`.
   - While that process runs, `rename tmp-x tmp-y` writes `tmp-y` into the marker, `names` and `dir tmp-y` use `tmp-y`, and `add tmp-x </dev/null` creates `~/.claude-tmp-x-2` for a new `tmp-x`. With the process stopped, `rename tmp-y tmp-z` moves the folder to `~/.claude-tmp-z`.
   - In a terminal, `claude --account <profile> auth status` prints that account's email, and `claude --account <main name> auth status` the main account's, and `claude --account nope` fails with `no account 'nope'`.
   - `login-all --list` prints exactly the accounts that the cards show as missing, logged out or ending within 5 days. After a change to `login`, log in to one account with it and check that the Brave profile from accounts.json opened and that `list` shows the expected organization.
   - The cards render in a terminal: `tmux new-session -d -s cpt -x 110 -y 40 claude-accounts --watch`, then `tmux capture-pane -p -t cpt` shows one card per account and a login line per host.
4. Land the change on nixos-config `main` (`AGENTS.md`).

## Tests

The end-to-end tests in `tests/` run on risoluto-dev-1 against real Claude accounts and a real herdr server, each in its own herdr session or tmux server. Run them from a nixos-config checkout against the installed tools, for example `pkgs/claude-tools/tests/orch-e2e.sh "$(dirname "$(readlink -f "$(command -v orch-watch)")")"`; each prints `PASS` and exits 0.

- `claude-limit-switch-e2e.sh`: a switch, a scan that leaves an agent without a limit alone, the restore after a server stop, and `resume`.
- `claude-rotate-e2e.sh`: the account picker and the exit codes of claude-rotate.
- `orch-e2e.sh`: agent-start, agent-stop, agent-peek, orch-notify and orch-watch.

The picker step reads a usage cache and a `limits.json` that the test writes from the real cache with changed numbers, so it proves how the picker shows and orders those records, not how `claude-usage` and `claude-rotate` write them.

The dotfiles checkout's `desktop/bin/tests/desktop-sync-e2e.sh` runs the installed `claude-accounts prefs` and `claude-config-lock.sh` against scratch homes, so a change to either needs that test too: `~/Desktop/workspace/dotfiles/desktop/bin/tests/desktop-sync-e2e.sh` after the deploy.

No test covers these, because a run cannot reach them for real:

- a move after a real usage limit, in claude-rotate and claude-limit-switch, with the session's memory kept across the move;
- the limit parser: the reset time and reason that `scan` writes to `limits.json`;
- the StopFailure hook handshake of claude-rotate (`$XDG_RUNTIME_DIR/claude-rotate/ID-PID.json`), including a nested `claude -p` whose limit must leave the session alone;
- a session that waits while no account is free;
- agent-start's cleanup when herdr refuses the brief;
- the lock release of `prefs` and `update` when TERM ends them.
