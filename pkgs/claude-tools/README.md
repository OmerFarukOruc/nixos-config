# Claude account tools

`claude-tools` runs several Claude Code accounts on one machine at the same time, one config folder per account, shows their usage and logins, and keeps Claude agents in herdr running across usage limits. It runs on nixos-desktop and nixos-rog under `oruc`, and on devbox under `omer`. Home Manager installs it (`home-manager/modules/claude-tools.nix`). It reads the account list `accounts.json` and the shared preferences `account-prefs.json` from `~/.config/claude-tools`, where `home-manager/modules/claude-tools.nix` links them: `accounts.json` from the sops key `claude-tools-accounts`, because it holds emails and organizations, and `account-prefs.json` from an attribute set in that module. `CLAUDE_TOOLS_DATA` names another folder.

`claude-tools --help` lists the commands, and each command prints its own `--help`, except `rotate` and `accounts`, which pass their arguments on: `claude-tools rotate --help` prints `claude --help`, and `claude-tools accounts help` lists the account commands.

| Command | What it does |
|---|---|
| `accounts` | account folders, links, preferences and logins (`libexec/claude-accounts`, bash) |
| `usage` | the usage cards, the cache, `--order` |
| `rotate` | runs `claude` with the account picker and moves a session at a usage limit |
| `limit-switch` | moves named Claude agents at a usage limit and starts every recorded agent again after a herdr restart |
| `agent start\|stop\|watch` | named Claude, Codex or opencode agents in herdr tabs, and the lines that wake their orchestrator |

## Package layout

- `src/claude_tools`: the Python package, stdlib only. `cli.py` builds the argument parser from each command module's `add_parser`, and prints the completion words from it. `commands/` holds one module per command with its workflow, and the modules beside it hold what several commands share: `settings.py` (paths and environment, read once per run), `accounts.py`, `usage.py` (reading and caching usage), `selection.py` (the account order), `display.py` (the display rules of a usage window: reset minute, tone, pace, spans), `terminal.py` and `picker.py` (cards and the account list), `herdr.py` (the herdr CLI and its socket), `agents.py` (Claude, codex and opencode processes in herdr panes), `watch.py` (`agent watch`), `limits.py`, `store.py` (JSON files, file locks and the clock) and `errors.py` (the errors a command reports).
- `libexec/`: `claude-accounts`, which `claude-tools accounts` runs with the rest of its arguments; `login-browser`, the `BROWSER` of a login; `config-lock.sh`, the `.claude.json` lock that `claude-accounts` sources. They stay bash because the lock reads a file's birth time with `stat`, which Python 3.14 cannot read.
- `share/claude-tools.sh`: the `claude` shell function and the completion of `claude-tools`, for zsh and bash. Home Manager's zsh sources it.
- `pkgs/claude-tools.nix` builds the package with `buildPythonApplication` and writes the store paths in place of `@libexec@` in `settings.py` and of `@bin@` in `claude-accounts` and `claude-tools.sh`.
- The package holds no comments or docstrings, only shellcheck directives beside the lines they cover: facts that are not usage live in this README, usage lives in `--help`, and lint settings live in `ruff.toml` and `.shellcheckrc`.

## Accounts

| Account | Folder | `CLAUDE_CONFIG_DIR` | Account config |
|---|---|---|---|
| The main account (named in `~/.claude/.claude-profile-name`; without that file, the accounts.json account its login matches, written there, else `main`) | `~/.claude` | unset | `~/.claude.json` |
| Every other account | `~/.claude-<folder>`, marked by a `.claude-profile` file | `~/.claude-<folder>` | `~/.claude-<folder>/.claude.json` |

An extra account's name is the content of its `.claude-profile` file, or `<folder>` when the file is empty; `add` and `rename` write the name into it. `rename` moves an idle account's folder to `~/.claude-<new name>`. While a session runs with the account, `rename` leaves the folder where it is, because the session keeps writing to the path in its `CLAUDE_CONFIG_DIR`. That folder still holds the old name's path, so `add` and `rename` put a new account with that name in `~/.claude-<name>-2` (or `-3`, and so on).

- Each machine logs in to each account on its own, with a browser login (setup-token logins cannot run Remote Control). Never copy a `.credentials.json` to another machine: Claude Code rotates the refresh token on use, so the first refresh on one machine logs the other out. For the same reason no tool of ours refreshes a token (Usage).
- An email that belongs to several organizations, such as a personal Max plan and a Team seat, needs one account per organization, because a login holds one organization. After `add`, the Org column of `list` shows which organization the login picked; `personal` is the email's own organization. The plan column adds the usage tier (5x, 20x), which only the credentials file holds, as `rateLimitTier`.
- Each extra folder symlinks the entries in the script's `shared` array to `~/.claude`, so settings, skills, hooks, rules, plugins, themes, transcripts (`projects`), rewind checkpoints (`file-history`), plans, and the list of running sessions (`sessions`) are one copy for every account. A session resumed under another account keeps its session ID and numbers its checkpoints from that account's `file-history`, so a separate copy per account reuses checkpoint names and rewind can restore another account's file content. Claude Code creates `projects`, `plans`, `file-history` and `sessions` in `~/.claude` only when the main account runs, and a profile cannot create them through its link, so `add` and `update` create them when they are missing; without them a profile's sessions are never saved and `--resume` finds nothing. `list` shows `broken` for a link that points at nothing.
- `ListAgents` and `SendMessage` find only the sessions whose file is in their own config folder's `sessions/`, one `<pid>.json` per running session, so a shared `sessions` lets an agent on one account list and message an agent on another. Claude Code does not support this: [anthropics/claude-code#105426](https://github.com/anthropics/claude-code/issues/105426) asks for cross-account messaging. Checked on 25-11-2026 with Claude Code 2.1.331: `ListAgents` lists an agent on another account, and `SendMessage` reaches it, only while that account's `sessions` links to `~/.claude/sessions`.
- `history.jsonl` (the prompt history behind the up arrow) stays per account. Claude Code 2.1.292 never reads or writes it through a symlink, and its retention prune rewrites the file, which would break a hard link.
- `.credentials.json` and `.claude.json` stay per folder. Claude Code rotates the OAuth refresh token on use, so two accounts sharing one credentials file log each other out. `.claude.json` holds the account identity next to the MCP servers.
- `.claude.json` also holds preferences that some commands save per account, such as the `/focus` view (`briefTranscript`), so a new profile starts without them. Put a preference every account shares in `settings.json` when it has a key there, as `"viewMode": "focus"` does for focus view, together with `"tui": "fullscreen"`, which focus view needs and `workflowSizeGuideline` does for the dynamic workflow size; /config may hide a row while a settings file sets its key, so change such a value in the settings file. `cc-setting KEY` shows whether a key has a `settings.json` key. Otherwise add the key and its value to the `account-prefs.json` attribute set in `home-manager/modules/claude-tools.nix`, as `leftArrowOpensAgents` is. `claude-tools accounts prefs` writes those values into `~/.claude.json` and every profile's `.claude.json`, and each Home Manager switch runs it. A value changed in /config stays in that one account until the next switch writes the declared value back.
- `claude-tools.sh` makes `claude` a shell function: `claude --account NAME` runs one session on NAME, and an interactive `claude` in a terminal without `CLAUDE_CONFIG_DIR`, `CLAUDE_TOOLS_ROTATE_ID` or `CLAUDE_TOOLS_PLAIN` runs `claude-tools rotate`.

## Logins

- `accounts.json` comes from the `claude-tools-accounts` key of `secrets/agents.yaml`, because it holds account emails and organizations and this repository is public; sops-nix decrypts it for the user and `home-manager/modules/claude-tools.nix` links it into `~/.config/claude-tools`. Edit it with `sops` as `docs/devbox.md` (Network and secrets) describes, then switch each host. It lists every account with the email and organization its login must show and the display name of the Brave profile that holds its claude.ai session. An account name means the same login on every device; the `~/.claude` account's name file says which one it is there (`own-team` on devbox, `work1` on nixos-rog).
- `accounts login NAME` creates the account's folder when the device has none, runs `claude auth login --claudeai --email EMAIL` with `BROWSER=libexec/claude-tools/login-browser`, and then checks `claude auth status` against accounts.json. A login that picked the wrong organization fails with both values printed and is logged out again.
- `login-browser` opens the authorize URL in the Brave profile whose display name is `CLAUDE_TOOLS_LOGIN_BRAVE_PROFILE`, so the claude.ai session of that profile signs in; unset or empty opens Brave's last profile. Each device resolves the name to its own profile folder through the browser's `Local State` file (Brave is brave-origin on nixos-desktop and nixos-rog). A name the device has no profile for gets a new profile in the folder `Claude <name as a slug>`: its `Preferences` file names it before Brave first opens it, and Brave takes that name into its profile list (checked on 19-10-2026 with brave-origin and a scratch `--user-data-dir`). An existing folder is never written. With `CLAUDE_TOOLS_LOGIN_URL_FILE` set, it writes the URL to that file and opens nothing.
- `login NAME --on HOST` runs the same login on HOST in a tmux session there, under `timeout --foreground`, because without `--foreground` claude stops on its first terminal read (state T) before it prints the URL. The remote `login-browser` writes the URL to a file; this device opens it and tunnels the browser's redirect to the remote claude's `localhost` port with `ssh -L`.
- `login-window` is the widget's Log in button. It runs `login` in a new Ghostty or Konsole window with `~/.local/bin` on `PATH`, because plasmashell, which starts it, has no `~/.local/bin` on `PATH`, where `claude` lives on two hosts.
- `login-all --list` prints the accounts that are missing, logged out, or end within 5 days; `login-all` logs in to each of them.

## Usage

- `claude-tools usage`, which `claude-tools accounts` without a command runs for the cards, writes each account's 5 h and 7 d use, reset times, login end and state to `~/.cache/claude-tools/usage.json` (`claude-tools-usage.timer`, every 10 min). `claude-tools` adds `~/.local/bin` to `PATH` before any command, for the same plasmashell reason as `login-window`, because the widget runs it and `rotate` and `limit-switch` probe accounts in the same process. It also drops the `bin` of its own interpreter, which the `buildPythonApplication` wrapper puts first on `PATH`, so the `claude` it starts finds the profile `python3` from `pkgs/agent-python.nix` instead of the plain one.
- It never refreshes a token. While an account's access token stays valid for more than 5 min, it reads the usage endpoint with that token. Otherwise, and when the endpoint answers 401, it runs a one-turn `claude -p` on haiku in `~/.cache/claude-tools/probe` and reads the `rate_limit_event`, so Claude Code refreshes the token itself and writes the new one to its own credentials file. Only the probe's `result` event and its stderr name a failure, because its `init` event lists commands such as `/login`. A failed reading keeps the last numbers and marks them stale. It checks up to 4 accounts at once, and the remote caches beside them. With `--max-age`, an account read within that age keeps its reading. `updated` in the cache is the start of the run, or the check time of the oldest reading the run reused without checking, such as one within `--max-age` or one whose check missed the deadline; a failed check's stale reading does not count, so a failing account does not make every `--max-age` caller check again. A run with `--account` that leaves an account out leaves `updated` as it was.
- Logins on other devices show in the cards because `remote_hosts` in accounts.json names, per device, the devices whose cache it reads over ssh. A device whose everyday key has a passphrase reads with `~/.ssh/id_ed25519_claude_usage`, which the target accepts only for `cat .cache/claude-tools/usage.json`: nixos-config `machines/nixos-rog/claude-tools-usage-read.nix` declares it for nixos-rog.
- The cards show one card per account in accounts.json, and the widget (`pkgs/claude-accounts-widget`) one row per account in accounts.json; an account a host has that accounts.json does not list does not appear, and the widget's login badge and best account ignore it too. `usage`, `rotate`, `limit-switch` and `agent start` skip such a folder as well (`Accounts.usable` in `accounts.py`), so a dropped account is neither read nor chosen, while `limit-switch` still moves an agent that runs on it to a listed account. `accounts list` and `accounts dirs` still show the folder, and `accounts delete` removes it. The widget's best account is the first of `usage --order` (the `order` list of `usage --json`), the one `rotate` would start on. Usage limits belong to the account, so each account appears once with the newest reading from any host, a fresh one before a stale one, followed by one login line per host (`no login` means that host never logged in to it). `usage --json` adds this list as `combined`, and `usage --watch` redraws the cards every 30 s. A pace mark follows each percent: ▲ when the account uses the window faster than an even spread to the reset, ▽ when it has room to spare, ≈ within 5 points of even. `usage --json` rounds every `resets_at` of `accounts` and `combined` to the nearest minute, because the API's reset times sit a fraction of a second either side of the full minute, and adds finished display values to each window there: `tone` (`green`, `amber` from 70%, `red` from 90%), `pace` (points ahead of an even spread, rounded) with `pace_state` (`ahead`, `behind`, `even`, within 5 points) and `pace_tone` (`amber` ahead, `red` from 20 points ahead, `green` behind, `dim` even), `reset_in` (`now` or a span such as `2h 53m`) and `reset_clock` (`HH:MM`, with the weekday from 1 d ahead), and `login_left` next to each `login_expires_at`. These rules live in `display.py`; the cards and the widget print the fields and compute nothing of their own, so both show the same minute.

## Rotation

- `claude-tools rotate` opens each interactive `claude` with an account list: every account in accounts.json with its 5 h and 7 d bars and pace, best first, with the reason for each place, and the highlighted account's windows and login below. Enter starts the highlighted account, 1-9 start a row, `r` checks every account's usage now and opens the list again, and `q` starts nothing. Accounts logged out on this host, and accounts this host has no folder for, are listed with their `accounts login` command but cannot be picked. A list that fails to open starts the recommended account.
- `usage --order` prints the same order. Every account follows one rule, and its plan only scales its room, so a 20x account has 4 times the room of a 5x account. Two burn rates measure our use: the 5 h rate sums the use per hour of every running 5 h window, at least one 5x window spent evenly over 5 h, and the weekly rate sums the use per hour of every weekly window that has run for at least 5 h, at least one 5x week spent evenly. An account lasts until its 5 h room (up to 90%) runs out at the 5 h rate or its weekly room (up to 95%) runs out at the weekly rate, whichever comes first. A window counts only while it runs and only when its room runs out before the window's own reset, so a window that has not started, has no limit, or resets first does not stop the account. It comes first when the weekly rate could not spend its weekly room before the weekly reset, because that room would otherwise go unused; inside that group, the accounts that last to their 5 h reset go before the others, then the soonest weekly reset goes first. Next come the accounts that last to their 5 h reset, or for 5 h when no 5 h window runs, soonest weekly reset first, so the room that expires first is spent first. After them, under the picker's "reaches a limit before its 5h reset" line, come the accounts that would reach a limit first, the one that lasts longest first, with the window that runs out first in the reason, so a move does not land next to a limit. Accounts held back after a limit, at 90% of 5 h or 95% of 7 d, or without a reading go last. A per-model weekly limit, such as Fable's, blocks only sessions on that model, so only an order for that model puts the account last, or leaves it out of the list `usage --order` prints: `usage --order` and the `order` of `usage --json` (`--model`, else `ANTHROPIC_MODEL`, else `model` in `~/.claude/settings.json`), the picker of a session whose model `rotate` knows (the same sources), and a move after that model's limit. A model matches a limit when the limit's first word other than `Claude`, such as `Fable`, is part of the model name, such as `claude-fable-5-2`. For a session on another model, the picker shows such a hold as a note, such as `Fable held for 1d 9h`.
- A new session or agent starts on the first account of the start order, which `rotate`'s list, `usage --order`, the `order` of `usage --json` and `agent start` without `--account` use. Among the accounts nothing blocks, it puts two rules before the order above. First, an account whose week runs more than 5 points ahead of an even spread to its weekly reset (the ▲ mark of the cards) goes after the others, so new work does not go to an account that is burning its week fast while its reset is still far. An account that is not ahead goes after them too once it has more than 1 open session per plan unit more than the emptiest account that is ahead, so a single slow account does not take every new agent. Second, the account with the fewest open Claude sessions for its plan goes first, a 20x account counting its sessions at a quarter, so starts made one after another fill the accounts in turn. The open sessions are the `claude` processes on a terminal whose `CLAUDE_CONFIG_DIR` is the account's, idle ones included. Every start through `rotate` or `agent start`, with or without a chosen account, and every move to another account records its pick in `~/.local/state/claude-tools/picks.json`, under a lock that the pick itself also holds, and a pick counts as one more open session on its account until that account has gained a `claude` process since the pick, or for at most 2 min, so starts and moves in the same few seconds spread too. The list holds its recommended account's pick while it is open; picking another account moves the pick there, and `q` drops it. `agent start` drops its pick when Claude does not start. The count is a difference of process counts, so for up to those 2 min a pick can count twice, when a session on its account exits as its process starts, or not at all, when another start on that account gains the process first; a start that fails some other way, or a move that does not happen, keeps its pick for the 2 min. A restore of an agent that does not run under `rotate` records no pick. The order above then breaks ties. A 5 h window whose reset has passed counts as empty in every order, because a reading of that window describes the window that ended. The list draws its "reaches a limit before its 5h reset" line only above a run of such accounts that ends the startable rows. A move after a limit uses the start order as well.
- `rotate` and `limit-switch` choose the next account the same way (`selection.py`). After a usage limit, `hold_limit` holds the account back until the reset that the limit message names. A model limit ("You've hit your Fable limit · resets Nov 21, 6am (Europe/Istanbul)"; the model's name must start with a capital, so a lowercase word such as "usage" never becomes a model hold that blocks nothing) holds only that model on the account, under the key `ACCOUNT:MODEL`, such as `work2-team:Fable`; a session, 5-hour or weekly limit holds the whole account under its name. A message without a reset time holds until the reset of a full window in a reading taken then (the 7 d or 5 h window for a whole-account hold, that model's window for a model limit), else for 1 h. An account accounts.json does not list gets no reading, so it is held for 1 h. A reset time more than one window ahead (5 h for a session limit, 7 d for a weekly or model one) belongs to an old message, so it holds nothing. The holds live in one file, `~/.local/state/claude-tools/limits.json`, written under a lock, with ended holds dropped on each write. A new hold replaces the earlier one under the same key, because the newest limit message is the latest word, while a model hold and a whole-account hold on one account stay side by side. The move looks for an account with room on the model the session last ran, read from its transcript, else the model of the limit message, and resumes the session with that model, so a model chosen with `/model` survives the move. `next_account` then reads the usage of every account that is not held back for the model in question and was not read in the last minute, with a 2 min wait budget for accounts that already have a cached reading, and returns the first of the start order that nothing blocks, recording it in `picks.json` unless it is the account the session already runs on. An unfinished check keeps its last reading; accounts without a cached reading must finish first and can exceed that budget.
- `rotate` passes every argument to `claude`. It reads `claude --help` once per installed binary, because it costs a node start, to learn which options take values and which words are subcommands; a subcommand, `-p`, `--version`, `--help` or a run without a terminal runs plain `claude`.
- It starts each session on the chosen account and moves the session to the next account when its turn fails on a usage limit: the StopFailure hook `libexec/rotate-on-limit`, which `home-manager/modules/claude-tools.nix` registers with the matcher `rate_limit`, writes the hook input to `$XDG_RUNTIME_DIR/claude-tools/rotate/ID-PID.json`, which carries the limit message as `last_assistant_message`. ID is the `CLAUDE_TOOLS_ROTATE_ID` that `rotate` gives its Claude process, and PID is the nearest Claude process above the hook, so a `claude -p` started inside the session inherits the ID but not the PID, and its limit leaves the session alone. A Claude Code session without `CLAUDE_TOOLS_ROTATE_ID`, such as a herdr agent, writes nothing. `rotate` holds the account, stops the session and resumes it with `--resume` on the next account. The resume command keeps the other arguments but not the session flags (`--resume`, `--continue`, `--session-id`, `--fork-session`, `--from-pr`) nor `--worktree` and `--tmux` with their values, and the resumed session starts in the folder the StopFailure hook reports as its `cwd`, so a session started with `--worktree`, or one that moved into a worktree, continues in that folder instead of a new git worktree. When no account is free, it waits until the first time any account, its own included, leaves the blocked group, else 1 h, and then resumes the session on the best account, its own one too when that limit has reset. A prompt typed into the session after the limit cancels the move and the wait; a `!` command does not, because it sends no turn to the model.

## Limit switch

`claude-tools limit-switch scan` keeps Claude agents in herdr running; `claude-tools-limit-switch.timer` runs it every minute on devbox.

- A scan first restores, then switches each named idle Claude agent whose session transcript ends in Claude Code's usage limit error: the last assistant entry has `isApiErrorMessage` and `apiError` `usage_limit_reached`, and its text gives the reset time ("You've hit your 5-hour limit · resets ..." since Claude Code 2.1.312, "session limit" before). The screen alone never moves an agent, because an agent can print the same sentence when it quotes a log or a test. The hold counts the reset from the time of that entry. A switch types `/exit` in the agent's pane, sets `CLAUDE_CONFIG_DIR` there, starts Claude like `claude --resume <session>` with its other old arguments under the same agent name, and tells the agent to continue. The resume adds `--dangerously-skip-permissions`, so an agent never stops at a permission prompt after a switch. It adds nothing to an agent that was started with `--settings` or `--permission-mode` and without `--allow-dangerously-skip-permissions`, because that flag turns the session into bypass mode, so such an agent keeps its own permission settings, as the Status Lantern audit agent does. The accounts share `~/.claude/projects`, so `claude --resume <session>` continues the same conversation under another account. A scan holds the account and moves the agent to `next_account`. When that is the agent's own account, because its limit has reset, the scan only sends the resume message.
- `~/.config/claude-tools/resume/NAME` replaces the resume message for agent NAME. `--resume` brings back a fixed-interval `/loop` but not a self-paced one or a Monitor, so an agent that runs them needs a message that checks CronList first (`agents/reference/unattended-agents.md`). With a scheduled task, `/exit` opens "Background work is running". Its first choice "Exit and stop tasks" deletes a session `/loop`, so `--resume` no longer finds it (Claude Code 2.1.329), while a SIGHUP ends Claude, stops its background shell tasks and keeps the loop for `--resume`. So the switch sends SIGHUP to the Claude process when the screen shows the dialog's selected first choice. For a Claude process of another user, which the signal cannot reach, it presses Enter on that choice instead, and the loop ends with the process.
- herdr itself resumes Claude as plain `claude --resume`, without the flag and the account (`agents/reference/headless-clis/herdr.md`), so its own restore is off. Each scan records every Claude, Codex and opencode agent in herdr that reports a session, named or not, together with the server process and the boot ID in `agents.json`. An agent without a herdr name is recorded as `pane-<pane id>`, such as `pane-w34-p1` for pane `w34:p1`; `agent start` refuses a name that starts with `pane-`, and the scan skips an agent named that way. When the scan cannot read the process of an agent it recorded before, it keeps the last record. For opencode the record keeps the `OPENCODE_CONFIG*` variables of the agent's process. For Claude the record keeps the account, the arguments, whether `rotate` started it (`CLAUDE_TOOLS_ROTATE_ID` in its environment), and the model of its last assistant entry in the transcript, because a `/model` choice is in no argument and the Home Manager switch at boot resets the default model. When the next scan finds a different server process, it starts each recorded agent that is missing in its old pane or a new workspace and sends it the resume message: a Claude agent like `claude --resume <session>` with its account and with `--model` set to the recorded model when its own `--model` names another one; a named Claude agent with the same flag rule as a switch, and an unnamed one with its own flags only; one that `rotate` started through `rotate` again, which starts on the recorded account when `CLAUDE_TOOLS_START_ACCOUNT` names it and moves it at a limit as before; a Codex agent like `codex resume <session>` with its options and the `CODEX_HOME` of its process, without its prompt and its session choice (`codex resume --help` names the options that take a value); an opencode agent like `opencode --session <session>` with its recorded options and `OPENCODE_CONFIG*` variables, without `--prompt` and `--continue`. The restore starts an unnamed agent under its `pane-` name, then clears the name with `herdr agent rename NAME --clear` before it sends the resume message, so the agent stays out of the switch. A recorded agent counts as running when a live agent reports its session, or, for a named one, has its name; a different agent in its old pane does not count, and the restore then opens a new workspace. When the agent started but the resume message did not arrive, the next try after 5 minutes sends only the message. The default resume message says whether the host rebooted (the boot ID changed) or only the herdr server restarted, that background tasks, Monitors, subagents and self-paced loops have ended, and that the agent checks what a cut-off command already did before it runs it again. An agent that is missing while the same server runs was ended on purpose; the record keeps it under `ended` with its last session for 30 days, and only `resume NAME` starts it again, the same way. `resume` restores first, because after a server restart the other missing agents need the restore, and the record would otherwise mark them as ended. When no server runs, a scan starts it (`herdr-default.service` for the default session).
- A start waits until the pane's shell runs typed input: in a folder with an `.envrc` the shell first loads direnv, and text typed during that load shows on screen but never runs. A start that fails closes the workspace it made.
- A scan skips an agent for 5 min after a move it tried, and a restore waits 5 min after a failed start, because the transcript keeps the old limit error as its last reply until the agent answers, and a scan every minute would otherwise try again on each run.

## Agents and the orchestrator

- `agent start NAME --cwd DIR` opens a tab named NAME in the caller's workspace with `--no-focus`, so the view of whoever looks at herdr stays where it is. A Claude agent without `--account` starts on the first account of the start order (Rotation) for its `--model`, else `model` in `~/.claude/settings.json`, and the command prints the account on stderr. It leaves out the caller's `ANTHROPIC_MODEL`, because the agent's pane gets its environment from the herdr server, not from the caller. When every account is blocked, or the order cannot be read, it starts on the caller's account and says so. With `CLAUDE_TOOLS_HERDR_SESSION` the tab opens in that session's own workspace, because the caller's pane id belongs to its own session. The brief goes as one prompt that names the file, so a long brief never goes through argv. herdr refuses the prompt with `agent_not_ready` while Claude is still booting, so the start sends it again every second for 60 s; a screen that shows the folder trust question gets Down and Enter (herdr answers a prompt at that question with `agent_blocked`, which the start treats the same way), and any other `agent_blocked` screen, or 60 s without a taken prompt, fails the start with the last 400 characters of the screen. The resume message that `limit-switch` sends after a switch or a restore goes out the same way. `--permission-mode` waits until the footer shows the mode before the brief goes out, because a mode switched by keypresses after start raced the brief once. A name whose agent just exited is waited for, since herdr frees it a moment later. When any step fails after the tab exists, the agent that started is stopped and the tab is closed, so the same command can run again.
- `agent stop NAME` refuses, with exit 1, while herdr shows the agent `working` or `blocked` at a question or approval, and prints the `herdr agent read` and `herdr agent wait --until idle --until done` commands for the session it uses, because an orchestrator that stopped an agent after its done message cut off the answer it was writing to Omer. `--force` cuts the agent off on purpose. Every stop of a claude agent presses Esc and then Ctrl+C before it types `/exit`, because Claude Code puts an interrupted prompt back into the input box, and `/exit` typed after it was sent as part of that prompt.
- `agent start NAME --kind opencode --agent AGENT` starts opencode's TUI with `--standalone` and `OPENCODE_CONFIG_CONTENT={"default_agent": AGENT}`, because the TUI has no model or agent flag and only a server it starts itself reads that variable. The agent file sets the model and the permissions, so `--agent` is required and `--account`, `--model`, `--effort` and `--permission-mode` are refused. Before the tab opens, `opencode debug agents` run in `--cwd` and in an empty folder must both list AGENT with the same mode, model, permissions and system prompt, because opencode starts its unrestricted `build` agent for an unknown name and appends a project's permission rules to the global ones. opencode 2.4.1 leaves the agents of its config folder out of that list in some runs (2 of 15, 5 of 15 and 1 of 8 runs in three batches on devbox, 2026-11-24), so claude-tools reads each list up to 3 times before it counts AGENT as missing. The TUI is a separate opencode process, so after the start claude-tools waits up to 30 s for its footer to name the agent, such as `E2e-Review` for `e2e-review`, presses Esc once when opencode's "What's new" dialog covers it, and fails the start, closing the tab, when the footer names no such agent. The agent must set a model, and `opencode models` in `--cwd` must list it, because opencode 2.3.0 runs an agent whose model it cannot reach on another model without a warning (devbox, with no Mistral provider, started the agent on DeepSeek V4.1 Flash Free). These opencode runs and the tab both get the caller's `OPENCODE_CONFIG`, `OPENCODE_CONFIG_DIR` and `OPENCODE_CONFIG_PROJECT_DISABLE`, and `OPENCODE_CONFIG_CONTENT` set to the agent, because the tab's shell otherwise inherits the herdr server's environment; other variables, such as a provider's API key, still come from the herdr server. Starts and restores also pass the caller's or recorded `OPENCODE_CLI_CONFIG_CONTENT`, with `prompt.paste` defaulting to `"full"` so the composer shows the text. When a brief stalls in Claude, Codex or opencode, or no turn starts within 5 s of it, claude-tools presses Enter once if the idle or done agent's visible composer matches the entire brief. An opencode box at its height limit may hide earlier rows, so claude-tools leaves it alone. Herdr reads the box and sends Enter in separate calls, so an edit between them can still be submitted. The start waits for `working` or `blocked` within the original 60 s deadline. `agent stop` presses Ctrl+C, which ends the TUI when its input box is empty and clears the box first otherwise.
- `agent start NAME --kind codex` types `export CODEX_HOME=...` (`unset CODEX_HOME` when the caller has none) in the tab's shell, because the shell inherits the herdr server's environment, not the caller's, and then starts `codex -s workspace-write -c sandbox_workspace_write.network_access=true -a never`, with `-m` from `--model` and `-c model_reasoning_effort=` from `--effort` when given; without `--model` Codex uses its configured defaults. Codex's efforts differ from Claude's and between models (some models list `ultra`, some do not), so before the tab opens `--model` must be a slug in `models_cache.json` of `CODEX_HOME` (default `~/.codex`), the file Codex keeps, and `--effort` one of that model's `supported_reasoning_levels`. `--effort` without `--model` is refused, because the tool does not know the model Codex would take from its config. `--account` and `--permission-mode` are refused, each with its own reason, and so is `--agent`, as for Claude. The brief goes out like opencode's, as one prompt that waits for a turn to start. Codex asks `Trust this folder?` only in a git repository it has not trusted, which a new worktree is; a start whose screen shows `Trust this folder?` and `› 1. Trust and continue` presses Enter, which saves the trust in `config.toml` of `CODEX_HOME` as answering by hand does. Each kind answers only its own trust screen. Claude's `--effort` is checked by the command against `low, medium, high, xhigh, max`, so a wrong value exits 1 like the other refusals, and an empty `--model`, `--effort`, `--account` or `--agent` is an argument error. With `HERDR_PANE_ID` set and no `CLAUDE_TOOLS_HERDR_SESSION`, a failed lookup of the caller's pane fails the start instead of opening the tab in the workspace someone has focused. When a step fails after the tab exists, the cleanup closes the tab even when stopping the agent fails.
- `agent watch NAME-REGEX` follows herdr's own agent events over its socket instead of polling. herdr sends `pane.agent_status_changed` only for a pane named in the subscription, so the watcher subscribes to the pane of each matching agent, and to the topology events (`pane.agent_detected`, `pane.updated`, `pane.moved`, `pane.closed`, `pane.exited`, `tab.closed`, `workspace.closed`), after which it reads `agent.list` again and subscribes anew when the set of panes changed. Closing a tab or a workspace sends only `tab.closed` or `workspace.closed`, not `pane.closed`. A turn is finished when the status in the pushed events goes from `working` or `blocked` to `idle` or `done`, the same rule herdr uses for `completion_seq`. The events count, because herdr clears `completion_seq` at the next state change, so a read after a quick next turn shows none. When the watcher missed events, such as during a lost connection, it counts a turn when `completion_seq` changed between two reads; it compares with `!=`, because a restarted server numbers from 0 again. herdr does not replay events from before a subscription, so the watcher prints each matching agent's state at start. An `events_lost` or `pane_not_found` answer makes it read and subscribe again at once; any other error prints an `ALERT` and it tries again every 5 s. An agent whose session id changed under the same name prints as a new agent. It reads no screen or transcript: the orchestrator reads an agent with `herdr agent read`, which collects the history of Claude's alternate screen for an idle agent (herdr 0.8.0 and later).
- An agent sends a question or a result to its orchestrator with `herdr agent prompt`, as `agents/reference/headless-clis/herdr.md` describes; claude-tools keeps no inbox.

## Config lock

`claude-accounts` rewrites a `.claude.json` only while it holds the lock directory `<file>.lock` (`libexec/config-lock.sh`). Claude Code holds the same directory while it writes the file (a mkdir lock, read from the 2.1.301 binary: stale after 10 s without an mtime change), so a write of a live session cannot land between the read and the move.

- Our holds are well under 10 s, so the helper never refreshes its lock. A holder that keeps one longer can lose it to a stale break; the break is best effort between our own runs. Our runs take turns on `<lock>.break` and read the age again inside the turn, so a lock another run broke and took meanwhile is not removed. The empty `.break` file stays, because removing it while another run waits on its flock lets a third run make a new file and take a second flock, and then two runs break at once.
- The lock directory stays empty, as Claude Code expects, so Claude Code can break a lock a dead holder of ours left. A holder recognises its own directory by inode plus birth time, read right after `mkdir`; a filesystem that reports no birth time fails the lock. `lock` and `unlock` run in the same shell, because the identity lives in a variable of that shell. Two directories created within one kernel clock tick can share both values (about 4 ms on kernel 6.12, finer with multigrain timestamps from 6.13). The check and the `rmdir` of an unlock are two commands, so a lock taken between them is lost.
- `claude_config_lock_all` takes the locks of several files, in order, or none. It waits half a second for each; when one is held, it releases the others and tries again after a growing pause until 10 s have passed, so no lock it holds ages toward Claude Code's 10 s bound while it waits. A held lock fails the call with "config: not changed" and changes no file.

## Invariants

Keep these true in every change:

- The main account's files stay in `~/.claude`. The default claude-desktop-extra profile and the IDE extensions read only that folder, and Claude Code finds `~/.claude.json` only with `CLAUDE_CONFIG_DIR` unset. Never run the main account with `CLAUDE_CONFIG_DIR=~/.claude`: that writes a second config, `~/.claude/.claude.json`, and a login there leaves `~/.claude.json` naming the old account, so `list` shows the wrong email. `list` marks the main account's links `split` while that file exists. Renaming the main account writes its name file; deleting it is refused.
- `sync_config` writes a profile's `.claude.json` only while no `claude` process runs with that profile, because a running session holds the MCP servers and onboarding keys in memory; only keeping an outside preference key was checked. `sync_config` checks with `in_use` itself, so `update`, `add` and `login` skip a profile in use and say so, and `cmd_delete` checks too, because a running session writes its files back into a deleted folder. `prefs` is the exception: it writes the keys in `account-prefs.json` while sessions run, because a running session keeps a key written to its `.claude.json` from outside (checked on 10-10-2026 with Claude Code 2.1.296). To check that with the installed version, while a session runs with `~/.claude.json`:
  1. Add a probe key: `t=$(mktemp ~/.claude.json.XXXX) && jq '.zzProbe=1' ~/.claude.json > $t && chmod 600 $t && mv $t ~/.claude.json`.
  2. Use the session until `stat -c %y ~/.claude.json` shows a newer time, which means the session wrote the file.
  3. `jq .zzProbe ~/.claude.json` prints `1` when the session kept the key. If it prints `null`, `prefs` must skip accounts in use, as `sync_config` does.
  4. Remove the key the same way with `jq 'del(.zzProbe)'`.
- Before linking, `cmd_update` moves the files of a profile's own copy of a shared folder into `~/.claude` with `fold_dir`, also only while no session runs with that profile. `relink` does the same for the folders in `session_dirs` (`projects`, `plans`, `file-history`, `sessions`), so a Home Manager switch links a profile's own copy of one once no session runs with the profile; until then `relink` and `update` name the folder and do not fail. Before that, `relink` deletes each `sessions/<pid>.json` whose process has ended, because Claude Code leaves that file behind only when a session dies without cleanup. A file `~/.claude` already has keeps its copy, and the profile's copy stays in `<folder>.unmerged` inside the profile.
- `sync_config` copies three things from `~/.claude.json`: `mcpServers`, `lastOnboardingVersion`, and every folder with `hasTrustDialogAccepted`. Then it writes the values in `account-prefs.json`, so a new account starts with them. `claude auth login` leaves `hasCompletedOnboarding` unset, and without it the first interactive start reruns the first-run wizard, which opens on the theme picker and then asks for a login method again. `account-prefs.json` therefore sets `hasCompletedOnboarding`, and `prefs` writes it into `~/.claude.json` too, which a new login on the main account leaves without it.
- Delete runs `rm -rf` on the profile folder. `rm` removes the symlinks and never follows them, so `~/.claude` is untouched.
- A claude-desktop-extra profile NAME runs Claude Code in `~/.claude-NAME`, so an account with a desktop profile keeps its folder equal to its name. After renaming such an account, run `claude-desktop --delete-profile=OLD`, move `~/.config/Claude-OLD` to `~/.config/Claude-NEW`, and run `claude-desktop --create-profile=NEW`.
- A write through the `settings.json` symlink keeps the link. This was checked on 14-11-2026 with Claude Code 2.1.325 by running `/tui default`, `/tui fullscreen` and a `/config` toggle in a scratch `CLAUDE_CONFIG_DIR` whose `settings.json` linked to another file. A tool that rewrites the file with `jq ... > new && mv new settings.json` replaces the link with a plain copy, and that profile then misses every later change to `~/.claude/settings.json`. `list` shows `broken` in the Links column for such a copy.
- `relink`, which each Home Manager switch runs after Home Manager writes `~/.claude/settings.json`, and `update` repair a profile whose `settings.json` is a plain copy. Every value the copy has and `~/.claude/settings.json` lacks goes into `~/.claude/settings.json`; an array and an empty object count as one value. A key someone removed from `~/.claude/settings.json` after the copy was made therefore comes back from the copy. When the copy sets a value that `~/.claude/settings.json` sets differently, `~/.claude/settings.json` keeps its own value and the copy stays as `settings.json.unmerged` in the profile. They repair it also while a session runs with the profile, and the new link replaces the copy in one rename. The session keeps the settings it loaded until it saves a setting or restarts, and a save reads the file through the link and changes only its own key, so the session writes none of the copy's old values into `~/.claude/settings.json` (checked on 14-11-2026 with Claude Code 2.1.325: `/tui default` after the swap kept a key only the target held, and `/config` then showed the target's values). A copy that is not one JSON object stays, and the command exits 1 after it links the profile's other entries. A copy or `~/.claude/settings.json` that changes while the command reads it is read again, up to 3 times; the last check and the rename are two steps, so a save in the microseconds between them is lost. When `~/.claude/settings.json` is itself a link, the command writes the file it points at.

## Changing the code

1. Edit `src/claude_tools` or `libexec/`. When the `claude` function needs new behaviour, add a command and call it from `share/claude-tools.sh`; keep paths and names out of the shell config.
2. Run `nix fmt` from the repository root. It runs ruff with `ruff.toml` on `src`, and shellcheck with `.shellcheckrc` on `libexec`, `share` and `tests` (`tooling.nix`), and exits non-zero on a finding. 3. Deploy, then run the commands against the real accounts. A change to `accounts` is done when every one of these holds:
   - `claude-tools accounts list` shows every account with its email and `ok` links.
   - `claude-tools accounts update` prints `config: synced` for each profile with no running session and exits 0.
   - `add tmp-x </dev/null`, then removing one link in `~/.claude-tmp-x`, makes `list` show `broken` for it.
