# Claude account tools

`claude-tools` runs several Claude Code accounts on one machine at the same time, one config folder per account, shows their usage and logins, and keeps Claude agents in herdr running across usage limits. It runs on nixos-desktop and nixos-rog under `oruc`, and on devbox under `omer`. Home Manager installs it (`home-manager/modules/claude-tools.nix`). It reads the account list `accounts.json` and the shared preferences `account-prefs.json` from `~/.config/claude-tools`, where `home-manager/modules/claude-tools.nix` links them: `accounts.json` from the sops key `claude-tools-accounts`, because it holds emails and organizations, and `account-prefs.json` from an attribute set in that module. `CLAUDE_TOOLS_DATA` names another folder.

`claude-tools --help` lists the commands, and each command prints its own `--help`, except `rotate` and `accounts`, which pass their arguments on: `claude-tools rotate --help` prints `claude --help`, and `claude-tools accounts help` lists the account commands.

| Command | What it does |
|---|---|
| `accounts` | account folders, links, preferences and logins (`libexec/claude-accounts`, bash) |
| `usage` | the usage cards, the cache, `--order` |
| `rotate` | runs `claude` with the account picker and moves a session at a usage limit |
| `limit-switch` | moves herdr agents at a usage limit and starts them again after a herdr restart |
| `agent start\|stop\|watch` | named Claude agents in herdr tabs, and the lines that wake their orchestrator |

## Package layout

- `src/claude_tools`: the Python package, stdlib only. `cli.py` builds the argument parser from each command module's `add_parser`, and prints the completion words from it. `commands/` holds one module per command with its workflow, and the modules beside it hold what several commands share: `settings.py` (paths and environment, read once per run), `accounts.py`, `usage.py` (reading and caching usage), `selection.py` (the account order), `display.py` (the display rules of a usage window: reset minute, tone, pace, spans), `terminal.py` and `picker.py` (cards and the account list), `herdr.py` (the herdr CLI and its socket), `agents.py` (Claude and codex processes in herdr panes), `watch.py` (`agent watch`), `limits.py`, `store.py` (JSON files, file locks and the clock) and `errors.py` (the errors a command reports).
- `libexec/`: `claude-accounts`, which `claude-tools accounts` runs with the rest of its arguments; `login-browser`, the `BROWSER` of a login; `config-lock.sh`, the `.claude.json` lock that `claude-accounts` sources. They stay bash because the lock reads a file's birth time with `stat`, which Python 3.14 cannot read.
- `share/claude-tools.sh`: the `claude` shell function and the completion of `claude-tools`, for zsh and bash. Home Manager's zsh sources it.
- `pkgs/claude-tools.nix` builds the package with `buildPythonApplication` and writes the store paths in place of `@libexec@` in `settings.py` and of `@bin@` in `claude-accounts` and `claude-tools.sh`.
- The package holds no comments or docstrings, only shellcheck directives beside the lines they cover: facts that are not usage live in this README, usage lives in `--help`, and lint settings live in `ruff.toml` and `.shellcheckrc`.

## Accounts

| Account | Folder | `CLAUDE_CONFIG_DIR` | Account config |
|---|---|---|---|
| The main account (named in `~/.claude/.claude-profile-name`; without that file, the accounts.json account its login matches, written there, else `main`) | `~/.claude` | unset | `~/.claude.json` |
| Every other account | `~/.claude-<folder>`, marked by a `.claude-profile` file | `~/.claude-<folder>` | `~/.claude-<folder>/.claude.json` |

An extra account's name is the content of its `.claude-profile` file, or `<folder>` when the file is empty; `add` and `rename` write the name into it. `rename` moves an idle account's folder to `~/.claude-<new name>`. While a session runs with the account, `rename` leaves the folder where it is, because the session keeps writing to the path in its `CLAUDE_CONFIG_DIR`. That folder still holds the old name's path, so `add` and `rename` put a new account with that name in `~/.claude-<name>-2` (or `-3`, and so on).

- Each machine logs in to each account on its own, with a browser login (setup-token logins cannot run Remote Control). Never copy a `.credentials.json` to another machine: Claude Code rotates the refresh token on use, so the first refresh on one machine logs the other out. For the same reason no tool of ours refreshes a token (Usage).
- An email that belongs to several organizations, such as a personal Max plan and a Team seat, needs one account per organization, because a login holds one organization. After `add`, the Org column of `list` shows which organization the login picked; `personal` is the email's own organization. The plan column adds the usage tier (5x, 20x), which only the credentials file holds, as `rateLimitTier`.
- Each extra folder symlinks the entries in the script's `shared` array to `~/.claude`, so settings, skills, hooks, rules, plugins, themes, sessions (`projects`), rewind checkpoints (`file-history`), and plans are one copy for every account. A session resumed under another account keeps its session ID and numbers its checkpoints from that account's `file-history`, so a separate copy per account reuses checkpoint names and rewind can restore another account's file content. Claude Code creates `projects`, `plans` and `file-history` in `~/.claude` only when the main account runs, and a profile cannot create them through its link, so `add` and `update` create them when they are missing; without them a profile's sessions are never saved and `--resume` finds nothing. `list` shows `broken` for a link that points at nothing.
- `history.jsonl` (the prompt history behind the up arrow) stays per account. Claude Code 2.1.292 never reads or writes it through a symlink, and its retention prune rewrites the file, which would break a hard link.
- `.credentials.json` and `.claude.json` stay per folder. Claude Code rotates the OAuth refresh token on use, so two accounts sharing one credentials file log each other out. `.claude.json` holds the account identity next to the MCP servers.
- `.claude.json` also holds preferences that some commands save per account, such as the `/focus` view (`briefTranscript`), so a new profile starts without them. Put a preference every account shares in `settings.json` when it has a key there, as `"viewMode": "focus"` does for focus view and `workflowSizeGuideline` does for the dynamic workflow size; /config may hide a row while a settings file sets its key, so change such a value in the settings file. `cc-setting KEY` shows whether a key has a `settings.json` key. Otherwise add the key and its value to the `account-prefs.json` attribute set in `home-manager/modules/claude-tools.nix`, as `leftArrowOpensAgents` is. `claude-tools accounts prefs` writes those values into `~/.claude.json` and every profile's `.claude.json`, and each Home Manager switch runs it. A value changed in /config stays in that one account until the next switch writes the declared value back.
- `claude-tools.sh` makes `claude` a shell function: `claude --account NAME` runs one session on NAME, and an interactive `claude` in a terminal without `CLAUDE_CONFIG_DIR`, `CLAUDE_TOOLS_ROTATE_ID` or `CLAUDE_TOOLS_PLAIN` runs `claude-tools rotate`.

## Logins

- `accounts.json` comes from the `claude-tools-accounts` key of `secrets/agents.yaml`, because it holds account emails and organizations and this repository is public; sops-nix decrypts it for the user and `home-manager/modules/claude-tools.nix` links it into `~/.config/claude-tools`. Edit it with `sops` as `docs/devbox.md` (Network and secrets) describes, then switch each host. It lists every account with the email and organization its login must show and the display name of the Brave profile that holds its claude.ai session. An account name means the same login on every device; the `~/.claude` account's name file says which one it is there (`own-team` on devbox, `work1` on nixos-rog).
- `accounts login NAME` creates the account's folder when the device has none, runs `claude auth login --claudeai --email EMAIL` with `BROWSER=libexec/claude-tools/login-browser`, and then checks `claude auth status` against accounts.json. A login that picked the wrong organization fails with both values printed and is logged out again.
- `login-browser` opens the authorize URL in the Brave profile whose display name is `CLAUDE_TOOLS_LOGIN_BRAVE_PROFILE`, so the claude.ai session of that profile signs in; unset or empty opens Brave's last profile. Each device resolves the name to its own profile folder through the browser's `Local State` file (Brave is brave-origin on nixos-desktop and nixos-rog). A name the device has no profile for gets a new profile in the folder `Claude <name as a slug>`: its `Preferences` file names it before Brave first opens it, and Brave takes that name into its profile list (checked on 19-10-2026 with brave-origin and a scratch `--user-data-dir`). An existing folder is never written. With `CLAUDE_TOOLS_LOGIN_URL_FILE` set, it writes the URL to that file and opens nothing.
- `login NAME --on HOST` runs the same login on HOST in a tmux session there, under `timeout --foreground`, because without `--foreground` claude stops on its first terminal read (state T) before it prints the URL. The remote `login-browser` writes the URL to a file; this device opens it and tunnels the browser's redirect to the remote claude's `localhost` port with `ssh -L`.
- `login-window` is the widget's Log in button. It runs `login` in a new Ghostty or Konsole window with `~/.local/bin` on `PATH`, because plasmashell, which starts it, has no `~/.local/bin` on `PATH`, where `claude` lives on two hosts.
- `login-all --list` prints the accounts that are missing, logged out, or end within 5 days; `login-all` logs in to each of them.

## Usage

- `claude-tools usage`, which `claude-tools accounts` without a command runs for the cards, writes each account's 5 h and 7 d use, reset times, login end and state to `~/.cache/claude-tools/usage.json` (`claude-tools-usage.timer`, every 10 min). `claude-tools` adds `~/.local/bin` to `PATH` before any command, for the same plasmashell reason as `login-window`, because the widget runs it and `rotate` and `limit-switch` probe accounts in the same process. It also drops the `bin` of its own interpreter, which the `buildPythonApplication` wrapper puts first on `PATH`, so the `claude` it starts finds the profile `python3` from `pkgs/agent-python.nix` instead of the plain one.
- It never refreshes a token. While an account's access token stays valid for more than 5 min, it reads the usage endpoint with that token. Otherwise, and when the endpoint answers 401, it runs a one-turn `claude -p` on haiku in `~/.cache/claude-tools/probe` and reads the `rate_limit_event`, so Claude Code refreshes the token itself and writes the new one to its own credentials file. Only the probe's `result` event and its stderr name a failure, because its `init` event lists commands such as `/login`. A failed reading keeps the last numbers and marks them stale. It checks up to 4 accounts at once, and the remote caches beside them. With `--max-age`, an account read within that age keeps its reading. `updated` in the cache is the start of the run, or the check time of the oldest reading the run reused without checking, such as one within `--max-age` or one whose check missed the deadline; a failed check's stale reading does not count, so a failing account does not make every `--max-age` caller check again. A run with `--account` that leaves an account out leaves `updated` as it was.
- Logins on other devices show in the cards because `remote_hosts` in accounts.json names, per device, the devices whose cache it reads over ssh. A device whose everyday key has a passphrase reads with `~/.ssh/id_ed25519_claude_usage`, which the target accepts only for `cat .cache/claude-tools/usage.json`: nixos-config `machines/nixos-rog/claude-tools-usage-read.nix` declares it for nixos-rog.
- The cards show one card per account in accounts.json, and the widget (`pkgs/claude-accounts-widget`) one row per account in accounts.json; an account a host has that accounts.json does not list does not appear, and the widget's login badge and best account ignore it too. `usage`, `rotate`, `limit-switch` and `agent start` skip such a folder as well (`Accounts.usable` in `accounts.py`), so a dropped account is neither read nor chosen, while `limit-switch` still moves an agent that runs on it to a listed account. `accounts list` and `accounts dirs` still show the folder, and `accounts delete` removes it. The widget's best account is the first of `usage --order` (the `order` list of `usage --json`), the one `rotate` would start on. Usage limits belong to the account, so each account appears once with the newest reading from any host, a fresh one before a stale one, followed by one login line per host (`no login` means that host never logged in to it). `usage --json` adds this list as `combined`, and `usage --watch` redraws the cards every 30 s. A pace mark follows each percent: ▲ when the account uses the window faster than an even spread to the reset, ▽ when it has room to spare, ≈ within 5 points of even. `usage --json` rounds every `resets_at` of `accounts` and `combined` to the nearest minute, because the API's reset times sit a fraction of a second either side of the full minute, and adds finished display values to each window there: `tone` (`green`, `amber` from 70%, `red` from 90%), `pace` (points ahead of an even spread, rounded) with `pace_state` (`ahead`, `behind`, `even`, within 5 points) and `pace_tone` (`amber` ahead, `red` from 20 points ahead, `green` behind, `dim` even), `reset_in` (`now` or a span such as `2h 53m`) and `reset_clock` (`HH:MM`, with the weekday from 1 d ahead), and `login_left` next to each `login_expires_at`. These rules live in `display.py`; the cards and the widget print the fields and compute nothing of their own, so both show the same minute.

## Rotation

- `claude-tools rotate` opens each interactive `claude` with an account list: every account in accounts.json with its 5 h and 7 d bars and pace, best first, with the reason for each place, and the highlighted account's windows and login below. Enter starts the highlighted account, 1-9 start a row, `r` checks every account's usage now and opens the list again, and `q` starts nothing. Accounts logged out on this host, and accounts this host has no folder for, are listed with their `accounts login` command but cannot be picked. A list that fails to open starts the recommended account.
- `usage --order` prints the same order. Every account follows one rule, and its plan only scales its room, so a 20x account has 4 times the room of a 5x account. Two burn rates measure our use: the 5 h rate sums the use per hour of every running 5 h window, at least one 5x window spent evenly over 5 h, and the weekly rate sums the use per hour of every weekly window that has run for at least 5 h, at least one 5x week spent evenly. An account lasts until its 5 h room (up to 90%) runs out at the 5 h rate or its weekly room (up to 95%) runs out at the weekly rate, whichever comes first. A window counts only while it runs and only when its room runs out before the window's own reset, so a window that has not started, has no limit, or resets first does not stop the account. It comes first when the weekly rate could not spend its weekly room before the weekly reset, because that room would otherwise go unused; inside that group, the accounts that last to their 5 h reset go before the others, then the soonest weekly reset goes first. Next come the accounts that last to their 5 h reset, or for 5 h when no 5 h window runs, soonest weekly reset first, so the room that expires first is spent first. After them, under the picker's "reaches a limit before its 5h reset" line, come the accounts that would reach a limit first, the one that lasts longest first, with the window that runs out first in the reason, so a move does not land next to a limit. Accounts held back after a limit, at 90% of 5 h or 95% of 7 d, or without a reading go last. The per-model weekly limits stay out of the order, because one blocks only sessions on its model and the picker does not know the model a session will use.
- `rotate` and `limit-switch` choose the next account the same way (`selection.py`). After a usage limit, `hold_limit` holds the account back until the reset that the limit message names. A message without a reset time, such as a model limit, holds it until the reset of a full window in a reading taken then, else for 1 h. An account accounts.json does not list gets no reading, so it is held for 1 h. A reset time more than one window ahead (5 h for a session limit, 7 d for a weekly one) belongs to an old message, so it holds nothing. The holds live in one file, `~/.local/state/claude-tools/limits.json`, written under a lock, with ended holds dropped on each write; a new hold replaces the account's earlier one, because the newest limit message is the latest word. `next_account` then reads the usage of every account that is not held back and was not read in the last minute, with a 2 min wait budget for accounts that already have a cached reading, and returns the first of the order that nothing blocks. An unfinished check keeps its last reading; accounts without a cached reading must finish first and can exceed that budget.
- `rotate` passes every argument to `claude`. It reads `claude --help` once per installed binary, because it costs a node start, to learn which options take values and which words are subcommands; a subcommand, `-p`, `--version`, `--help` or a run without a terminal runs plain `claude`.
- It starts each session on the chosen account and moves the session to the next account when its turn fails on a usage limit: the StopFailure hook `libexec/rotate-on-limit`, which `home-manager/modules/claude-tools.nix` registers with the matcher `rate_limit`, writes the hook input to `$XDG_RUNTIME_DIR/claude-tools/rotate/ID-PID.json`, which carries the limit message as `last_assistant_message`. ID is the `CLAUDE_TOOLS_ROTATE_ID` that `rotate` gives its Claude process, and PID is the nearest Claude process above the hook, so a `claude -p` started inside the session inherits the ID but not the PID, and its limit leaves the session alone. A Claude Code session without `CLAUDE_TOOLS_ROTATE_ID`, such as a herdr agent, writes nothing. `rotate` holds the account, stops the session and resumes it with `--resume` on the next account. The resume command keeps the other arguments but not the session flags (`--resume`, `--continue`, `--session-id`, `--fork-session`, `--from-pr`) nor `--worktree` and `--tmux` with their values, and the resumed session starts in the folder the StopFailure hook reports as its `cwd`, so a session started with `--worktree`, or one that moved into a worktree, continues in that folder instead of a new git worktree. When no account is free, it waits until the first time any account, its own included, leaves the blocked group, else 1 h, and then resumes the session on the best account, its own one too when that limit has reset. A prompt typed into the session after the limit cancels the move and the wait; a `!` command does not, because it sends no turn to the model.

## Limit switch

`claude-tools limit-switch scan` keeps Claude agents in herdr running; `claude-tools-limit-switch.timer` runs it every minute on devbox.

- A scan first restores, then switches each named idle Claude agent whose session transcript ends in Claude Code's usage limit error: the last assistant entry has `isApiErrorMessage` and `apiError` `usage_limit_reached`, and its text gives the reset time ("You've hit your 5-hour limit · resets ..." since Claude Code 2.1.312, "session limit" before). The screen alone never moves an agent, because an agent can print the same sentence when it quotes a log or a test. The hold counts the reset from the time of that entry. A switch types `/exit` in the agent's pane, sets `CLAUDE_CONFIG_DIR` there, starts Claude like `claude --resume <session>` with its other old arguments under the same agent name, and tells the agent to continue. The resume adds `--dangerously-skip-permissions`, so an agent never stops at a permission prompt after a switch. It adds nothing to an agent that was started with `--settings` or `--permission-mode` and without `--allow-dangerously-skip-permissions`, because that flag turns the session into bypass mode, so such an agent keeps its own permission settings, as the Status Lantern audit agent does. The accounts share `~/.claude/projects`, so `claude --resume <session>` continues the same conversation under another account. A scan holds the account and moves the agent to `next_account`. When that is the agent's own account, because its limit has reset, the scan only sends the resume message.
- `~/.config/claude-tools/resume/NAME` replaces the resume message for agent NAME. `--resume` brings back a fixed-interval `/loop` but not a self-paced one or a Monitor, so an agent that runs them needs a message that checks CronList first (`agents/reference/unattended-agents.md`). With a scheduled task, `/exit` opens "Background work is running"; the switch presses Enter only on its selected first choice "Exit and stop tasks", so a screen that only quotes the dialog gets no Enter.
- herdr itself resumes Claude as plain `claude --resume`, without the flag and the account (`agents/reference/headless-clis/herdr.md`), so its own restore is off. Each scan records the named Claude agents and the server process in `agents.json`. When the next scan finds a different server process, it starts each recorded agent that is missing like `claude --resume <session>`, with the same flag rule, with its account, in its old pane or a new workspace, and sends it the resume message. An agent that is missing while the same server runs was ended on purpose; the record keeps it under `ended` with its last session for 30 days, and only `resume NAME` starts it again, the same way. `resume` restores first, because after a server restart the other missing agents need the restore, and the record would otherwise mark them as ended. When no server runs, a scan starts it (`herdr-default.service` for the default session).
- A start waits until the pane's shell runs typed input: in a folder with an `.envrc` the shell first loads direnv, and text typed during that load shows on screen but never runs. A start that fails closes the workspace it made.
- A scan skips an agent for 5 min after a move it tried, and a restore waits 5 min after a failed start, because the transcript keeps the old limit error as its last reply until the agent answers, and a scan every minute would otherwise try again on each run.

## Agents and the orchestrator

- `agent start NAME --cwd DIR` opens a tab named NAME in the caller's workspace with `--no-focus`, so the view of whoever looks at herdr stays where it is. With `CLAUDE_TOOLS_HERDR_SESSION` the tab opens in that session's own workspace, because the caller's pane id belongs to its own session. The brief goes as one prompt that names the file, so a long brief never goes through argv. `--permission-mode` waits until the footer shows the mode before the brief goes out, because a mode switched by keypresses after start raced the brief once. A name whose agent just exited is waited for, since herdr frees it a moment later. When any step fails after the tab exists, the agent that started is stopped and the tab is closed, so the same command can run again.
- `agent stop NAME` refuses, with exit 1, while herdr shows the agent `working` or `blocked` at a question or approval, and prints the `herdr agent read` and `herdr agent wait --until idle --until done` commands for the session it uses, because an orchestrator that stopped an agent after its done message cut off the answer it was writing to Omer. `--force` cuts the agent off on purpose. Every stop presses Esc and then Ctrl+C before it types `/exit`, because Claude Code puts an interrupted prompt back into the input box, and `/exit` typed after it was sent as part of that prompt.
- `agent watch NAME-REGEX` follows herdr's own agent events over its socket instead of polling. herdr sends `pane.agent_status_changed` only for a pane named in the subscription, so the watcher subscribes to the pane of each matching agent, and to the topology events (`pane.agent_detected`, `pane.updated`, `pane.moved`, `pane.closed`, `pane.exited`, `tab.closed`, `workspace.closed`), after which it reads `agent.list` again and subscribes anew when the set of panes changed. Closing a tab or a workspace sends only `tab.closed` or `workspace.closed`, not `pane.closed`. A turn is finished when the status in the pushed events goes from `working` or `blocked` to `idle` or `done`, the same rule herdr uses for `completion_seq`. The events count, because herdr clears `completion_seq` at the next state change, so a read after a quick next turn shows none. When the watcher missed events, such as during a lost connection, it counts a turn when `completion_seq` changed between two reads; it compares with `!=`, because a restarted server numbers from 0 again. herdr does not replay events from before a subscription, so the watcher prints each matching agent's state at start. An `events_lost` or `pane_not_found` answer makes it read and subscribe again at once; any other error prints an `ALERT` and it tries again every 5 s. An agent whose session id changed under the same name prints as a new agent. It reads no screen or transcript: the orchestrator reads an agent with `herdr agent read`, which collects the history of Claude's alternate screen for an idle agent (herdr 0.8.0 and later).
- An agent sends a question or a result to its orchestrator with `herdr agent prompt`, as `agents/reference/headless-clis/herdr.md` describes; claude-tools keeps no inbox.

## Config lock

`claude-accounts` rewrites a `.claude.json` only while it holds the lock directory `<file>.lock` (`libexec/config-lock.sh`). Claude Code holds the same directory while it writes the file (a mkdir lock, read from the 2.1.301 binary: stale after 10 s without an mtime change), so a write of a live session cannot land between the read and the move.

- Our holds are well under 10 s, so the helper never refreshes its lock. A holder that keeps one longer can lose it to a stale break; the break is best effort between our own runs. Our runs take turns on `<lock>.break` and read the age again inside the turn, so a lock another run broke and took meanwhile is not removed. The empty `.break` file stays, because removing it while another run waits on its flock lets a third run make a new file and take a second flock, and then two runs break at once.
- The lock directory stays empty, as Claude Code expects, so Claude Code can break a lock a dead holder of ours left. A holder recognises its own directory by inode plus birth time, read right after `mkdir`; a filesystem that reports no birth time fails the lock. `lock` and `unlock` run in the same shell, because the identity lives in a variable of that shell. Two directories created within one kernel clock tick can share both values (about 4 ms on kernel 6.12, finer with multigrain timestamps from 6.13). The check and the `rmdir` of an unlock are two commands, so a lock taken between them is lost.
- `claude_config_lock_all` takes the locks of several files, in order, or none. It waits half a second for each; when one is held, it releases the others and tries again after a growing pause until 10 s have passed, so no lock it holds ages toward Claude Code's 10 s bound while it waits. A held lock fails the call with "config: not changed" and changes no file.

## Invariants

Keep these true in every change:

- The main account's files stay in `~/.claude`. The default claude-desktop-extra profile and the IDE extensions read only that folder, and Claude Code finds `~/.claude.json` only with `CLAUDE_CONFIG_DIR` unset. Never run the main account with `CLAUDE_CONFIG_DIR=~/.claude`: that writes a second config, `~/.claude/.claude.json`, and a login there leaves `~/.claude.json` naming the old account, so `list` shows the wrong email. `list` marks the main account's links `split` while that file exists. Renaming the main account writes its name file; deleting it is refused.
- `sync_config` writes a profile's `.claude.json` only while no `claude` process runs with that profile, because a running session holds the MCP servers and onboarding keys in memory; only keeping an outside preference key was checked. `sync_config` checks with `in_use` itself, so `update`, `add` and `login` skip a profile in use and say so, and `cmd_delete` checks too, because a running session writes its files back into a deleted folder. `prefs` is the exception: it writes the keys in `account-prefs.json` while sessions run, because a running session keeps a key written to its `.claude.json` from outside (checked on 10-10-2026 with Claude Code 2.1.296). To check that with the installed version, while a session runs with `~/.claude.json`:
  1. Add a probe key: `t=$(mktemp ~/.claude.json.XXXX) && jq '.zzProbe=1' ~/.claude.json > $t && chmod 600 $t && mv $t ~/.claude.json`.
  2. Use the session until `stat -c %y ~/.claude.json` shows a newer time, which means the session wrote the file.
  3. `jq .zzProbe ~/.claude.json` prints `1` when the session kept the key. If it prints `null`, `prefs` must skip accounts in use, as `sync_config` does.
  4. Remove the key the same way with `jq 'del(.zzProbe)'`.
- Before linking, `cmd_update` moves the files of a profile's own copy of a shared folder into `~/.claude` with `fold_dir`, also only while no session runs with that profile. A file `~/.claude` already has keeps its copy, and the profile's copy stays in `<folder>.unmerged` inside the profile.
- `sync_config` copies three things from `~/.claude.json`: `mcpServers`, the onboarding keys, and every folder with `hasTrustDialogAccepted`. Then it writes the values in `account-prefs.json`, so a new account starts with them. `claude auth login` leaves the onboarding keys unset, and without them the first interactive start reruns the first-run wizard, which asks for a login method again.
- Delete runs `rm -rf` on the profile folder. `rm` removes the symlinks and never follows them, so `~/.claude` is untouched.
- A claude-desktop-extra profile NAME runs Claude Code in `~/.claude-NAME`, so an account with a desktop profile keeps its folder equal to its name. After renaming such an account, run `claude-desktop --delete-profile=OLD`, move `~/.config/Claude-OLD` to `~/.config/Claude-NEW`, and run `claude-desktop --create-profile=NEW`.
- A write through the `settings.json` symlink keeps the link. This was checked on 26-09-2026 with Claude Code 2.1.283 by changing a setting with `/config` in a profile. Recheck it after a major Claude Code update: `list` shows `broken` in the Links column when a link was replaced.

## Tests

The end-to-end tests in `tests/` other than `prefs-e2e.sh` run on devbox against real Claude accounts and a real herdr server, each in its own herdr session or tmux server. Run them from a nixos-config checkout against the installed command, for example `pkgs/claude-tools/tests/agent-e2e.sh "$(dirname "$(readlink -f "$(command -v claude-tools)")")"`; each prints `PASS` and exits 0.

- `limit-switch-e2e.sh`: a switch held back while every other account is held, a switch, a scan that leaves an agent without a limit alone, a scan that leaves alone an agent that printed a limit message, a scan that moves an agent whose transcript ends in a limit error, a scan that holds nothing after an old one, the restore after a server stop, and `resume`. `CLS_E2E_AGENT_ARGS=settings` starts the agent with `--settings` and `--permission-mode dontAsk` instead of the skip flag and leaves out the `/loop` and background-work steps, and every check then shows that a switch and a restore keep the first two and add no skip flag. On a host where `omer` can `sudo -n -u sl-factory` and that user has an account folder, a last step starts an agent that runs as `sl-factory` and checks that `scan`, `resume` and `switch` leave it running and out of `agents.json`.
- `rotate-e2e.sh`: the account picker and its accounts.json list, the exit codes of `rotate`, and a move after a limit to the first account of the order.
- `agent-e2e.sh`: `agent start` with a relative `--cwd` and a running name, `agent stop` of a running and of an exited agent, its refusal of a blocked and of a working agent, `agent stop --force` of a working agent, and `agent watch` started before the agent, through a question that blocks it, a pane moved to another workspace, a watcher restart that missed a turn, the agent leaving through `agent stop` and through a closed tab, and a herdr server that stops and starts again. On such a host it also stops an agent that runs as `sl-factory` with `agent stop --force`, whose process environment `omer` cannot read.
- `prefs-e2e.sh`: `accounts prefs` and `config-lock.sh` against a scratch home, with no account or herdr: the declared value reaching the main account and a profile with their other keys and modes kept, a profile that already holds it left untouched, a failure that names an account file that does not parse, a wait for a lock held 2 s, a failure when a lock stays held past 10 s while the lock taken first keeps being touched, the break of a lock nobody touched for a minute, unlock of a missing lock under `set -e`, a lock that a holder killed with SIGKILL left and Claude Code's `rmdir` can break, unlock leaving a foreign lock alone, and three runs breaking one stale lock one at a time. It runs on any host and needs a folder that reports birth times for `PREFS_E2E_DISK_DIR` (`/var/tmp` by default); ext4 also hands an inode number back, which one case needs, and on btrfs or tmpfs that case prints `SKIP`. `E2E_LOCK_ROUNDS` sets the rounds of the repeated cases (20). Run it under `sandbox-run --rw /var/tmp`, because a case stops its own holder with `kill -9`.

The picker step reads a usage cache and a hold file that the test writes from the real cache with changed numbers, so it proves how the picker shows and orders those records, not how `usage` and `rotate` write them. The move step runs the packaged `rotate-on-limit` hook from the session's own bash mode (`! <hook> < limit.json`) with a made-up session limit message, on accounts that have room, so it proves the hook's walk up to the Claude process, its flag file under the inherited `CLAUDE_TOOLS_ROTATE_ID`, the account choice after a fresh reading and the resume. It does not prove Claude Code's StopFailure dispatch, the `rate_limit` matcher, the Home Manager registration or a real limit. The limit-switch scan steps append a made-up limit error to the agent's transcript, in the form Claude Code writes for a real limit, so no real limit stands behind it. `limit-switch-e2e.sh` starts the agent on the first account with a folder, or on `CLS_E2E_ACCOUNT`. `rotate-e2e.sh` starts its session on the first signed-in account of the usage cache, or `CR_E2E_R`, and takes the next two accounts that `accounts names` lists, or `CR_E2E_A` and `CR_E2E_C`, which need no login. It makes the first of those a `team 5x` account with a week at 93% and gives the signed-in account a week at 1%, so the picker must list the team account under the signed-in one, among the accounts that reach a limit before their 5 h reset, and holds the third account back. It drops the check time of every other account, so their readings stay out of the burn rates and the order does not depend on the host's accounts.


No test covers these, because a run cannot reach them for real:

- a move after a real usage limit, in `rotate` and `limit-switch`, with the session's memory kept across the move;
- the hold after a limit message without a reset time, such as a model limit, which reads the account's windows;
- the StopFailure hook handshake of `rotate`, including a nested `claude -p` whose limit must leave the session alone;
- the hold that `rotate` writes until the reset time of a limit message, its wait while no account is free, and a prompt typed during that wait;
- the hold that `scan` writes until the reset time of a limit message;
- that `scan` neither moves nor restarts an agent whose old limit message has passed, beyond the prompt to continue;
- `agent start`'s cleanup when herdr refuses the brief;
- the lock release of `prefs` and `update` when TERM ends them;
- that unlock leaves alone a foreign lock with our birth time and another inode, and that a lock is refused on a filesystem without birth times, because both need a filesystem that a test cannot make on demand.
